Per-platform status, stated at the level it has actually been verified  ·  CNA snapshot 009d40f5

ℹ

What changed since alpha.1. This page describes the current development snapshot (branch next, commit 009d40f5). v0.1.0-alpha.1 offered four platform implementations and three audio implementations; this snapshot offers seven platform implementations (three of them native and SDL-free), four audio implementations (one native and SDL-free), a build switch that can remove SDL entirely, a 32-flag capability contract (29 before), and a curated set of 25 renderer identities. Everything below is stated at the level the code and CI actually prove. Statements about CI describe what the workflow files at this snapshot configure, build, run and assert; we read those files and did not inspect run results (see the caveat under What CI actually covers).

Four separate axes

In this snapshot, “backend” is still too ambiguous to be useful. CNA makes four different decisions, plus one build switch that decides whether SDL is present at all:

AxisQuestion it answersSelection
Target operating systemWhich toolchain and OS ABI is this binary built for?CMake toolchain / target; reported by CNA::TargetPlatform
Platform implementationWho owns windows, events, input, timing and host services?CNA_PLATFORM — 7 implementations
Graphics rendererWho turns CNA draw calls into pixels?CNA_GRAPHICS_RENDERER and optional CNA_GRAPHICS_RENDERERS — 25 identities
Audio implementationWho opens playback and recording devices, and (for two values) mixes?CNA_AUDIO_PLATFORM — 4 implementations
(switch) SDL availabilityIs SDL configured, built and linked at all?CNA_ENABLE_SDL = AUTO (default), ON or OFF

The platform implementation implements CNA::Platform::IPlatform and supplies narrow services to a renderer. It does not decide the renderer, audio implementation or target OS. This is also why the old public CNA::Platform enum became CNA::TargetPlatform (Desktop, Android, iOS, Web): CNA::Platform now names the host-integration namespace. The axes are independent with hard exclusions, listed under combination rules.

Platform and audio implementations

OptionImplemented valuesDefaultBoundary

CNA_ENABLE_SDLAUTO, ON, OFFAUTOAUTO and ON configure SDL3 as before. OFF fetches, builds and links no SDL, and refuses any selection that genuinely needs it (platform or audio SDL3/SDL2; renderers SDL_RENDERER, SDL_GPU, FNA3D, FREEDIRECT).
 
# A display-free simulation that still uses SDL3 audio
cmake -S . -B build-headless \
  -DCNA_PLATFORM=HEADLESS \
  -DCNA_AUDIO_PLATFORM=SDL3 \
  -DCNA_GRAPHICS_RENDERER=HEADLESS

# Real SDL 2.30 host plus the low-level SDL2 audio-device selection;
# this snapshot does not enable a high-level XNA mixer/playback facade for SDL2
cmake -S . -B build-sdl2 \
  -DCNA_PLATFORM=SDL2 \
  -DCNA_AUDIO_PLATFORM=SDL2 \
  -DCNA_GRAPHICS_RENDERER=OPENGLES3

# Native X11, no SDL anywhere, ALSA audio with CNA's own mixer
cmake -S . -B build-x11 -G Ninja \
  -DCNA_ENABLE_SDL=OFF \
  -DCNA_PLATFORM=X11 \
  -DCNA_AUDIO_PLATFORM=ALSA \
  -DCNA_GRAPHICS_RENDERER=OPENGL33

# POSIX terminal host: CPU renderers only
cmake -S . -B build-terminal \
  -DCNA_PLATFORM=TERMINAL \
  -DCNA_AUDIO_PLATFORM=NULL \
  -DCNA_GRAPHICS_RENDERER=SOFTWARE
⚠

SDL2 is not a compatibility shim. It is real SDL 2.30 (fetched with FetchContent, not sdl2-compat) and a deliberately narrow backend: it has no clipboard, mouse-snapshot, gamepad or surface-presenter service, and no Vulkan surface. When both platform and audio select SDL2, CNA refuses SDL_RENDERER, SDL_GPU, FNA3D and FREEDIRECT because those renderer families link SDL3 directly. This prevents one process from mixing the two SDL generations.

⚠

Audio selection is ahead of audio parity. In modules/CMakeLists.txt, SOUND_ENABLED is defined for CNA_AUDIO_PLATFORM=SDL3 and CNA_AUDIO_PLATFORM=ALSA only. SDL2 and NULL builds omit the mixer, decoder and mixer-dependent tests; the XNA audio facade remains present but does not gain production playback from the SDL2/Null device classes (SoundEffect::Play() returns false). Null is therefore useful for deterministic configuration and device-contract work, not proof that a silent mixer consumes normal game audio. Audio System has the full implementation matrix.

Combination rules and hard exclusions

  • SDL2 and SDL3 never share a process. Three configurations are hard configure errors: platform SDL2 with audio SDL3 (which is what -DCNA_PLATFORM=SDL2 alone gives you, because audio defaults to SDL3), platform SDL3 with audio SDL2, and platform SDL2 with audio SDL2 plus a renderer among SDL_RENDERER, SDL_GPU, FNA3D, FREEDIRECT.
  • TERMINAL accepts only CPU renderers: SOFTWARE, PORTABLEGL, HEADLESS, STUB.
  • CNA_ENABLE_SDL=OFF refuses platform SDL3/SDL2, audio SDL3/SDL2 and the four SDL-linked renderers, with a message naming the reason.
  • Platform gates: WIN32 only on Windows targets; TERMINAL only off Windows; X11/WAYLAND only where their dev packages exist (and not on Windows, Emscripten, Android, iOS; Wayland also not on Apple); ALSA only on Linux.
  • Renderer combinations in CNA_GRAPHICS_RENDERERS obey three rules: PORTABLEGL cannot share a binary with a real-GL family (OPENGLES2, OPENGLES3, OPENGL33, WEBGL1, WEBGL2, OPENGL4); GDI cannot share with SOFTWARE; and identities gated to different operating systems cannot be mixed. See Runtime Renderer Selection.
  • A name outside the 25 public renderer identities is a configure-time error.

Native backends and SDL-free builds

The three native backends are the headline platform change of this snapshot. Each talks to the operating system's own window-system API and contains no SDL code; source scans and link-closure tests keep it that way. SDL3 remains the default and an excellent platform — the point is that “CNA without SDL” is now a configuration that exists and is tested. The dedicated page, Native Platforms (X11, Wayland, Win32), has dependency tables, capability differences, validation harnesses and exact CI evidence.

In CI

What "supported" means here

"Supported" is doing a lot of work in most framework documentation. This page avoids the word and names the level instead, because the difference between "there is code for it" and "someone ran it" is exactly the difference that costs you a weekend.

LevelWhat it means
Code path existsSources and CMake wiring are present for the target.
ConfiguresCMake accepts the target and the chosen renderer, and produces a build system.
Cross-compilesA full build completes from a different host operating system.
Runs under Wine or an emulatorThe binaries execute and render, but not on the operating system they target.
Runs on real hardwareSomeone ran it on the actual platform.
Covered by CIA workflow builds or tests it automatically on push and pull request — the only level that keeps working without anyone remembering to check.

These levels do not imply each other. The repository contains MinGW/Wine paths, and in this snapshot one automatic workflow uses them — but only for the Win32 platform module, not for a full engine build; the native-Windows lanes that build the whole engine still require manual dispatch. macOS and iOS have build workflows that trigger automatically (subject to the pinned-sibling caveat under CI). Android has source/NDK wiring and no workflow. Native Wayland has code and local test suites and no workflow.

Linux

Linux is CNA's primary development platform and carries most of its CI. It is where the largest number of renderers can be selected, where all seven platform implementations except WIN32 are offered, and where the project is developed on real hardware — the default renderer here is OPENGLES3, one of the five EasyGL profiles.

Which platform to pick depends on your session. SDL3 (the default) works on X11 and Wayland sessions alike and has the fullest capability set. Native X11 is the SDL-free choice for Xorg and Xwayland. Native Wayland is a direct Wayland client but has no CI. HEADLESS and TERMINAL need no display server. See Native Platforms.

The Windows-gated renderers are also driven from Linux: they are cross-compiled with MinGW-w64 and executed under Wine, so a Linux workstation is in practice the machine where the Direct3D ladder gets exercised too. See Windows for what that does and does not prove.

Practical requirements: the sharp-runtime sibling checkout (its next branch) for every build, easy-gl plus meta-gl for the default renderer, a C++23 compiler (CI uses GCC 14), and, for a windowed build, the X11/GL/Vulkan/ALSA/D-Bus development packages so the vendored SDL3 gets real video drivers. FFmpeg development packages are optional now. Building has the exact commands and package lists.

Windows

Windows has the largest platform-exclusive renderer set in the project: 5 renderers refuse to configure anywhere else — DIRECTX9, DIRECTX11, DIRECTX12, DIRECT2D and GDI. The default renderer on Windows is SDL_RENDERER. Two platform choices exist besides SDL3: the native WIN32 backend (user32/gdi32/WGL, no SDL, but no gamepad, IME or drag-and-drop) and HEADLESS. Windows has no SDL-free audio: a fully SDL-free Win32 build must use CNA_AUDIO_PLATFORM=NULL.

⚠

The repository provides MinGW cross-build and Wine/DXVK or vkd3d-proton execution paths, but none is an automatic workflow in this snapshot for the full engine. The automatic Windows evidence is narrower: platform-ci.yml cross-builds the standalone platform harness with mingw-w64 and runs it under Wine on every push. The native MSVC workflows (DIRECTX11, DIRECTX12 and DIRECT2D in one, GDI in another, a Headless content-pipeline build, and the Win32 harness on MSVC) are all manual dispatch. Treat runtime claims as results from the exact manual configuration, not as continuous native-Windows coverage.

Two further Windows facts worth knowing before you plan a release:

  • FFmpeg video is never built for Windows. CNA_ENABLE_VIDEO=AUTO silently falls back to the no-video backend on Windows and MinGW, and ON is a configure error. Video and VideoPlayer still compile and link; without a decoder they throw System::NotSupportedException at run time.
  • The full-engine MinGW cross-build is not covered by CI. Only the platform module is cross-built and run under Wine automatically (plus a MinGW header-compatibility check for the experimental C API); building the engine for Windows is exercised by hand or by the manual MSVC workflows.

Web (Emscripten)

The web target is real and has browser workflows (with the sharp-runtime pin caveat under What CI actually covers). Five renderers are Emscripten-only — WEBGL1, WEBGL2, CANVAS, HTML_DOM and SVG_DOM — and WEBGL2 is the default. Multi-renderer Emscripten jobs also configure and link compatible browser sets, and the workflows pin emsdk 6.0.3. The platform is always SDL3 here; CNA_PLATFORM=EMSCRIPTEN is reserved and refused.

⚠

There is no save persistence on the web at all. CNA mounts no persistent file system: no IDBFS, and it never calls FS.syncfs. Everything StorageDevice or GamerServices writes lands in Emscripten's default in-memory file system and is silently discarded when the page reloads. Nothing fails, nothing warns — the data is simply gone. Plan around it (persist through your own browser storage) before you ship a browser build.

ℹ

Your Game object no longer must be heap-allocated on the web. Earlier builds unwound the caller's stack, so a stack-allocated Game was silently corrupted. In this snapshot Game::Run() blocks on the caller's own stack through Asyncify, so an ordinary local MyGame game; game.Run(); is supported. CNA-owned application executables link Asyncify automatically; an external final executable that uses a blocking Game::Run() must link CNA::EmscriptenAsyncify.

Video links but cannot decode here: the Video/VideoPlayer types are part of every build, no FFmpeg backend exists for Emscripten, and playback throws System::NotSupportedException at run time. Networking discovery does not work on Emscripten either.

Serve the generated .html, .js and .wasm from a local web server; browsers block direct file:// access. Configure with emcmake: emcmake cmake --preset web — the web preset carries no toolchain file, so cmake --preset web alone would configure natively.

macOS

macOS carries the METAL renderer, which drives Apple Metal directly and uses SDL3 only for the window and CAMetalLayer. It is macOS-only, and a workflow is configured to build it on a real macos-14 runner on every push and pull request. It is not the only non-Linux job: apple-ci.yml also builds CnaTests on SDL_RENDERER for macOS, runs the portable suites and verifies and launches a self-contained .app bundle, and the same workflow covers iOS.

Two caveats: METAL throws on custom ShaderEffect shaders, and the Metal job builds and runs the ^Metal tests rather than the full suite. The macOS deployment floor is 13.3 (a lower CNA_MACOS_DEPLOYMENT_TARGET is a configure error, because CNA needs Apple's floating-point std::to_chars). FFmpeg is optional on macOS (CNA_ENABLE_VIDEO=AUTO uses it when found; CI installs it with Homebrew), so video is available there only in builds that found it. SDL3 is the only platform implementation on macOS.

Android

Android is genuinely wired rather than aspirational: the NDK toolchain path is in the build system, the code paths exist, and the NDK sensor implementations are real — Compass and Motion are in fact Android-only and report NotSupported elsewhere. See Sensors.

⚠

Android has no CI at all — zero jobs, zero presets. Every Android build is one somebody ran by hand, and nothing catches an Android regression automatically. The only Android build project in the repository is the Devices demo (Gradle: minSdk 24, target/compile SDK 35, NDK 30.0.14904198, arm64-v8a only). CNA's own Android status note, last updated before alpha.1, records an NDK cross-build failing inside two sibling sharp-runtime files; we did not re-run it against the current sibling, so treat Android builds as unverified. Video is unavailable here too.

iOS and tvOS

iOS support is experimental and deliberately narrow. The snapshot ships an iOS toolchain file (cmake/toolchains/ios.cmake, with CNA_IOS_SIMULATOR for the simulator SDK) and allows only SDL_RENDERER by default. The Apple workflow is configured to final-link a device application and launch a simulator smoke application for one frame. That establishes configuration, link and simulator startup — not physical-device behavior, input/audio coverage or pixel correctness. The deployment floor is iOS 16.3. CNA_APPLE_ALLOW_UNVALIDATED_RENDERER=ON merely permits experiments outside the allow-list; it is not a support claim. tvOS has no validated path.

What CI actually covers

This snapshot contains 20 GitHub Actions workflow files (28 jobs; 17 files run automatically, three are manual or branch-specific). They cover general tests, platform conformance, multi-renderer Linux and Emscripten builds, Apple/Metal, declared C API compatibility/release gates, and focused renderer/subsystem checks. Trigger and evidence still matter more than the raw file count. No workflow configures an invalid renderer identity any more; the general job configures OPENGLES3, runs a full default build and an unfiltered ctest, and tolerates a single named known failure.

⚠

Configured is not the same as passing. Nine jobs in eight workflows check CNA out against a sharp-runtime revision that predates the components this snapshot requires: emscripten-multi-renderer-ci, htmldom-ci and devices-tests pin commit bc8dbf41 (15 August 2026); apple-ci (its macOS and iOS jobs) and metal-macos-ci pin f23ded28 (15 August); content-pipeline-windows-ci pins df1b42ab; and d3d-windows-ci and gdi-windows-ci take sharp-runtime's default branch. None of those revisions contains the Resources and Xml.Serialization components that CNA's default build now links (only sharp-runtime's next does), so by a static reading of the CMake logic those lanes should fail at configure time; we did not run them. Treat the Emscripten, HTML_DOM, Apple, Metal, Devices and Windows workflows as configured to do what is described here, not as currently passing. The lanes that fetch siblings through scripts/ci/clone_siblings.sh — the platform matrix (including native X11 and the CNA_ENABLE_SDL matrix), general tests, input, multi-renderer, glTF and the C API checks — pick sharp-runtime's next branch on a push to next, so they do not have this problem. The Win32 cross-build job does not use sharp-runtime at all.

How to read the matrix

The snapshot has much broader automated coverage than alpha.1, but a workflow is not universal proof:

  • The Windows D3D, GDI and content-pipeline lanes remain manual, so their existence is not an automatic merge gate.
  • The iOS device lane final-links; the simulator lane launches one smoke frame. Neither establishes physical-device or full-game correctness.
  • The Emscripten multi-renderer lane covers configuration and linking, while browser-specific workflows are the runtime evidence for selected web renderers — when they pass; see the caveat above.
  • Android has source and NDK wiring but no automatic workflow. Native Wayland has code and local test suites but no workflow.
  • Every Linux job runs on a virtual X server with Mesa's software drivers. None provides a physical-GPU or real-desktop run.

Not exercised by any workflow: native Wayland, SDL2 outside Linux, Android, tvOS, CNA_BUILD_C_API=ON builds, Clang on Linux (except C header compatibility), CNA_ENABLE_VIDEO=OFF on Linux, the full engine + DirectX under Wine/MinGW (only the platform module), and the GPU pixel/oracle corpus (run locally, by hand). Verification & Known Issues covers the wider testing picture, and Graphics Renderers the per-renderer side of it.

Where video is available

⚠

Video and VideoPlayer exist in every build and link everywhere, but decoding is available on Linux and macOS only, and only where the optional FFmpeg backend was compiled in: CNA_ENABLE_VIDEO is ON, or AUTO found libavcodec, libavformat, libavutil and libswresample. On Windows, Emscripten, Android and iOS FFmpeg is never built (AUTO falls back silently, ON is a configure error). Without a backend the calls throw System::NotSupportedException at run time — a run-time exception, not a link error. Audio and MediaPlayer song playback do not depend on FFmpeg. See Video Playback.
