Platform Support

CNA platform targets - verified status, and what CI actually covers

Platform matrix

PlatformToolchain(s)Backend(s)StatusHow it's verified
Linux gcc-14 in CI EASYGL (default), VULKAN, BGFX, SDL_RENDERER, SDL_GPU, SOFTWARE, HEADLESS, WEBGPU, DX3, ASCII Primary The only platform with automatic CI. The full unit suite and the GPU pixel suites are run here - though by hand, not by CI.
Windows MinGW-w64 (cross from Linux) and native MSVC D3D9, D3D11, D3D12, SDL_RENDERER Real, but hand-driven Verified from Linux through Wine + DXVK / vkd3d-proton on a real GPU, and - for D3D11 and D3D12 - on real Windows through a manual-dispatch MSVC workflow.

Android Android NDK SDL_RENDERER Genuinely wired Handled properly through CMake, and the sensor code links against android. But there is no CMake preset and no CI job.
macOS — — Minimal handling only The build system contains only minimal macOS handling. No CI, no preset. Treat as unsupported.
iOS — — No support There are zero iOS references anywhere in the build system. iOS is not a target in any sense.
⚠

Only Linux is continuously verified, and even there CI covers a slice. Every other row above depends on a build someone ran by hand. If you are choosing a target platform, weight that accordingly.

What CI actually covers

There are three workflows in .github/workflows/, and it is worth being precise about what each one does, because only one of them runs on its own.

WorkflowTriggerRunnerWhat it runs
input-ci.yml Automatic — the only auto-triggered workflow ubuntu-24.04, gcc-14 A 5-way backend matrix (EasyGL, EasyGL + ASan/UBSan, SDL_Renderer, Vulkan, Bgfx), running only the input-labelled tests.
devices-tests.yml Path-filtered to Microsoft/Devices/** ubuntu-latest The Devices/Sensors tests only.
d3d-windows-ci.yml Manual dispatch only windows-latest, native MSVC D3D11 and D3D12, plus verification of 20 HLSL shaders against a real D3DCOMPILER_47.dll.

Stated plainly:

  • There is no macOS, Android, or Emscripten CI at all.
  • The full unit suite (4,845 GoogleTest cases) and the GPU pixel suites are run locally, by hand. CI does not gate them.
  • The full CnaTests suite cannot be built on any Windows toolchain - roughly 10 test files use the POSIX ::setenv(). Windows verification is therefore backend-level, not whole-suite.
  • Because backend choice is a compile-time decision, covering all 14 backends means 14 separate configure + build + test runs. No CI job does that.

Linux

Linux is CNA's primary platform and the only one with automatic CI. EASYGL is the default backend here, and it is also the project's most mature and best-verified backend by a wide margin (239 registered CTest entries).

SDL3, SDL3_image and SDL3_mixer are built from vendored submodules, so no system SDL packages are required. The sharp-runtime sibling repository is required for every build; easy-gl is additionally required for EASYGL and free-direct for DX3. See Building for the exact commands.

Linux is also the only platform where FFmpeg-backed video decoding is available - see the note at the end of this page.

Windows

Windows is a real target, reached two ways:

  • MinGW-w64 cross-compilation from Linux. This is the day-to-day path. The resulting binaries are then run through Wine + DXVK (D3D9, D3D11) or Wine + vkd3d-proton (D3D12) on a real GPU.
  • Native MSVC. D3D11 and D3D12 have been verified on real Windows through the d3d-windows-ci.yml workflow, which also checks 20 HLSL shaders against a real D3DCOMPILER_47.dll. That workflow is manual dispatch only - it does not run on push.

Windows is the only platform where the three Direct3D backends are available at all: D3D9, D3D11 and D3D12 are hard-gated to a Windows configure and fail fast elsewhere. Of those, D3D9 is the most complete and is the backend used for pixel-exact XNA 4.0 authenticity checks; D3D12 is rated partial and has exactly one automated test. SDL_RENDERER is the default backend on Windows.

Remember that the full CnaTests unit suite does not build on Windows toolchains, so what gets verified on Windows is the backend layer rather than the whole library.

Web / Emscripten

The web target is real infrastructure, not a plan. There is a dedicated web CMake preset, a prebuilt Emscripten SDL tree, and -sASYNCIFY / -sEXIT_RUNTIME wiring so the test binaries can run under Emscripten's event loop.

Two backends are usable here. EASYGL compiles to the browser and is the well-tested option. CANVAS is an Emscripten-only backend that drives the HTML5 2D canvas directly through 11 EM_JS functions - but it has zero automated pixel tests, so nothing mechanically proves it renders correctly.

There is no Emscripten CI job. FFmpeg is unavailable on this target, so VideoPlayer does not work in the browser.

Android

Android is genuinely wired up rather than merely aspirational: CMake handles the Android NDK toolchain properly, and the sensor implementation links against android and uses real NDK APIs. The Compass and Motion sensors are in fact Android-only, built on an NDK fusion of five sensors, and they honestly report NotSupported on other platforms.

What is missing is verification infrastructure: there is no CMake preset and no CI job for Android, so every Android build is one someone ran by hand. FFmpeg is unavailable here too, so video playback is out.

macOS

The build system contains minimal macOS handling only - no CI, no preset, no verification. Treat macOS as unsupported today. Note also that the BGFX backend would not help here: its shader blobs cover OpenGL, OpenGL ES, Vulkan and WebGPU only, with no Metal variants, so 3D silently draws nothing on bgfx's default macOS renderer.

iOS

There is no iOS support of any kind. There are zero iOS references in the build system. Any claim that CNA runs on iOS is wrong.

Backends that are not tied to a platform

Two backends never touch a GPU or a display server, so they build and run anywhere: HEADLESS, which renders nothing at all and exists so game logic can be exercised quickly in CI, and SOFTWARE, a genuine CPU rasterizer with a real Z-buffer and perspective-correct interpolation (TriangleList only). Neither is intended for shipping a real-time game - see Rendering Backends for their design purpose and limits.

Video playback is desktop-Linux only

⚠

VideoPlayer decodes video through FFmpeg (real libavcodec / libavformat / libswresample, with PTS-driven pacing). FFmpeg is found via pkg-config and is unavailable on Emscripten, Android and every Windows target. Video playback is therefore effectively native-Linux-only today. Audio and MediaPlayer song playback, which go through SDL3_mixer, are not affected.

CNA

A modern C++ reimplementation of the XNA 4.0 API. Near-complete XNA 4.0 type coverage, verified by 4,845 unit tests and 648 backend pixel/integration tests across 14 selectable rendering backends.
