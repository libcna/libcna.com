Tutorial 102: The OpenGL Family

CNA Tutorials  ·  Renderers

ℹ

What you’ll learn

  • How OPENGLES2, OPENGLES3, OPENGL33, WEBGL1 and WEBGL2 relate to one shared implementation.
  • Exactly which features OPENGLES2 and WEBGL1 lose, and which answers are decided at runtime by your driver.
  • Why your own ShaderEffect GLSL is not translated between profiles, even though CNA's own shaders are.
  • The sibling checkouts a GL build needs, and why EASYGL is not a renderer name.
  • Where the separate, desktop-only OPENGL4 renderer fits, and how to opt into compiled XNA effects on this family.

Before you start — Tutorial 20: Building and Running Your Game, because the profile is a CMake configure-time choice.

Five of CNA's 25 renderer identities are OpenGL profiles that share a single internal implementation called EasyGL, which lives in the ../easy-gl sibling library. In an ordinary single-renderer build, selecting any of the five compiles the same source tree and sets two compile definitions: CNA_RENDERER_EASYGL, the implementation identity, and CNA_GL_PROFILE_<NAME>, which names the default profile. The profile itself is a runtime value inside the renderer, which is why several of the five can be linked into one multi-renderer build (never across the native/Emscripten divide).

⚠

EASYGL is not a renderer name. “EasyGL” names the internal implementation and the sibling library. It is not one of the 25 accepted CNA_GRAPHICS_RENDERER values, and it has no alias — a configure that passes it stops with an unknown graphics renderer error that lists the supported names. CMake compares the public names case-sensitively, so opengles3 is rejected the same way. Pick one of the five profiles instead.

The five profiles

ValueGL flavourWhere it builds
OPENGLES3OpenGL ES 3.0, GLSL ES 3.00Not Emscripten. The Linux default, and the renderer CNA's general-test and platform CI lanes select. Warns at configure time on non-Linux hosts.
OPENGL33Desktop OpenGL 3.3 core, GLSL 3.30 coreNot Emscripten.
OPENGLES2OpenGL ES 2.0, GLSL ES 1.00Not Emscripten. Warns at configure time on non-Linux hosts, like OPENGLES3.
WEBGL2WebGL 2 (GLES 3.0), GLSL ES 3.00Emscripten only. The Emscripten default.
WEBGL1WebGL 1 (GLES 2.0), GLSL ES 1.00Emscripten only.

The gates are hard. Configuring OPENGLES2, OPENGLES3 or OPENGL33 under Emscripten is a FATAL_ERROR telling you to use WEBGL1/WEBGL2; configuring either WebGL profile natively is a FATAL_ERROR pointing the other way.

The sibling checkouts

All five need ../easy-gl checked out next to your cna/ directory, and easy-gl itself expects its own ../meta-gl sibling. These are separate repositories, not git submodules — git submodule update --init will not fetch them, and a missing ../easy-gl/CMakeLists.txt is a FATAL_ERROR that says so explicitly. Both siblings use their default develop branch; CNA itself and sharp-runtime must be on their next branches for this snapshot.

The five identities do not require SDL at source level: they take their GL context from whichever CNA_PLATFORM you build with — SDL3 (the default), SDL2, or the native X11, Wayland or Win32 platforms — but not from the Terminal or Headless platforms, which have no GL context service.

Because the Linux default renderer is OPENGLES3, this means an ordinary Linux build of CNA needs three siblings present before it will configure at all: ../sharp-runtime, ../easy-gl and ../meta-gl.

cd /path/to/workspace
git clone -b next https://github.com/libcna/cna.git
git clone -b next https://github.com/libcna/sharp-runtime.git
git clone https://github.com/libcna/easy-gl.git      # default branch: develop
git clone https://github.com/libcna/meta-gl.git      # default branch: develop

cd cna
cmake -S . -B build -DCNA_GRAPHICS_RENDERER=OPENGLES3
cmake --build build --parallel

The profiles are not cosmetic

⚠

OPENGLES2 and WEBGL1 genuinely lose multiple render targets, occlusion queries, Texture3D, instancing and multi-stream vertex input. This is not a relabelled context — the underlying API has no draw-buffers MRT, no query objects, no 3D textures and no attribute-divisor entry points at all.

Here is what the renderer actually reports, profile by profile. “Driver” means the answer is computed at runtime from the live GL context, not baked in at compile time. OPENGLES3, OPENGL33 and WEBGL2 form the ES 3 generation; OPENGLES2 and WEBGL1 the ES 2 generation.

CapabilityOPENGLES3 / OPENGL33 / WEBGL2OPENGLES2 / WEBGL1
MultipleRenderTargetsYesNo
OcclusionQueryYesNo
Texture3DYesNo
InstancingYesNo
MultiStreamVertexInputYesNo
MultiSampleAntiAliasingDriver — from GL_MAX_SAMPLESNo — reported unconditionally, whatever context version the driver grants
AnisotropicFilteringDriver — the GL_EXT_texture_filter_anisotropic extension, on every profile
WireFrameYes on OPENGL33 (native glPolygonMode); otherwise Driver — GL_NV_polygon_mode on native ES, WEBGL_polygon_mode on WebGL
FloatRenderTargets, HalfFloatRenderTargetsDriver — the renderer checks that the float format can really be created as a targetNo
ComputeShaders, IndirectDrawDriver — the runtime context decides: compute needs ES 3.1 or desktop GL 4.3, indirect draw ES 3.1 or GL 4.0, and WebGL has neither in any version. These profiles ask for an ES 3.0 / GL 3.3 context, so expect false unless the driver grants a newer one
CompiledEffectsBuild option — false unless configured with -DCNA_EASYGL_COMPILED_EFFECTS=ON (see below)

Three of these deserve a note. MSAA is a live query on the ES 3 generation — the renderer reads GL_MAX_SAMPLES and reports whether it exceeds 1, so the same binary can answer differently on two machines. On the ES 2 generation the answer is an unconditional false, because GLES 2.0 has no multisample renderbuffers or blit and GL_MAX_SAMPLES is undefined there; the renderer reports the profile's forced single-sample surfaces rather than what a generously newer runtime context could do.

Wireframe needs a real polygon-mode API. Earlier versions of this page said EasyGL re-expands triangles into line primitives. In this snapshot it does not: a true answer means the context exposes a genuine polygon mode, which preserves culling, clipping, depth bias, MSAA and stencil across every triangle route, and GL_LINES expansion cannot promise that. Where the context has none — most native ES contexts without GL_NV_polygon_mode, and WebGL without WEBGL_polygon_mode — a wireframe triangle draw is refused with a System::NotSupportedException rather than approximated. Query the capability and select FillMode::Solid when it is false.

Compute and indirect draw follow the context you actually got. The renderer asks for an ES 3.0 context and Mesa routinely hands back 3.2, so the same OPENGLES3 binary can report compute on one machine and not on another. The detailed capability profile reports the same facts as separate features and limits.

This is exactly the asymmetry Tutorial 101 describes, from the other direction: the GL family is one of the renderers whose answers are worth reading, because they are authored and in several cases measured.

Shader source is not portable across the profiles

CNA authors every one of its own built-in GL shaders once, in GLSL ES 3.00, and adapts it at first use:

  • On OPENGL33, the #version 300 es line becomes #version 330 core and the following precision line is dropped, because desktop core GLSL does not accept it. The shader body is otherwise identical.
  • On OPENGLES2 and WEBGL1, the whole body is transformed to GLSL ES 1.00: #version 100, in/out become attribute/varying, texture() becomes texture2D() or textureCube() depending on the sampler's declared type, FragColor becomes gl_FragColor, and layout(location = N) qualifiers are stripped and re-applied as explicit attribute-location bindings before linking.
⚠

Your shaders do not get this treatment. GLSL you hand to a ShaderEffect is passed straight to the GL compiler, verbatim. A shader that compiles under OPENGLES3 will not compile under WEBGL1, and a shader written for OPENGL33 will not compile under OPENGLES3. If you ship more than one GL profile, you ship more than one shader variant — or you write your own header rewriter.

Integer vertex attributes are the hard case. uvec4 and ivecN have no GLSL ES 1.00 equivalent at all, so a shader that uses them simply cannot run under OPENGLES2 or WEBGL1. CNA's own skinning shaders sidestep this by encoding bone indices as floats. See Tutorial 52 for the ShaderEffect API itself.

Profile differences reach further than syntax, too. Desktop core profiles require GL_VERTEX_PROGRAM_POINT_SIZE to be enabled before a vertex shader's gl_PointSize output has any effect, while GLES and WebGL honour it automatically. CNA enables it for you on OPENGL33; the lesson is that “it works on ES 3, so it works on GL 3.3” is not a safe assumption.

Choosing a profile

SituationProfile
Desktop Linux, no special requirementOPENGLES3 — the default, and the profile CNA develops against
Desktop, and you need desktop-GL debugging tools or a core-profile contextOPENGL33
Desktop, and you want the modern GL 4.x feature set (compute, indirect draw, GPU timers, shadow and image-based-lighting sampling) without the easy-gl siblingsOPENGL4 — a separate renderer, see Tutorial 130
BrowserWEBGL2 — the Emscripten default, and feature-equivalent to OPENGLES3
Browser, and the target genuinely cannot get a WebGL 2 contextWEBGL1, having removed every use of MRT, occlusion queries, Texture3D and instancing first
Old mobile or embedded GPUOPENGLES2, with the same feature audit as WEBGL1

The practical way to plan a downgrade to OPENGLES2/WEBGL1 is to build the ES 3 profile first, get the game working, then grep your code for the five lost features rather than discovering them one exception at a time. Tutorial 62, Tutorial 61 and Tutorial 60 cover three of them.

Limits the whole family shares

Surface formats are classified per profile. Color, Alpha8 and Dxt1/Dxt3/Dxt5 work on every profile — DXT blocks are decoded on the CPU when the driver has no S3TC support. On the ES 3 generation the packed 16-bit formats, NormalizedByte2/NormalizedByte4, Rgba1010102 and the float and half-float formats are also supported; the ES 2 generation refuses them, and Rg32/Rgba64 depend on a 16-bit normalized-texture extension in the live context. The seven CNA-extension formats are left to the framework's own rule. Ask GraphicsDevice::SupportsSurfaceFormatAsRenderTargetEXT() or the profile's per-format usage before creating a target in an unusual format.

Cube faces in a multiple-render-target set are implemented on the ES 3 generation. Binding a RenderTargetCube face as one slot of an MRT set works, and the same cube may occupy several slots as different faces. It needs MRT, so it does not exist on OPENGLES2 or WEBGL1.

Compiled XNA effects (opt-in)

By default the GL family reports CompiledEffects as false. Configure with -DCNA_EASYGL_COMPILED_EFFECTS=ON to build support for XNA/FNA Direct3D 9 Effect Framework bytecode; it is off by default because it pulls in a fetched dependency (MojoShader, taken from the pinned FNA3D checkout) that the renderer does not otherwise need. It goes through MojoShader’s own GLSL adapters, in parallel to EasyGL’s own stock shaders, and applies to all five identities. A compiled effect whose vertex shader samples a texture, or that binds a 3D or cube sampler, is refused explicitly rather than mishandled. This is separate from CustomEffects, which covers the hand-written GLSL ShaderEffect path above.

Not in this family: OPENGL4

OPENGL4 is a sixth GL-based identity, but it is not EasyGL and does not need ../easy-gl or ../meta-gl. It is a real desktop OpenGL 4.1+ core renderer with its own loader, built against the system OpenGL (find_package(OpenGL)); a lower version or a compatibility profile is refused by name. Compute shaders need a 4.3+ context. It targets desktop OpenGL only (use WEBGL1/WEBGL2 in a browser), and it cannot be linked into the same binary as PORTABLEGL, which defines the same global gl* symbols. Tutorial 130: The OPENGL4 Desktop Renderer builds and runs it.

Build commands

# Desktop, OpenGL ES 3.0 (the Linux default -- this is what you get with no flag)
cmake -S . -B build -DCNA_GRAPHICS_RENDERER=OPENGLES3

# Desktop OpenGL 3.3 core
cmake -S . -B build-gl33 -DCNA_GRAPHICS_RENDERER=OPENGL33

# WebGL 2 (the Emscripten default)
emcmake cmake -S . -B build-web -DCNA_GRAPHICS_RENDERER=WEBGL2

# WebGL 1 -- fewer features, see the table above
emcmake cmake -S . -B build-web1 -DCNA_GRAPHICS_RENDERER=WEBGL1

cmake --build build --parallel

The equivalent per-renderer option form (-DCNA_RENDERER_OPENGLES3=ON) also works; exactly one such option must be ON, and mixing the two forms in one configure is a mistake.
