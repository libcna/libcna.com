Tutorial 72: Choosing the Right Rendering Backend

CNA Tutorials  ·  Architecture

CNA supports 14 selectable graphics backends via the CNA_GRAPHICS_BACKEND CMake option: SDL_RENDERER, EASYGL, BGFX, VULKAN, WEBGPU, HEADLESS, SOFTWARE, D3D11, D3D12, CANVAS, ASCII, DX3, D3D9 and SDL_GPU. Maturity varies enormously: EASYGL is the only one that is genuinely production-ready, with SDL_RENDERER production-ready within its 2D-only scope; VULKAN, D3D9, D3D11, SDL_GPU, SOFTWARE, DX3 and ASCII are functional; BGFX, D3D12 and WEBGPU are still partial; HEADLESS renders nothing by design (it exists for fast CI of game logic); and CANVAS has no automated pixel tests at all. The backend is selected at compile time and compiled into the binary — runtime switching is not supported, so there is no dispatch overhead. See the Rendering Backends guide for the full per-backend picture.

SDL_RENDERER — 2D only, best compatibility

The SDL_RENDERER backend maps CNA's API onto SDL3's built-in 2D accelerated renderer. It requires no OpenGL or Vulkan driver. SDL3's renderer targets can be hardware-accelerated via the OS compositor (Metal on macOS, D3D11 on Windows, OpenGL on Linux) without the application needing to use those APIs directly.

Limitations: no VertexBuffer, no IndexBuffer, no custom Effect shaders, no BasicEffect 3D rendering, no RenderTarget2D with depth/stencil, no MRT. Any call that requires 3D will throw a NotSupportedException.

Use this backend when: your game is purely 2D, you need to run in a CI environment without a GPU driver, or you are targeting a platform with no OpenGL/Vulkan support.

EASYGL — most mature backend, OpenGL ES 3.0

The EASYGL backend uses the easy-gl library (a sibling repo) to provide an OpenGL ES 3.0 / OpenGL 3.3 core profile implementation. It is CNA's primary, most mature backend, and covers the vast majority of the XNA 4.0 API surface including:

  • Full 3D rendering with VertexBuffer, IndexBuffer, BasicEffect, custom Effect
  • RenderTarget2D with depth/stencil, plus MRT
  • All BlendState, DepthStencilState, RasterizerState presets
  • GLSL shader support via the Effect system — 13 GLSL programs covering all 9 effect families
  • Per-vertex and per-pixel lighting, instancing, occlusion queries, anisotropy, fog, and GL context-loss recovery

Only 4 of IGraphicsBackend's virtuals are left unoverridden here — fewer than on any other backend. Note one framework-wide limit that EasyGL does not escape: only SurfaceFormat::Color textures can be constructed anywhere in CNA, so half-float, float and HDR formats are unavailable despite appearing in the SurfaceFormat enum.

EASYGL is the recommended backend for development and for shipping on Linux, Windows, and Android. RenderDoc attaches cleanly for GPU debugging.

VULKAN — second-most mature, best performance

The VULKAN backend targets Vulkan 1.2 and is CNA's second-most mature backend, with all five stock effects implemented and pixel-tested. It offers lower CPU overhead and better multi-threading opportunities (though CNA does not currently use Vulkan secondary command buffers from worker threads).

The setup cost is higher: you need vulkan-headers and libvulkan-dev, and Vulkan validation layers are recommended during development (see Tutorial 73). Shader code compiles to SPIR-V at build time via glslangValidator or shaderc.

Use VULKAN when: you are targeting modern desktop GPUs, you need the best frame time performance, or you want to future-proof your pipeline — outside of workloads that need custom BlendState modes or working OcclusionQuery.

BGFX — partial, and narrower than it looks

The BGFX backend wraps the bgfx library, which can in principle target OpenGL, Metal, Direct3D and Vulkan. CNA's wrapper does not reach all of those. It ships 108 shader blobs, but only for GL, GLES, Vulkan and WebGPU — there are no D3D or Metal variants. The practical consequence is severe: on bgfx's default renderer on Windows (Direct3D) and macOS (Metal), 3D silently draws nothing. There is no error, just an empty frame.

Two further verified defects: bgfx never overrides CreateIndexBuffer32, so 32-bit indices are uploaded into a 16-bit buffer and DrawUserIndexedPrimitives corrupts geometry (every other 3D backend implements this correctly); and draw offsets (startIndex/baseVertex) are ignored outside the wireframe path.

Use BGFX when: you are working on the backend itself, or you have verified your target platform resolves to a GL, GLES or Vulkan renderer. Do not reach for it as the macOS answer — it is not one today.

D3D9 — pixel-exact XNA authenticity, Windows-only

The D3D9 backend is the newest of the Direct3D trio and, for CNA's purposes, the most interesting: it uniquely targets pixel-exact XNA 4.0 authenticity. It is the backend CNA's XNA oracle corpus diffs against — 39 scenes rendered by a real C#/XNA reference renderer and compared at --tolerance 0. 43 of its 45 overrides are real, with 72 verified SM2/SM3 shader blobs, full device-lost and D3DPOOL_DEFAULT recovery, and caps-validated MRT.

Use D3D9 when: you care about matching original XNA output exactly, or you are targeting older Windows hardware.

D3D11 — native Direct3D 11, Windows-only

The D3D11 backend is a native (non-bgfx) Direct3D 11 implementation, hard-gated to Windows at configure time. It implements 5 state-object caches, MRT with a deferred resolve, instancing, and a runtime D3DCompile path. It builds through the MinGW-w64 cross-toolchain from Linux and under native MSVC, and is verified both through Wine+DXVK on a real GPU and on real Windows via a manual-dispatch MSVC CI workflow that additionally checks 20 HLSL shaders against a real D3DCOMPILER_47.dll.

One verified defect to know about: draw offsets (startIndex/baseVertex) are ignored on D3D11, so drawing a sub-range of a shared buffer renders the wrong geometry.

D3D12 — native Direct3D 12, Windows-only, partial

The D3D12 backend has a strong core — PSO and root-signature caches and a per-resource barrier tracker — but it is genuinely partial at the fixed-function layer. It implements no scissor, no viewport, no stencil and no blend factor, and its MRT path clears attachments but never draws to them. It is also by far the least-tested backend in CI terms.

It shares D3D11's HLSL/DXBC bytecode and is likewise verified through Wine+vkd3d-proton from Linux and on real Windows through the manual MSVC workflow.

Use D3D12 when: you want to experiment with CNA's D3D12 command-list and PSO architecture, not when you need a complete Direct3D 12 render path.

WEBGPU — experimental, native wgpu-native

The WEBGPU backend uses native wgpu-native (pinned at v29.0.1.1) with WGSL shaders. It is a backbuffer-only forward renderer, and the list of what it does not have is the important part: no render targets at all, no MSAA, no cube or 3D textures, no queries, no instancing, and a non-functional stencil. It also claims 5 capabilities through SupportsCapability() that it does not actually have, so do not trust that query here.

Use WEBGPU when: you want to track native WebGPU as it matures. It is not a substitute for EasyGL or Vulkan for 3D work, and every render-target technique — post-processing, shadow maps, deferred shading — is unavailable on it.

SDL_GPU, DX3, ASCII and CANVAS — the newer backends

SDL_GPU is functional: a deferred/retained design over SDL's own GPU abstraction, with 23 SPIR-V blobs, 9 effect families, stencil support and MSAA resolve. Its device is Vulkan-only today.

DX3 is DirectDraw-shaped and fronts the free-direct sibling repo. Despite the name it is genuinely cross-platform, and within 2D it has the best fidelity of any CNA backend — a real CPU compositor, bilinear filtering, 4 distinct blend formulas, and real Wrap/Mirror texture addressing, which is a concrete win over SDL_Renderer.

ASCII is a thin decorator over SDL_Renderer that quantises each frame to a glyph and colour grid, switchable via CNA_ASCII_MODE=BLACKWHITE|COLOR. It is still an SDL window, not a terminal backend. Note that it reports the inverse of the backend it wraps through SupportsCapability().

CANVAS is Emscripten-only, built on 11 EM_JS functions with careful un-premultiply and clip handling. It is mature within its narrow scope but carries a real caveat: no automated test ever renders a Canvas pixel, so nothing about it is machine-verified.

All four of these were created within roughly the last two weeks of the audit. Maturity across CNA's backends tracks age closely — EasyGL, Vulkan, bgfx and SDL_Renderer date from April 2026, and the other ten are much newer.

HEADLESS and SOFTWARE — CI/testing-only backends

HEADLESS and SOFTWARE exist purely to make game logic and rendering behavior testable without a GPU or display server — neither is meant for shipping a real game.

HEADLESS never touches SDL video, OpenGL, Vulkan, or any GPU library, and renders nothing by design — ReadBackbuffer() just reports the last Clear() color. Instead it does real bookkeeping: argument validation, resource-lifecycle tracking, and draw-call/state-change counters, with a runtime strictness dial (CNA_HEADLESS_MODE=Fast|Validation|Trace) for fast CI runs of game logic.

SOFTWARE also needs no GPU, window, or display server, but it genuinely rasterizes triangles into a CPU-owned RGBA8 framebuffer (a real edge-function rasterizer, perspective-correct interpolation, real depth testing) — GetBackBufferData() returns real, correct pixels, verified against EasyGL on a canonical scene (max per-channel pixel diff of 1). It is deliberately not real-time (no SIMD, multithreading, or tiling) and has real limits: TriangleList only, no per-light lighting/fog, only two distinguished blend modes, and no MRT/MSAA/mipmapping/Texture3D/RenderTargetCube. Present() is a no-op — there's no way to view a Software-rendered frame on screen.

Use HEADLESS when: you need CI to exercise game logic fast without any GPU. Use SOFTWARE when: you need deterministic, GPU-free pixel tests or a cross-backend rendering diagnostic.

How to set the backend in CMake

Pass -DCNA_GRAPHICS_BACKEND=<NAME> to the CMake configure step. The value is case-sensitive.

// CMakeLists.txt excerpt — backend selection

set(CNA_GRAPHICS_BACKEND "EASYGL" CACHE STRING
    "CNA rendering backend: SDL_RENDERER | EASYGL | VULKAN | BGFX | WEBGPU | HEADLESS |
     SOFTWARE | D3D11 | D3D12 | CANVAS | ASCII | DX3 | D3D9 | SDL_GPU")
set_property(CACHE CNA_GRAPHICS_BACKEND PROPERTY STRINGS
    SDL_RENDERER EASYGL VULKAN BGFX WEBGPU HEADLESS SOFTWARE D3D11 D3D12
    CANVAS ASCII DX3 D3D9 SDL_GPU)

# Validate the choice
if(NOT CNA_GRAPHICS_BACKEND MATCHES "^(SDL_RENDERER|EASYGL|VULKAN|BGFX|WEBGPU|HEADLESS|SOFTWARE|D3D11|D3D12)$")
    message(FATAL_ERROR
        "Invalid CNA_GRAPHICS_BACKEND: '${CNA_GRAPHICS_BACKEND}'. "
        "Valid values: SDL_RENDERER, EASYGL, VULKAN, BGFX, WEBGPU, HEADLESS, SOFTWARE, D3D11, D3D12")
endif()

# D3D11/D3D12 additionally require the MinGW-w64 Windows cross-toolchain:
# cmake -S . -B build-d3d11 -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/mingw-w64.cmake -DCNA_GRAPHICS_BACKEND=D3D11

# Each backend adds its own CMake subdirectory
add_subdirectory(src/backends/${CNA_GRAPHICS_BACKEND})

# Expose the selection as a preprocessor define
target_compile_definitions(CNA PUBLIC
    CNA_BACKEND_${CNA_GRAPHICS_BACKEND}=1)

To configure and build with the Vulkan backend:

cmake -S . -B build-vulkan -DCNA_GRAPHICS_BACKEND=VULKAN
cmake --build build-vulkan --target CNA CnaTests

Preprocessor defines in game code

You can use the preprocessor defines to include backend-specific code paths in your game:

#if defined(CNA_BACKEND_VULKAN)
    // Vulkan-specific: enable Vulkan validation layers at startup
    SDL_SetHint(SDL_HINT_VULKAN_DISPLAY, "1");
#elif defined(CNA_BACKEND_EASYGL)
    // EasyGL-specific: request a debug context for RenderDoc
    SDL_GL_SetAttribute(SDL_GL_CONTEXT_FLAGS,
                        SDL_GL_CONTEXT_DEBUG_FLAG);
#elif defined(CNA_BACKEND_D3D11) || defined(CNA_BACKEND_D3D12)
    // D3D11/D3D12-specific: Windows-only native Direct3D code path
#endif

Runtime switching (not supported)

CNA does not support switching the rendering backend at runtime. The backend is compiled into the binary and initialised once during Game::Run(). If you need to support multiple backends from a single executable, build the project twice with different CNA_GRAPHICS_BACKEND settings and ship both binaries (e.g. auto-select based on SDL_GetPlatform() in a launcher shell script).

Alternatively, the BGFX backend selects its underlying API at runtime from the set of backends bgfx was compiled with, which gives some degree of runtime flexibility on platforms where BGFX supports multiple APIs.
