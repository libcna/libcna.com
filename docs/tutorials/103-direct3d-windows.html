Tutorial 103: Direct3D 11 and 12 on Windows

CNA Tutorials  ·  Renderers

ℹ

What you’ll learn

  • Cross-compiling DIRECTX11 and DIRECTX12 from Linux with MinGW-w64.
  • Running and testing the resulting .exe under Wine with DXVK and vkd3d-proton, including the guards that stop a silent fallback.
  • Exactly what Wine verification proves — and the five things it does not.
  • The Direct3D 12 presentation split, and why the routine test suite renders off-screen.

Before you start — Tutorial 72: Choosing a Renderer covers renderer selection and the platform gates this tutorial works within.

CNA has two native modern Direct3D renderers, DIRECTX11 and DIRECTX12; they sit beside DIRECTX9 (the XNA-fidelity renderer), DIRECT2D and GDI in the five-renderer Windows set. All five are hard-gated to Windows, and the repository supplies a manual Linux cross-build/Wine validation route for the Direct3D ones. In this snapshot that route is not run automatically, and the native-Windows MSVC workflows are manual-dispatch only, which is why this tutorial distinguishes what a manual result proves from continuous or native-hardware coverage.

The Windows gate is hard

Five renderers refuse to configure unless CMAKE_SYSTEM_NAME is Windows: DIRECTX9, DIRECTX11, DIRECTX12, DIRECT2D and GDI. Attempting one on a native Linux or macOS configure is a FATAL_ERROR, not a warning, and the message points you straight at the cross-compilation toolchain. (FREEDIRECT, the DirectDraw-shaped 2D renderer, is deliberately not Windows-gated and builds natively on Linux.)

CNA: DIRECTX11 renderer only builds when targeting Windows. Either build
natively on Windows, or cross-compile from Linux with
-DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/mingw-w64.cmake

The reason is simply that d3d9.h, d3d11.h, d3d12.h and dxgi.h do not exist anywhere else. No CMake dependency is fetched for these renderers — the headers and import libraries (d3d9, d3d11, d3d12, dxgi, d3dcompiler, d2d1, gdi32) come from the Windows SDK under MSVC, or from MinGW-w64's own copies when cross-compiling. On the platform side, a Windows target can use the default SDL3 platform or the native WIN32 platform (-DCNA_PLATFORM=WIN32, no SDL); iOS accepts none of these renderers.

Cross-compiling from Linux

sudo apt install mingw-w64

# Direct3D 11
cmake -S . -B build-dx11 \
      -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/mingw-w64.cmake \
      -DCNA_GRAPHICS_RENDERER=DIRECTX11 \
      -DCNA_BUILD_TESTS=ON
cmake --build build-dx11 --parallel

# Direct3D 12
cmake -S . -B build-dx12 \
      -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/mingw-w64.cmake \
      -DCNA_GRAPHICS_RENDERER=DIRECTX12 \
      -DCNA_BUILD_TESTS=ON
cmake --build build-dx12 --parallel
⚠

The renderer names changed. D3D9, D3D11 and D3D12 are not accepted CNA_GRAPHICS_RENDERER values any more — use DIRECTX9, DIRECTX11 and DIRECTX12. The CTest labels moved with them, so ctest -L D3D11 matches nothing; the label is DIRECTX11.

Example and test executables land at the root of the build directory (the smoke tests are cna_test_directx11_smoke and cna_test_directx12_smoke). Both renderers need cmake --build against a real target. CNA itself is an interface umbrella library with no sources and is not buildable; build CnaTests, a demo target, or the whole build directory.

Two different translation layers

A cross-compiled .exe runs on the development machine under Wine, with its Direct3D calls translated to Vulkan on the real GPU. The two renderers need different translators, and their Wine prefixes do not interchange:

RendererTranslatorWrapper script
DIRECTX11DXVK (Direct3D 9 and 11 to Vulkan)scripts/run-wine-dxvk.sh
DIRECTX12vkd3d-proton (Direct3D 12 to Vulkan)scripts/run-wine-vkd3d.sh
DIRECTX9DXVK (Direct3D 9 to Vulkan)scripts/run-wine-dxvk9.sh
DIRECT2DWine or Proton (Direct2D over Direct3D 11)scripts/run-wine-direct2d.sh, scripts/run-proton-direct2d.sh

The rest of this tutorial walks through DIRECTX11 and DIRECTX12; DIRECTX9 follows the same cross-compile recipe and is covered under the XNA-fidelity section below.

# DXVK, for DIRECTX11
sudo apt-get install -y dxvk-wine64
WINEPREFIX=~/.wine-cna-d3d11 wineboot --init
WINEPREFIX=~/.wine-cna-d3d11 dxvk-setup install

scripts/run-wine-dxvk.sh build-dx11/cna_test_directx11_smoke.exe

# vkd3d-proton, for DIRECTX12 -- a separate, dedicated prefix
WINEPREFIX=~/.wine-cna-d3d12 wineboot --init
# copy vkd3d-proton's d3d12.dll / d3d12core.dll into the prefix, then:
WINEPREFIX=~/.wine-cna-d3d12 wine reg add \
  'HKEY_CURRENT_USER\Software\Wine\DllOverrides' /v d3d12 /d native /f
WINEPREFIX=~/.wine-cna-d3d12 wine reg add \
  'HKEY_CURRENT_USER\Software\Wine\DllOverrides' /v d3d12core /d native /f

scripts/run-wine-vkd3d.sh build-dx12/cna_test_directx12_smoke.exe

The guard that stops a silent fallback

This is the detail worth copying into your own workflow. If the DLL override is not in place, Wine quietly falls back to its own built-in WineD3D implementation. Your test still runs, still produces plausible pixels, and proves nothing about the path you meant to exercise.

Both wrapper scripts therefore assert on the run's own log output before reporting success: run-wine-dxvk.sh requires a DXVK: <version> marker, and run-wine-vkd3d.sh requires a vkd3d-proton - applicationVersion: <version> line. If the marker is missing, the script exits 3 rather than passing.

Environment variableEffect
CNA_D3D11_WINEPREFIX / CNA_D3D12_WINEPREFIXOverride the Wine prefix the wrapper uses.
CNA_D3D11_SKIP_DXVK_GATE=1Opt a binary out of the DXVK marker check — correct only for a test that legitimately never opens a D3D11 device, such as a pure mapping-table unit test.
CNA_D3D12_SKIP_VKD3D_GATE=1The same opt-out for vkd3d-proton.

CTest wires the wrappers in automatically, so ctest --test-dir build-dx11 -L DIRECTX11 runs every registered test through the guarded path rather than bare wine.

What Wine verification proves, and what it does not

Running under DXVK on a real GPU is a genuinely strong test: it exercises real call sequencing, real resource lifetimes, real HLSL compilation and real pixel maths, and the results come back from actual GPU readback rather than from an API returning S_OK. It is far more than a compile check.

⚠

It is not real-Windows verification, and CNA does not claim otherwise. The following are all explicitly open in CNA's own tracking, for both renderers:

  • Real DXGI presentation and tearing behaviour.
  • Real device-lost / device-removed recovery — the detection logic exists and is wired in, but a genuine removal cannot be triggered on the development loop, so the trigger path is unverified.
  • WARP fallback.
  • MSVC-versus-MinGW ABI parity.
  • Multi-vendor driver behaviour — every result comes from one AMD GPU through one translator.

There are two native-Windows MSVC CI workflows in this snapshot: d3d-windows-ci.yml (windows-latest) covers DIRECTX11, DIRECTX12 and DIRECT2D, and gdi-windows-ci.yml covers GDI. Both are manual-dispatch only (workflow_dispatch) — they do not run on pushes or pull requests, and no workflow names DIRECTX9. The Direct3D job builds with MSVC and runs the renderers' off-screen smoke and common suites against the real Windows runtime DLLs, plus a recompile of every checked-in HLSL shader; it is a native-runtime regression gate, not a physical-display or multi-vendor driver claim. If you are shipping on Windows, budget for your own hardware verification pass.

The Direct3D 12 presentation split

DIRECTX12 carries one extra wrinkle worth knowing before you debug it. Swap-chain creation crashes under plain Wine: a null-pointer read inside Wine's own dxgi.dll, caused by an architecture mismatch between the system dxgi.dll and the separately overridden vkd3d-proton d3d12.dll. It is not a CNA bug and it reproduces from a raw spike with no CNA code involved.

A properly Proton-managed launch gives vkd3d-proton the matched DLL pair it expects, and both swap-chain creation and real Present() work through a live window:

scripts/run-proton-vkd3d.sh build-dx12/cna_diag_d3d12_swapchain.exe

Because Proton's bootstrap launch is heavy, the routine DIRECTX12 test suite deliberately renders off-screen instead: it binds a real render target and reads pixels back through a readback heap, never touching the swap chain. So use the ordinary CTest path for pixel correctness, and the Proton script only when you genuinely need a window on screen.

The off-screen route is available to your own code too, on DIRECTX12. PresentationParameters exposes a CNAEXT HeadlessEXT flag that creates a windowless GraphicsDevice, and DIRECTX12 is the Direct3D renderer that honours it; DIRECTX11 creates its swap chain in its constructor and does not support HeadlessEXT. Under Wine, scripts/run-wine-vkd3d-headless.sh wraps run-wine-vkd3d.sh for tests that must never create a swap chain.

What SupportsCapability() says on the Direct3D renderers

At alpha.1 the Direct3D renderers relied on the permissive base answers. That changed in this snapshot: DIRECTX11 and DIRECTX12 now have their own SupportsCapability() switch, with no default arm, so an unknown enumerator answers false. Of the three Direct3D renderers, only DIRECTX9 still inherits the base defaults wholesale. GraphicsCapability now has 19 members (14 at alpha.1).

⚠

DIRECTX9 is the one Direct3D renderer that does not override SupportsCapability(): its answers are the inherited base defaults, so nothing in them was authored for that renderer. Do not design a feature-detection path around those answers — probe the real operation instead, or query the richer capability profile that Tutorial 101 describes.

The compiled-effects switches (all default OFF) enable XNA Effect Framework bytecode through MojoShader; a default configure reports CompiledEffects as false on all three. Positive answers are still a hint rather than proof that a particular draw path executes: the ComputeShaders doc comment in the public header says D3D11/D3D12 “can express” compute, but neither renderer implements it in this snapshot. For a richer, queryable picture — features, numeric limits and per-format usage — use the RendererCapabilityProfile API described in Tutorial 101.

One concrete gap no capability answer reflects: binding a RenderTargetCube face inside a multiple-render-target set is unimplemented on all three renderers (a single cube face bound alone works, and a multi-target set with a cube face throws). Occlusion queries are wired on all three; on DIRECTX9 the query is created only when the device passes D3D9's own support probe, otherwise the renderer reports it unsupported.

If pixel-exactness is the goal, this is the wrong page

Both renderers above are real, tested Direct3D implementations. Neither is the fidelity renderer. CNA's XNA oracle corpus is 39 scenes (256×256, HiDef) with reference PNGs captured from the genuine Microsoft XNA 4.0 runtime — run under Wine with DXVK on Linux, not on native Windows. DIRECTX9 is the only renderer recorded in the repository as matching all 39 at tolerance 0: the CTest D3D9_XNA_Diff renders every scene through a cross-built DIRECTX9 binary under Wine + DXVK and fails on any single-channel difference. The last consolidated dated divergence report covers 31 scenes (later per-scene notes record the rest), the run has not been repeated on native Windows hardware, and none of this runs in CI. That is a statement about DIRECTX9 over DXVK, not about Direct3D 9 on every native driver.

Pick DIRECTX11/DIRECTX12 for a modern Windows path with a runtime HLSL shader route; pick DIRECTX9 when bit-identical XNA 4.0 output is the requirement. The other two Windows-only renderers are 2D-only: DIRECT2D (Direct2D 1.1 over a Direct3D 11 device) and GDI (classic Win32 GDI with a private CPU rasterizer that cannot be linked into the same binary as SOFTWARE).
