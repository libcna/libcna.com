Tutorial 105: Browser Renderers: WebGL, Canvas and WebGPU

CNA Tutorials  ·  Renderers

ℹ

What you’ll learn

  • What WEBGL2, WEBGL1, CANVAS and WEBGPU each draw with in the browser, and how to choose between them.
  • What WEBGL1 and the 2D-only CANVAS give up, and the WebGL-specific divergences worth knowing.
  • How CANVAS maps blending, sampling and backbuffer readback onto the Canvas 2D API, and where it refuses.
  • How to pick the browser renderer at run time, how much of this has run in a real browser, and the web caveats that apply no matter which one you pick.

Before you start — Tutorial 81: Building for the Web covers the Emscripten toolchain these renderers require.

Under Emscripten CNA offers four renderers. WEBGL2 (the Emscripten default) and WEBGL1 are two profiles of the shared EasyGL implementation that also drives OPENGLES3 on the desktop; CANVAS draws with the browser’s Canvas 2D API and is 2D-only; and WEBGPU, the same identity CNA builds natively over wgpu-native, reaches the browser through Emscripten’s emdawnwebgpu port and is declared experimental (see Tutorial 132). OPENGLES2, OPENGLES3 and OPENGL33 are refused under Emscripten.

WEBGL2, WEBGL1 and CANVAS are Emscripten-only and refuse to configure for a native target with a FATAL_ERROR, because a WebGL context and a CanvasRenderingContext2D only exist inside a browser. In every case SDL3 still owns the page’s <canvas> element, keeps it sized and delivers input through it.

What each one draws with

RendererBrowser APIWhat you get
WEBGL2A WebGL 2.0 context (EasyGL asks for a GLES 3.0-shaped context and the browser maps it to WebGL 2)Full 2D and 3D, custom ShaderEffect in GLSL ES 3.00, render targets, MRT, instancing, occlusion queries, Texture3D. Feature-equivalent to OPENGLES3, minus what WebGL itself lacks (below).
WEBGL1A WebGL 1.0 context, with CNA’s stock shaders rewritten to GLSL ES 1.002D and 3D, but it genuinely loses multiple render targets, occlusion queries, Texture3D, instancing and multi-stream vertex input. In a bundle that also contains WEBGL2, the WEBGL1 profile runs on a WebGL 2 context.
CANVASCanvasRenderingContext2D: drawImage, putImageData, fillRect2D only, the same scope as SDL_RENDERER: no 3D pipeline, no programmable shader stage, no depth or stencil buffer, no MSAA. Each Texture2D and render target owns a private off-screen canvas, and an upload is one synchronous putImageData.
WEBGPUWebGPU through emdawnwebgpu, presenting into the page’s #canvas2D and 3D with WGSL custom shaders, from the same renderer source as the native build. Declared experimental; it needs a browser with WebGPU enabled.

Every 3D entry point CANVAS overrides throws deterministically rather than silently doing nothing; Unsupported3DGraphicsCallBehavior::WarnAndStub turns that into one warning per operation and a no-op, as on SDL_RENDERER (Tutorial 101).

WEBGL2 and WEBGL1: the GL family in the browser

Both WebGL identities are the EasyGL renderer compiled with a different profile define, so most of Tutorial 102 applies unchanged: the same stock effects, the same capability answers per generation, and the same rule that your own ShaderEffect source is passed to the driver verbatim. WEBGL2 wants GLSL ES 3.00 (#version 300 es); WEBGL1 wants GLSL ES 1.00, and CNA’s ES 3.00-to-1.00 rewrite applies to its own stock shaders only. A few things are specific to WebGL:

  • No compute and no indirect draw in any WebGL version; the capability answers are false there whatever the GPU underneath could do.
  • Wireframe needs WEBGL_polygon_mode. Without that extension GraphicsCapability::WireFrame stays false; EasyGL emulates wireframe for two bounded stock routes (non-indexed VertexPositionColor triangle lists, and indexed position-and-normal geometry), and every other wireframe draw is refused.
  • Two recorded divergences from Direct3D. WebGL never applies MultiSampleMask (an all-ones mask is fine), and the channels a one- or two-channel render target does not store read back as 0 rather than D3D’s 1, because WebGL has no texture swizzle.
  • The back buffer is the canvas itself. On the desktop EasyGL draws into an off-screen framebuffer and blits it at Present; on the web it draws straight into the canvas, whose size CNA manages.
  • Compiled XNA effects are opt-in with -DCNA_EASYGL_COMPILED_EFFECTS=ON, as on the desktop. In this snapshot compiled effects that use volume samplers or sample float textures also build on WEBGL2 (GLSL ES 3.00 precision fixes to the pinned MojoShader).

CANVAS: readback, blending and the 2D boundary

GetBackBufferData() is a real, synchronous getImageData against whichever context is bound, so screenshots and pixel comparisons work, and a RenderTarget2D reads back the same way. Present() is a no-op: the browser compositor shows the canvas on its next paint.

Blending maps onto globalCompositeOperation, which has no general blend-factor model, so only XNA’s four presets exist:

BlendStateCanvas 2D mapping
Opaque'copy', clipped to the sprite’s own rectangle so the rest of the canvas is untouched
AlphaBlend'source-over', after converting the premultiplied texture to straight alpha (cached once per texture generation)
NonPremultiplied'source-over' directly — Canvas 2D already treats its input as straight alpha
Additive'lighter'; AdditiveBlending is the one capability CANVAS reports as true
Any other blend factor or functionThrows

Sampling is coarser than on a GPU. TextureFilter maps onto imageSmoothingEnabled (Canvas 2D has no separate minification, magnification or mip control). Clamp is implemented by clamping the source rectangle; Wrap and Mirror use canvas patterns and only matter when a source rectangle exceeds the texture, and CNA’s own documentation lists both as not yet verified in a real browser. Mixed per-axis address modes, a tinted draw with an out-of-bounds Wrap/Mirror source rectangle, and an AlphaBlend draw in the same situation throw rather than guess.

The rest of the boundary is explicit: SetData on a mip level above 0 throws (Canvas 2D has no mip chain), binding two or more render targets throws (a 2D context is single-target), SpriteBatch::Begin with a custom Effect throws, and depth, stencil, cube and volume resources do not exist. Colour tint is an exact per-pixel RGB multiply, with alpha applied through globalAlpha.

WEBGPU in the browser

WEBGPU is one renderer identity with two backends, not two renderers. The browser build reuses the native renderer and every WGSL shader; under Emscripten it links the emdawnwebgpu port (no WebGPU library to download or ship), creates its surface from the CSS selector #canvas, waits for WebGPU’s promises by yielding through Asyncify, and lets requestAnimationFrame present each frame. CNA’s records describe cna_demo_2d, the 3D house demo and pages for every stock effect running in headless Chrome, and compiled XNA effects passing there with -DCNA_WEBGPU_COMPILED_EFFECTS=ON; those runs use the repository’s scripts/run-webgpu-browser-test.sh harness and are not part of CI. Treat the browser route as experimental, and check that your target browsers expose WebGPU at all. Tutorial 132 covers the renderer itself.

Web caveats that apply to all of them

ℹ

Heap-allocate your Game? Not any more. Alpha.1 built the web main loop on emscripten_set_main_loop with an infinite-loop simulation, which unwound the caller and destroyed a stack-local Game under the running callback. In this snapshot Game::Run() blocks on the caller's own stack through Asyncify (EM_ASYNC_JS awaiting requestAnimationFrame), so an ordinary local MyGame game; game.Run(); is supported, exactly as on native platforms. CNA-owned application executables opt into Asyncify automatically; an external final executable that uses a blocking Game::Run() must link the CNA::EmscriptenAsyncify CMake interface target.

Saves persist through IndexedDB. CNA’s storage module mounts IndexedDB-backed IDBFS at /cna-storage (StorageDevice) and /save (IsolatedStorage) and restores both before main(), so saves survive a page reload. A threaded build uses WasmFS by default, which cannot host IDBFS, and StorageDevice reports storage as unavailable there unless you configure -DCNA_EMSCRIPTEN_USE_WASMFS=OFF. See Tutorial 19.

Video links but does not play. The Video and VideoPlayer types exist and link on the web (FFmpeg is never built for Emscripten), and any attempt to decode throws System::NotSupportedException at run time. Alpha.1's “fails to link” behaviour is gone.

Picking the renderer from the page

When one WebAssembly bundle links several browser renderers (the multi-renderer build below), the page chooses among them without recompiling. The property Module.cnaPreferredRenderer is consulted at the same precedence as the CNA_GRAPHICS_RENDERER environment variable (an actual environment variable wins over it); an explicit GraphicsRendererSelection::SetPreferred() call wins over both:

<script>
  // Must be defined before the Emscripten glue script loads.
  var Module = { cnaPreferredRenderer: "CANVAS" };
</script>

The exported Module._cna_set_preferred_renderer(name) is an alternative that behaves like SetPreferred(). Names are the 18 canonical spellings, matched case-insensitively at run time; a name that does not name a renderer, or names one that is not linked into the bundle, throws instead of falling back. Selection latches when the first GraphicsDevice is successfully created (see Runtime Renderer Selection). A page can therefore offer CANVAS as a fallback for players whose browser refuses a WebGL context.

Building

emcmake cmake -S . -B build-web     -DCNA_GRAPHICS_RENDERER=WEBGL2   # the default
emcmake cmake -S . -B build-web1    -DCNA_GRAPHICS_RENDERER=WEBGL1
emcmake cmake -S . -B build-canvas  -DCNA_GRAPHICS_RENDERER=CANVAS
emcmake cmake -S . -B build-webgpu  -DCNA_GRAPHICS_RENDERER=WEBGPU   # experimental

cmake --build build-canvas --parallel

# One bundle with the three Emscripten-only renderers (WEBGL2 stays the default)
emcmake cmake -S . -B build-web-multi \
      -DCNA_GRAPHICS_RENDERER=WEBGL2 \
      -DCNA_GRAPHICS_RENDERERS="WEBGL2;WEBGL1;CANVAS"

The two WebGL profiles need the ../easy-gl and ../meta-gl sibling checkouts, as on the desktop; CANVAS needs neither.

Choosing between them

You needPick
3D, custom shaders, or simply the safe defaultWEBGL2 — see Tutorial 102
A target that genuinely cannot get a WebGL 2 contextWEBGL1, after removing every use of MRT, occlusion queries, Texture3D and instancing
A pure 2D game that must run without WebGL, or a WebGL-free fallback in a multi-renderer bundleCANVAS
