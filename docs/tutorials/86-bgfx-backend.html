Tutorial 86: bgfx Backend: Features and Limitations

  • Enabling it, and how CNA's layer relates to bgfx's own API.
  • When bgfx is the right choice — and when it is not.

Before you start — Tutorial 72: Choosing the Right Rendering Backend — this is the detail page behind one row of that comparison. Note bgfx is a partial backend and narrower than bgfx itself; its renderer coverage is GL/GLES/Vulkan/WebGPU only.

bgfx overview — partial, and narrower than bgfx itself

⚠

Read this before choosing bgfx. The upstream bgfx library supports OpenGL, Vulkan, Direct3D and Metal. CNA's bgfx backend does not reach all of them: it ships 108 shader blobs, but only for GL, GLES, Vulkan and WebGPU — there are no D3D or Metal variants. On bgfx's default renderer on Windows (Direct3D) and macOS (Metal), 3D silently draws nothing. There is no error and no warning, just an empty frame.

CNA's bgfx backend wraps bgfx to provide XNA-compatible rendering, and is classified as partial. It is one of CNA's four original backends, dating from April 2026, and it carries a reasonable amount of CTest coverage — but its shader-variant gap and two verified correctness defects mean it is not a drop-in alternative to EasyGL or Vulkan today.

Note that bgfx's own Direct3D 11/12 support here is bgfx's internal abstraction, not CNA's. CNA also ships three separate, native Direct3D backends — D3D9, D3D11 and D3D12 (Windows-only, hand-written HLSL, no bgfx dependency) — see Tutorial 72 if you specifically want a direct Direct3D code path rather than going through bgfx's abstraction.

Enabling bgfx backend

bgfx is pulled in automatically via CMake FetchContent (bgfx.cmake) — you do not need to clone it yourself:

cmake -S . -B build-bgfx \
  -DCNA_GRAPHICS_BACKEND=BGFX \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build-bgfx -j$(nproc)

One caveat worth knowing: bgfx.cmake is fetched at GIT_TAG master, making it the only unpinned dependency in the entire project. An upstream bgfx change can therefore break this backend's build without any change on CNA's side.

What works (basic 3D, SpriteBatch, most effects)

  • Full SpriteBatch 2D rendering including rotation, scale, and color tinting
  • BasicEffect, AlphaTestEffect, DualTextureEffect
  • VertexBuffer, IndexBuffer, and DrawPrimitives / DrawIndexedPrimitives
  • Texture2D — note that CNA can only construct SurfaceFormat::Color textures anywhere, regardless of what bgfx supports
  • BlendState, DepthStencilState, RasterizerState
  • SamplerState (point, linear, anisotropic)
  • Keyboard, Mouse, GamePad input (via SDL3)
  • SoundEffect / SoundEffectInstance audio (via SDL3_mixer, independent of bgfx)

What is broken or missing

  • No D3D or Metal shader variants. The 108 shader blobs cover GL, GLES, Vulkan and WebGPU only, so 3D produces an empty frame on bgfx's default Windows and macOS renderers.
  • 32-bit index buffers are corrupted. The backend never overrides CreateIndexBuffer32, so 32-bit indices are uploaded into a 16-bit buffer and DrawUserIndexedPrimitives renders corrupt geometry. Every other 3D backend in CNA implements this correctly. This is a confirmed bug, not a limitation.
  • Draw offsets are ignored. startIndex and baseVertex have no effect outside the wireframe path, so drawing a sub-range of a shared buffer renders the wrong geometry.
  • Custom ShaderEffect is not a verified path here. The two pixel-tested custom-shader paths are GLSL on EasyGL and SPIR-V on Vulkan; bgfx expects its own precompiled binary shaders.

The first three of these are tracked as open contribution opportunities — see Contribute.

bgfx's own API layer

bgfx has its own API (bgfx::submit, bgfx::setVertexBuffer, etc.) that is separate from CNA's XNA-style API. CNA's bgfx backend translates XNA calls into bgfx draw calls internally. You do not need to know bgfx's API to use CNA on the bgfx backend, but if you need features not exposed by CNA, you can call bgfx:: functions directly after obtaining the bgfx context from CNA's internal backend handle (not officially supported, use at your own risk).

When to use bgfx — and when not to

Use it when you are working on the backend itself, or when you have verified that your target platform resolves bgfx to a GL, GLES or Vulkan renderer and you are not relying on 32-bit indices or draw offsets.

Do not reach for it as the macOS answer: CNA's bgfx ships no Metal shaders, so 3D will not draw. macOS handling across CNA is minimal in general and there is no macOS CI. Equally, do not choose it for Windows Direct3D — CNA has three native Direct3D backends (D3D9, D3D11, D3D12) that are Windows-gated, hand-written, and do not go through bgfx's abstraction. See Tutorial 72.

# CMakeLists.txt for bgfx backend
cmake_minimum_required(VERSION 3.20)
project(MyGame CXX)
set(CMAKE_CXX_STANDARD 23)

set(CNA_GRAPHICS_BACKEND "BGFX" CACHE STRING "CNA rendering backend")
set(BGFX_DIR "${CMAKE_SOURCE_DIR}/../bgfx" CACHE PATH "bgfx root")

add_subdirectory(../cna ${CMAKE_BINARY_DIR}/cna)

add_executable(MyGame main.cpp)
target_link_libraries(MyGame PRIVATE CNA::CNA)

Runtime check for backend (bgfx does not expose backend selection at the CNA API level — it is selected at compile time via CMake):

// At runtime you can query which backend was compiled in:
#if defined(CNA_BACKEND_BGFX)
    // bgfx-specific workaround: disable occlusion culling
    useOcclusionQuery_ = false;
#elif defined(CNA_BACKEND_EASYGL)
    useOcclusionQuery_ = true;
#elif defined(CNA_BACKEND_VULKAN)
    useOcclusionQuery_ = true;
#endif
