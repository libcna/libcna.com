Per-namespace API coverage, audited from the CNA source tree

ⓘ

How this page measures coverage. Two different numbers are reported for every namespace. Types present is a count of XNA 4.0 public types that exist in CNA's headers. Functional coverage is an audit of whether those types' members actually do the work — reached by reading the implementation, not by trusting the declaration. The two diverge sharply in places, and the gap is what this page is for.

Presence is not behaviour

Essentially every public XNA 4.0 type is present in CNA. The only outright absences are five reflection-only ContentSerializer* attributes — meaningless in C++, which has no reflection — and a handful of XNB type readers. Repo-wide there are just 2 CNA_STUB markers and 14 @note Status: Stub headers.

That gives:

  • Type presence ≈ 99%. If you look up an XNA class, it is almost certainly there, with its real member signatures.
  • Functional coverage ≈ 75%, weighted. That is what actually runs.
⚠

Do not read the first number as the second. A compiling call is not a working call. The largest single contributors to the 24-point gap are, in order: compiled .fx shader bytecode (throws unconditionally), the SurfaceFormat::Color-only texture restriction, GamerServices having no service backend at all, and Media's catalogue layer.

The two headline Graphics limitations

These two account for most of the distance between "the type is there" and "your game runs."

1. Compiled .fx bytecode is not supported at all

Effect(GraphicsDevice&, byte[]) — the constructor that every XNA game with a custom shader goes through — throws NotImplementedException unconditionally, in src/Microsoft/Xna/Framework/Graphics/Effect.cpp. There is no MojoShader equivalent in CNA and no bytecode translation layer of any kind.

Games with custom HLSL effects cannot run. Custom shaders are reachable only through the CNA-only (NOXNA) ShaderEffect, which takes hand-written GLSL or SPIR-V source. The six stock effects are unaffected: they are implemented natively in C++, not translated from bytecode, so BasicEffect and friends work everywhere.

This is the single biggest real porting gap in the project.

2. Only SurfaceFormat::Color textures can be constructed

Texture::ValidateFormat throws for all 25 other surface formats, and it is called from both Texture2D constructors, from Texture3D and from TextureCube. The SurfaceFormat enum lists the full XNA set; only one member of it is constructible.

Consequences worth planning around: DXT and DDS files load only by CPU-decompressing to RGBA, and float, half-float and HDR render targets are unavailable despite appearing in the enum.

Content and the .xnb pipeline

A real XNB reader exists and is wired into ContentManager — roughly 4,000 LOC under src/CNA/Internal/Xnb/ and include/CNA/Internal/Xnb/, with 24 test files, 134 test cases, and binary MonoGame fixtures under tests/assets/xnb/.

  • 49 XNB type readers are registered, covering all primitives, all math types, Texture2D/Texture3D/TextureCube, SpriteFont, SoundEffect, Song, the five stock effects and the model family.
  • A real 31 KB LZX decompressor, the full FNA ContentReader surface, two-pass shared-resource resolution, and fuzz-hardening against malformed and adversarial files.
  • ContentManager prefers a .xnb when one exists, and otherwise falls back to loose files.
💡

You must call CNA::Internal::Xnb::RegisterAllBuiltInXnbReaders() once at startup. This is a deliberate design decision, documented in the header — but it does mean the reader registry is empty by default, and a .xnb load will not work until you make that call.

Genuine gaps in the pipeline:

  • No ReflectiveReader, so no custom or user-defined type can be loaded from an XNB file at all. C++ has no reflection to build one on.
  • Missing EnumReader, ExternalReferenceReader, VideoReader, and a real EffectReader (registered as an always-throwing placeholder).
  • Array, List, Dictionary and Nullable readers are implemented but not registered — without reflection, each closed generic needs hand-registration.
  • ResourceContentManager is the repository's only pure stub. ContentManager::Unload() clears its maps without disposing the assets.

Media — a sharp split

Media is the namespace where presence and behaviour diverge most, so be precise about which half you are touching.

HalfState
Playback — MediaPlayer, Song, Video, VideoPlayer Real MediaPlayer genuinely plays songs through SDL3_mixer. VideoPlayer genuinely decodes video through FFmpeg — real libavcodec/libavformat/libswresample with PTS-driven pacing. Caveat: FFmpeg is unavailable on Emscripten, Android and every Windows target, so video playback is effectively native-Linux-only today.
Catalogue — MediaLibrary, MediaSource, Album, Artist, Genre, Playlist, Picture, PictureAlbum and all 6 collections Throws All 14 types throw on every member. This is the Zune / Windows Phone media-catalogue API, not something a game normally touches — but nothing behind it is implemented. MediaLibrary::SavePicture(string, Stream*) is worse than a throw: it is declared with no definition anywhere, so it is a link error.

There are zero test files for Media. Everything above was established by reading the code, not by running it.

GamerServices — shape without service

All 51 XNA GamerServices types are present with complete member signatures, and there is no backend of any kind behind them: no Steam, no HTTP, no sqlite, no filesystem persistence. This was verified by grep, not inferred. It is a faithful port of FNA's no-op shim — XNA code compiles and runs, and nothing is persisted.

⚠

If your port depends on achievements, leaderboards, friends or profile data surviving a restart, none of that happens. Earlier versions of this page claimed disk-persisted leaderboards and achievements. That was wrong and has been corrected.

  • 16 of the 17 Guide::Show* methods are empty bodies; all 3 ShowMessageBox entry points throw.
  • ShowKeyboardInput displays nothing, and EndShowKeyboardInput returns "".
  • GamerServicesDispatcher::Initialize() fabricates four gamers, all named "Stub Gamer".
  • Every LeaderboardReader and LeaderboardWriter I/O path throws.
  • SignedInGamer::IsFriend() always returns false; GetFriends() returns empty; AwardAchievement() is empty.
  • AvatarRenderer::Draw() validates 71 bones and then does nothing. The working renderer sits behind the NOXNA DrawRealEXT().

What is complete: all 16 enums, 6 exceptions, 3 EventArgs types and the 4 collection types — real data structures with correct .NET exception semantics. 311 unit tests cover exactly that shape, and nothing beyond it.

Framework core, Graphics and PackedVector

These three are the load-bearing part of the API and the part that holds up best.

  • Framework core (44 types, ~98%). The math library is complete and heavily tested: Matrix carries all 30 static factories including Decompose, the billboard pair, shadow and reflection; Curve::Evaluate implements all five loop types; Color defines all 141 named constants. Game is a genuine SDL loop with both fixed and variable timestep and a separate Emscripten path. The one hole is BoundingFrustum::Intersects(Ray), which throws while every other BoundingFrustum overload works.
  • Graphics (106 types, ~90%). Every XNA Graphics type exists. GraphicsDevice exposes all six events and all five Draw* families; SpriteBatch implements all five Begin, eight Draw and six DrawString overloads. Behaviour varies by backend — see Rendering Backends — and the two limitations above apply everywhere.
  • PackedVector (19 types, ~85%). All 17 packed formats are real, built on a correct IEEE 754 half-float codec that handles subnormals, infinities and NaN in both directions. The uniform gap is that none of the 17 implement ToString() or GetHashCode().

Input, Touch and Devices

  • Input (19 types, ~98%) has zero stubs. The GamePad path is a 2,071-line bridge onto real SDL3: rumble, trigger rumble, LED colour, hot-plug and per-device capability probing all work. Keys has all ~145 members.
  • Input::Touch (7 types, ~95%) genuinely detects all 10 XNA gesture types through a 474-line state machine with exponentially-smoothed flick velocity. One real bug: TouchCollection reports IsReadOnly == true, but its mutators mutate rather than throwing.
  • Microsoft::Devices and Sensors (18 types, ~85–90%) talk to real hardware. Accelerometer and Gyroscope use the SDL3 sensor API on Android, iOS and desktop, with correct m/s²→g conversion and serious concurrency hardening. VibrateController really vibrates, via SDL_InitHapticRumble plus a real SDL_HAPTIC_LEFTRIGHT effect, deliberately excluding gamepads. Compass and Motion are Android-only, built on an NDK fusion of five sensors, and honestly report NotSupported everywhere else.
💡

The Microsoft::Devices layer is built only when CNA_DEVICES=ON, which is not the default. No current default build or CI job exercises it.

Audio, Net and Storage

  • Audio (19 types, ~92%). XACT is a real parser and player rather than a facade: a 1,115-line parser for the XGS, XWB and XSB binary formats, FACT's actual volume formula, and real RPC curves, with output through SDL3_mixer. 3D audio uses FAudio's exact Doppler and F3DAudio attenuation. Partial: only the first PlayWave per track is honoured, XMA and WMA throw, and reverb is a no-op.
  • Net (23 types, ~87%). Real ENet over genuine UDP, with real LAN discovery (broadcast port 61190, measured RTT for QoS) and a two-process loopback test. Real transport is gated to NetworkSessionType::SystemLink; PlayerMatch and Ranked correctly no-op, because they need Xbox Live. Voice chat is a no-op by design.
  • Storage (3 types, 100%). Real std::filesystem IO, a hand-written glob matcher, and correct <root>/<displayName>/Player{N} namespacing. The async Begin*/End* pairs are implemented synchronously, which is the right call on desktop. The caveat is coverage, not correctness: Storage has zero unit tests, the same as Media.

NOXNA: what CNA adds beyond XNA

CNA also ships a substantial non-XNA surface. Every declaration that is not part of XNA 4.0 is tagged with the NOXNA marker macro — an empty macro whose only job is to make the boundary visible — and a CMake option enforces that boundary at compile time. There are 1,289 NOXNA markers across include/: 939 in include/Microsoft/ and 350 in include/CNA/.

AreaWhat CNA adds
Graphics ShaderEffect (the only custom-shader path), PbrEffect and SkinnedPbrEffect for physically based rendering, skeletal animation via SkinnedModelEXT + AnimationPlayer + AnimationClipEXT/BoneTrackEXT/KeyframeEXT, MorphTargetEXT blend shapes, tangent and skinned vertex types, and sRGB/BC7 surface formats.
Input Roughly 17 GamePad EXT methods (GUID, light bar, trigger vibration, gyro and accelerometer, power info, touchpad fingers, Steam handle), paddle/Misc1/TouchPad buttons, 6 Keyboard scancode methods, MouseCursor and TextInputEXT.
The whole CNA:: namespace About 58 public headers with no XNA counterpart at all: Camera, FileDialog, MessageBox, SystemTray, Clipboard, UrlLauncher, Locale, PowerInfo, DisplayInfo, SystemInfo, full Joystick and Haptics APIs, Logger, and RenderPipelineSettings/PbrMaterial/TonemappingMode/ShadowQuality.
Core TitleLocation, GraphicsDeviceManager::PresentationMode, GameWindow::{Minimize,Restore,GetNativeSdlWindow}EXT, and FPS-target helpers.

Two things follow from this. If you want to know whether your code would also compile against real XNA, the NOXNA boundary answers that at compile time. And if you are willing to leave XNA behind, PBR, skeletal animation and a real custom-shader path are available — just not through the XNA API. Note that CNA_NOXNA defaults to OFF, so the extended layer is not exercised by any current default build or CI job.

Is it actually usable?

Type-presence percentages only go so far. The most direct evidence that CNA's XNA surface holds up under real code is the sibling cna-samples repository, which ports Microsoft's official XNA Game Studio 4.0 sample collection to C++ on CNA.

ResultDetail
63 of 86 official XNA samples building The sample collection is ported to C++ against CNA's XNA surface; 63 of the 86 currently build.
The remaining 23 not building Any sample that ships custom .fx shaders is unreachable while the bytecode constructor throws.

Beyond the samples, CNA Craft ports fogleman/Craft, a voxel game, onto CNA, and cna-extended is a C++23 port of MonoGame.Extended on top of it. Both exercise the API from outside the project's own test suite.

💡

Honest positioning: CNA is a research-grade porting framework, not yet a ship-a-commercial-game framework. The strongest true claims are near-total XNA type presence, a genuinely production-real Graphics/Input/Audio/Net/Storage core, and pixel-exact verification against the real XNA runtime. The caveats on this page are the other half of that picture.

C++ API differences from C# XNA

While CNA mirrors XNA's API surface, there are necessary differences due to the C++ language:

  • No garbage collection: Resources are managed with RAII and std::unique_ptr / std::shared_ptr. Objects must be explicitly managed by the caller.
  • No properties: C# properties become getter/setter methods (e.g. getGraphicsDeviceProperty() instead of the C# GraphicsDevice property).
  • No C# delegates: event semantics are preserved where XNA has them — GraphicsDevice exposes all six of its events — but through C++ callback objects and virtual overrides rather than event/delegate.
  • Namespace syntax: Microsoft::Xna::Framework with :: instead of ..
  • No extension methods, LINQ, or generics as they exist in C#.

Known gaps and limitations

The headline gaps are below. The Verification & Known Issues page carries the complete, current list, including every open rendering bug.

  • Compiled .fx shader bytecode — Effect's bytecode constructor throws unconditionally. Custom shaders must be hand-written as GLSL or SPIR-V through the NOXNA ShaderEffect. This is the single biggest practical barrier to porting an existing XNA game.
  • Only SurfaceFormat::Color textures — Texture::ValidateFormat throws for the other 25 formats, so DXT/DDS assets are CPU-decompressed to RGBA and float/half/HDR render targets are unavailable.
  • No ReflectiveReader for XNB — the 49 registered readers cover the stock types, but no custom or user-defined type can be loaded from an .xnb file. EnumReader, ExternalReferenceReader, VideoReader and a real EffectReader are also missing, and the reader registry is empty until you call RegisterAllBuiltInXnbReaders().
  • GamerServices has no service backend — all 51 types exist with full signatures, and nothing persists. GamerServicesDispatcher::Initialize() fabricates four gamers named "Stub Gamer"; every leaderboard I/O path throws.
  • The media catalogue throws — MediaLibrary, MediaSource, Album, Artist, Genre, Playlist, Picture, PictureAlbum and their 6 collections, 14 types in all, throw on every member. Song and video playback is real, but FFmpeg-backed video is native-Linux-only.
  • BoundingFrustum::Intersects(Ray) — throws NotImplementedException; every other overload works.
  • Media and Storage have zero unit tests — their described behaviour rests on code reading, not on a passing suite.
  • SDL_Renderer is 2D-only — by design; every 3D entry point throws. Backend maturity varies widely; see Rendering Backends before committing to one.
  • macOS gets minimal handling only, and iOS has zero references in the build system. Neither is a target you can rely on.

Intentionally excluded from CNA

  • Real Xbox Live server-side services (authentication against Microsoft's servers, matchmaking, cloud-synced achievements and leaderboards) — GamerServices is a faithful port of FNA's no-op shim instead, and genuine Xbox Live integration is out of scope.
  • Non-SystemLink NetworkSessionType values (PlayerMatch, Ranked) — they correctly no-op rather than pretending; no synthetic offline approximation is attempted.
  • Voice chat — a no-op by design.
  • Reflection-dependent Content APIs — the five ContentSerializer* attributes have no meaning in C++ and are the only genuinely absent XNA types.
  • Windows Phone sensor emulation — Accelerometer and Gyroscope use real SDL3 sensors where the platform has them; Compass and Motion report NotSupported off Android rather than faking values.
