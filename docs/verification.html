Verification & Known Issues

How CNA's XNA compatibility is actually checked — and what is verifiably not checked at all

ⓘ

All figures on this page were taken from the CNA source tree and its build/test trees, not from a changelog. If a number here disagrees with a blog post or a README, trust this page — and if it disagrees with what ctest prints on your machine, trust ctest.

How CNA is verified

An XNA reimplementation can pass its own test suite perfectly and still be wrong, because the tests encode the author's belief about what XNA does. CNA works around that with five layers, three of which compare against something outside the project.

Layer What it checks Scale
Unit tests (GoogleTest) Math, geometry, curves, packed vectors, game-loop semantics, state objects, input, audio, networking, content readers. Runs headless. 4,845 cases across 419 suites in the built CnaTests binary (4,900 exist in source), from 287 test .cpp files
GPU pixel-readback tests (ctest) Renders a scene on a real device context, reads the framebuffer back to the CPU, and asserts on actual pixel values. This is what catches "the shader compiles but draws the wrong thing." 648 backend integration/pixel CTests; ~436 of 559 example programs (78%) do real GPU→CPU readback with tolerance 0 exact-match assertions, plus 17 golden PNGs
XNA 4.0 oracle corpus Scenes rendered by a real C#/XNA reference renderer and diffed pixel-exactly against CNA's D3D9 output. Ground truth is the actual Microsoft runtime, not anybody's reading of it. 39 scenes under tools/xna-oracle/, diffed at --tolerance 0
Differential testing against FNA A harness links a real, running FNA build and dumps reference values to JSON; a matching C++ tool dumps CNA's; a script diffs them key by key. Ground truth comes from executing FNA, not from reading its source. tools/fna-reference/, tools/cna-reference/, scripts/compare-fna-reference.py
NOXNA purity compile check Every declaration that is not part of XNA 4.0 is tagged NOXNA. A dedicated build turns that tag into [[deprecated]] and compiles with -Werror, so the build breaks if XNA-surface code ever leans on a CNA extension. tools/devices/StrictXnaApiSurfaceCheck.cpp proves the XNA-only surface stands alone. 1,289 tagged declarations in include/

Per-backend integration coverage

Backend selection is a compile-time choice (-DCNA_GRAPHICS_BACKEND=<NAME>), with exactly one backend per build and no runtime dispatch. That has a direct consequence for verification: covering all 14 backends requires 14 separate configure + build + test runs. Nobody runs all 14 on every change.

BackendCTestsVerification status
EasyGL239Production-ready The most heavily tested backend, and the Linux default.
Vulkan138Functional Near production; 35 SPIR-V entry points, real stencil PSO, MSAA resolve.
bgfx114Partial Well covered on GL/GLES/Vulkan/WebGPU; no D3D or Metal shader blobs exist, so 3D silently draws nothing on bgfx's default Windows/macOS renderer.
SDL_Renderer68Production-ready within its 2D scope The only backend whose capability reporting is fully truthful; 3D calls throw by design.
SDL_GPU21Functional Deferred/retained design, 23 SPIR-V blobs, stencil and MSAA resolve. Vulkan-only device today.
D3D919Functional Windows-only. 72 verified SM2/SM3 blobs; the only backend targeting pixel-exact XNA 4.0 authenticity, and the one the oracle corpus is diffed against.
WebGPU14Experimental Backbuffer-only forward renderer.
Dx39Functional 2D only, best 2D fidelity; real Wrap/Mirror addressing and four distinct blend formulas.
D3D117Functional Windows-only. Verified from Linux through Wine + DXVK, and on real Windows via the manual MSVC workflow.
Headless7Test harness, not a renderer Renders nothing by design; ReadBackbuffer returns the last clear colour.
Software6Functional Genuine CPU rasterizer with a real Z-buffer and perspective-correct interpolation. TriangleList only.
Ascii6Functional 2D only; a decorator over SDL_Renderer that quantizes the frame to a glyph grid.
D3D121Partial Strong core, but no scissor, no viewport, no stencil, no blend factor; MRT clears but never draws.
Canvas0Unverified Emscripten-only, carefully written — and no automated test ever renders a Canvas pixel.

The XNA 4.0 oracle corpus

This is the strongest verification claim CNA can make, so it is worth being precise about what it is.

Under tools/xna-oracle/ sit 39 scenes plus a reference renderer written in C# against real XNA. Each scene is rendered by the real Microsoft runtime, producing reference images. CNA renders the same scene through its D3D9 backend, and the two are diffed with --tolerance 0 — byte-identical or fail.

That makes the ground truth for those 39 scenes the actual XNA runtime rather than anyone's interpretation of it, and it is why D3D9 is the backend held to a pixel-exact authenticity bar rather than a "looks right" bar. The corpus does not cover the whole API; it covers 39 scenes, on one backend, on Windows.

Eight of the thirty-nine

Every image below was produced by the real Microsoft XNA 4.0 runtime, not by CNA and not by hand. CNA's D3D9 backend renders the same eight scenes and the diff must come back empty at --tolerance 0. They are reproduced throughout the tutorials where they illustrate the technique being taught.

These are deliberately austere scenes. A corpus like this is useful precisely because each frame isolates one piece of behaviour, so a diff that fails points at something specific. It is not a demonstration of what CNA can render — for that, see the demos.

What CI covers (and what it doesn't)

⚠

Be clear-eyed about this. There are three GitHub Actions workflows and only one of them is triggered automatically. Neither the full 4,845-case unit suite nor the 648 backend pixel tests are gated by CI on any platform. Everything else is verified by running ctest locally.

WorkflowTriggerWhat it actually runs
input-ci.yml Automatic ubuntu-24.04, gcc-14, a 5-way matrix (EasyGL, EasyGL with ASan+UBSan, SDL_Renderer, Vulkan, bgfx) — running only the input-labelled tests.
devices-tests.yml Path-filtered ubuntu-latest, fires only on changes under Microsoft/Devices/**.
d3d-windows-ci.yml Manual dispatch only windows-latest, native MSVC, D3D11 and D3D12, plus verification of 20 HLSL shaders against a real D3DCOMPILER_47.dll. Never runs unless someone clicks it.

Consequences, stated plainly:

  • No macOS, Android or Emscripten CI exists at all.
  • The full unit suite and every GPU pixel suite are run locally and by hand.
  • The full CnaTests suite cannot build on any Windows toolchain — roughly 10 files use POSIX ::setenv().
  • CNA_NOXNA and CNA_DEVICES both default to OFF, so the extended and device layers are not exercised by any current build or CI job.

Where there is no coverage at all

These are not "lightly tested." They have zero tests, and it is better that you hear it here.

  • Media — zero test files. That includes the FFmpeg-backed VideoPlayer and the SDL3_mixer-backed MediaPlayer, both of which are genuinely implemented but unverified by any automated check.
  • Storage — zero unit tests. The implementation is real std::filesystem IO with a hand-written glob matcher and correct player namespacing, but nothing asserts on it.
  • The Canvas backend — zero CTests. No automated test renders a single Canvas pixel.

Known open issues

Cross-backend correctness

IssueBackendStatus
SupportsCapability() is unreliable. The base implementation returns true for everything, and 8 of the 14 backends never override it (Ascii, D3D9, D3D11, D3D12, Headless, SDL_GPU, Software, WebGPU). WebGPU claims 5 capabilities it does not have; Software claims 6; Ascii reports the inverse of the backend it wraps. Most Open
DrawUserIndexedPrimitives corrupts geometry: CreateIndexBuffer32 is never overridden, so 32-bit indices are uploaded into a 16-bit buffer. Every other 3D backend implements this. bgfx Open
Draw offsets (startIndex / baseVertex) are ignored, so sub-range draws always start from 0. D3D11; bgfx outside the wireframe path Open
108 shader blobs exist, but only for GL, GLES, Vulkan and WebGPU — there are no D3D or Metal blobs, so 3D silently draws nothing on bgfx's default Windows and macOS renderers. bgfx Open
No scissor, no viewport, no stencil, no blend factor. MRT clears but never draws. D3D12 Open
Backbuffer-only forward renderer: no render targets at all, no MSAA, no cube or 3D textures, no queries, no instancing, non-functional stencil. WebGPU Experimental

API gaps that throw at runtime

Member Behaviour
Effect(GraphicsDevice&, byte[]) Throws NotImplementedException unconditionally. This is the compiled .fx bytecode constructor, and there is no MojoShader equivalent — see Deliberate deviations.
Texture::ValidateFormat Throws for all 25 surface formats other than SurfaceFormat::Color. Called from both Texture2D constructors, Texture3D and TextureCube, so float, half and HDR render targets are unavailable despite the enum listing them.
BoundingFrustum::Intersects(Ray) Throws NotImplementedException. Every other BoundingFrustum overload works.
The Media catalogue: MediaLibrary, MediaSource, Album, Artist, Genre, Playlist, Picture, PictureAlbum and their 6 collections All 14 types throw on every member. MediaLibrary::SavePicture(string, Stream*) is declared with no definition anywhere, which makes it a link error rather than a throw.
LeaderboardReader / LeaderboardWriter, all 3 Guide::ShowMessageBox entry points Throw. 16 of the 17 Guide::Show* methods are empty bodies; there is no service backend of any kind behind GamerServices.
ResourceContentManager, and the XNB EffectReader ResourceContentManager is the repository's only pure stub; EffectReader is registered as an always-throwing placeholder.
XMA and WMA audio Throw. Reverb is a no-op, and only the first PlayWave per track is honoured.

Silent wrong behaviour

  • TouchCollection reports IsReadOnly == true, but its mutators mutate instead of throwing.
  • ContentManager::Unload() clears its maps without disposing the assets.
  • The XNB reader registry is empty by default — RegisterAllBuiltInXnbReaders() must be called once at startup, by design.
  • None of the 17 PackedVector types implement ToString() or GetHashCode().

Deliberate deviations from XNA

These are not bugs and are not on a roadmap to be "fixed" — they are design decisions with real consequences for porting, so plan around them.

XNA does CNA does Why it matters
Ships custom shaders as compiled .fx bytecode Requires hand-written GLSL or SPIR-V through the CNA-only ShaderEffect class The six stock effects are implemented natively in C++ and work everywhere. Any custom HLSL shader must be rewritten by hand, per backend. This is the single biggest porting gap.
Constructs textures in any SurfaceFormat Constructs only SurfaceFormat::Color DXT and DDS assets load by CPU-decompressing to RGBA; HDR pipelines are not available through the XNA API.
Selects a graphics device at runtime Selects the backend at compile time via CNA_GRAPHICS_BACKEND One binary targets exactly one backend. There is no runtime fallback path — and full test coverage costs 14 build+test runs.
Discovers XNB type readers by reflection Requires one explicit RegisterAllBuiltInXnbReaders() call, and hand-registration for closed generics C++ has no reflection. The practical limit is that no custom user-defined type can be loaded from an .xnb: there is no ReflectiveReader.
Supports Xbox LIVE matchmaking (PlayerMatch, Ranked) Implements only SystemLink for real — genuine UDP over ENet with LAN broadcast discovery on port 61190 and measured RTT for QoS LAN multiplayer works across real machines. Internet matchmaking does not exist, and the other session types correctly no-op rather than pretending.
Runs GamerServices against a live service Ports FNA's no-op shim: full type shape, no persistence anywhere Your code compiles and runs; achievements, leaderboards and friends never persist. GamerServicesDispatcher::Initialize() fabricates four gamers named "Stub Gamer".

Reproducing these numbers yourself

Nothing here requires special access. Clone the repositories side by side and run the suite:

git clone https://github.com/openeggbert/cna.git
git clone https://github.com/openeggbert/sharp-runtime.git
git clone https://github.com/openeggbert/easy-gl.git
cd cna
git submodule update --init --recursive

cmake -S . -B build -DCNA_GRAPHICS_BACKEND=EASYGL
cmake --build build --target CNA CnaTests

# unit suite
./build/CnaTests

# everything registered with CTest (needs a GL context; use xvfb-run on a headless box)
ctest --test-dir build --output-on-failure

Swap EASYGL for any of SDL_RENDERER, BGFX, VULKAN, WEBGPU, HEADLESS, SOFTWARE, D3D11, D3D12, CANVAS, ASCII, DX3, D3D9 or SDL_GPU to reproduce the other rows of the backend table — one build each, because backend selection is a compile-time decision. The GPU tests are built from the programs in examples/: each renders a scene, reads the framebuffer back and asserts on pixels, so you can open any of them and see exactly what is being claimed.
