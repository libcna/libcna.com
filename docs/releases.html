⚠

Pre-1.0 software. CNA follows Semantic Versioning, but while the major version is 0 a minor release may change the public API, and neither the C++ API nor the experimental C ABI is promised stable before 1.0. Pin the tag or commit you build against, and rebuild C++ code whenever you move it.

ℹ

Two revisions, one version string. CNA’s latest release is 0.1.0 (tag v0.1.0). Most pages on this site document a later revision — the development snapshot c6dec91f on the next branch, 812 commits after that tag — and that snapshot still reports itself as 0.1.0. It is not a new release, has no tag and is described only by the [Unreleased] section of CNA’s changelog; see the snapshot section.

Browse the tagged source or its release changelog. For the first time the sibling checkouts CNA builds against are required rather than only recorded: cmake/DependencyVersions.cmake reads the version each sibling declares right after add_subdirectory and stops the configure step with the git checkout that fixes a mismatch (another minor line, a pre-release of the required version, or a checkout too old to declare a version); -DCNA_CHECK_DEPENDENCY_VERSIONS=OFF turns the error into a warning. The check compares versions, not commits.

CNA’s changelog records how the release was verified (CNA’s record, not repeated for this site): a cmake-build-multi tree on Debian 13 with GCC 14.2.0 configured with CNA: version 0.1.0 and the three accepted sibling versions, built with no errors, and ran 11,509 tests — 11,310 passed, 192 skipped by the tests’ own renderer conditions, and 7 failed: three failures that predated the release, three Wine-hosted XNA tests that need an X11 display the private runner does not give Wine, and one timing-sensitive test that passed three of three re-runs alone. Its known limitations also list renderer coverage as uneven by design and Content as having no general .xnb reader. At the release CNA had 14 renderer identities over 12 families and C ABI 0.46.0; both changed afterwards (below).

Because the version string did not change, CNA::getVersionString() cannot tell the release and the snapshot apart. If you need to know which one you built, record the Git commit (git rev-parse HEAD), not the product version. Where these docs say “this snapshot” they mean c6dec91f; where they say “0.1.0” or “the release” they mean the v0.1.0 tag, and “alpha.1” means the first tag.

ℹ

GitHub’s default branch is the 0.1.0 release. The repository’s default branch, main, points at the v0.1.0 commit. A plain git clone https://github.com/libcna/cna.git therefore gives you 0.1.0, and links of the form .../blob/main/... show 0.1.0 content. Link to the snapshot with a commit permalink such as .../tree/c6dec91fbf3ef5440f60e5329e4a4758b2d80c22; .../tree/next keeps moving.

What "6,302 changed paths" counts

The 6,302 figure comes from git diff --shortstat v0.1.0 c6dec91f with Git's default rename detection. That count treats each detected rename as one path. For a range this large, Git skips exhaustive rename detection and prints a diff.renameLimit warning. At these two commits Git's default name-status listing contains 788 additions, 3,840 deletions, 1,662 modifications and 12 renames. git diff --no-renames --name-status counts every rename as a deletion plus an addition and lists 6,314 records (800 / 3,852 / 1,662). Both figures are correct. The first counts files as Git pairs them; the second counts paths that appeared or disappeared. A comparison with another range should use the same flag and state it: from v0.1.0-alpha.1 to the snapshot the same commands give 10,670 (3,489 / 4,810 / 2,329 / 42 renames) and 10,712 records.

Which sharp-runtime revision goes with each tag

Since 0.1.0 the build checks the sibling's declared version: the root CMakeLists.txt adds whatever checkout CNA_SHARP_RUNTIME_ROOT points at (default ../sharp-runtime), and cmake/DependencyVersions.cmake accepts sharp-runtime 0.1.0 or a later 0.1.x; see which sharp-runtime a CNA build uses. The check compares versions, not commits, so it cannot tell sharp-runtime’s v0.1.0 tag from its later next commits, which still declare 0.1.0; the 0.1.0 changelog records the exact commit verified with the release (c20373bae5be1f02d1fe2fa33c4cbba8ad05e4a0, tag v0.1.0). For alpha.1 nothing was checked; the “Dependency pins” part of its changelog entry in CHANGELOG.md records the revision it was developed against:

sharp-runtime  625476d5b5fff5fa89f392c3c9af8638ff237692  (develop, 2026-08-19)

To rebuild alpha.1 against that recorded sibling, check the commit out in a separate worktree and point the option at it, instead of moving the sibling directory. The following commands are illustrative and were not executed:

git -C sharp-runtime worktree add ../sharp-runtime-alpha1 625476d5b5fff5fa89f392c3c9af8638ff237692
cmake -S cna -B cna/build -DCNA_SHARP_RUNTIME_ROOT="$PWD/sharp-runtime-alpha1"

The third-party submodules need no such step. The gitlinks of third_party/SDL, third_party/SDL_mixer, third_party/draco and vendor/googletest are identical at alpha.1, at 0.1.0 and at the snapshot; the snapshot no longer has the third_party/SDL_image submodule, which nothing in CNA used. So git submodule update --init selects the same third-party revisions for every row of the table above. This was checked with git ls-tree at the three commits.

Semantic Versioning before 1.0

CNA follows Semantic Versioning 2.0.0. The alpha.1 pre-release had lower precedence than the final 0.1.0 that followed it. During the 0.y.z phase, minor releases may change the API; pre-release identifiers communicate increasing release maturity, not an ABI guarantee. The snapshot above has not been given a new identifier: until a tag is created, the version 0.1.0 and the commit hash together are the only identity it has, and the version alone is ambiguous.

Reading the product version

The root project(CNA VERSION 0.1.0) and CNA_VERSION_PRERELEASE (empty since 0.1.0) are the build source of truth. CMake generates CNA/Version.hpp in the build tree.

#include "CNA/Version.hpp"

static_assert(CNA_VERSION_MAJOR == 0);
static_assert(CNA_VERSION_MINOR == 1);
static_assert(CNA_VERSION_PATCH == 0);
static_assert(!CNA::isPreReleaseVersion());

std::string_view version = CNA::getVersionString(); // "0.1.0"
std::string_view label = CNA::getVersionPreRelease(); // "" (alpha.1 built "alpha.1")

The generated header also provides CNA_VERSION_PRERELEASE, CNA_VERSION_STRING, and constexpr major/minor/patch accessors. Because it is generated, use the configured build's include directories rather than copying the template into a consumer. Both the 0.1.0 release and the development snapshot produce the values above; alpha.1 produced "0.1.0-alpha.1".

Product version versus C ABI

The experimental native C interface declares its own ABI identity, and that identity moves independently of the product version: 0.7.0 at the alpha.1 tag, 0.46.0 at the 0.1.0 release and 0.50.0 at snapshot c6dec91f, while the product version moved only once, from 0.1.0-alpha.1 to 0.1.0. Several of the minor steps in between were incompatible changes; the ABI history table is on the C API page.

At the alpha.1 tag the C library could not be produced at all: its C renderer table had 49 entries against the canonical 50, and a deliberate static_assert stopped compilation, so 0.7.0 identified a checked-in contract rather than a consumable binary. That blocker was resolved before 0.1.0. No CNA CI job builds the C library; CNA’s own campaigns build and test it locally (on Linux, and cross-compiled for Windows under Wine at this snapshot), and the C# binding CNA.NET builds and uses it on Linux. Treat both version numbers as identities of a source contract, not as evidence of a shipped binary.

#include <CNA/C/abi.h>

uint32_t runtime_abi = cna_get_abi_version();
if (runtime_abi != CNA_ABI_VERSION) {
    /* refuse or use an explicitly supported compatibility path */
}

See Experimental C API for the measured source scope, the package design, the version history and the boundary with external language bindings.

Exact source boundary for this site

The alpha.1 edition of this site audited changes from ae0be4b5211957efaef60f2f23627ae5a9ddda23 through the alpha.1 tag; later editions audited the ranges up to earlier development snapshots. This edition audits the range from the previous snapshot (c1c316b9, 22 commits before the v0.1.0 tag) to c6dec91fbf3ef5440f60e5329e4a4758b2d80c22, which includes the release commit. Claims come from the final tree's implementation, CMake configuration, headers, registries and tests. Repository plans and changelog entries are discovery aids, not overrides for contradictory code.

Consumer projects (the samples, demos, showcase games and language bindings) are evidence only for their own pinned revisions, not for any CNA revision described here.
