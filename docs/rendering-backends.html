CNA backend system - selection, tradeoffs, and implementation status

How backends work

CNA separates the game-facing rendering API from the underlying rendering implementation through a set of pure virtual interfaces. The central one is IGraphicsBackend (include/CNA/Internal/Backends/Common/IGraphicsBackend.hpp), which declares 132 virtual methods, 59 of them pure virtual. Game code never calls backend APIs directly.

A backend is selected at build time via the CMake variable CNA_GRAPHICS_BACKEND. Exactly one backend is compiled per build - there is no runtime dispatch and no runtime backend registry. Swapping backends requires a CMake reconfiguration and a rebuild. The default is EASYGL on Linux and Emscripten, and SDL_RENDERER everywhere else.

CNA ships 14 selectable backends: SDL_RENDERER, EASYGL, BGFX, VULKAN, WEBGPU, HEADLESS, SOFTWARE, D3D11, D3D12, CANVAS, ASCII, DX3, D3D9, and SDL_GPU. They differ enormously in maturity: one is production-ready, several are functional, three are partial or experimental, and one deliberately renders nothing at all. This page states which is which.

Two further source trees live under the backend directory but are not selectable backends: D3DCommon (966 lines of shared code plus roughly 40,000 lines of DXBC shader blobs - 34 HLSL sources compiled into 17 DXBC variants shared by D3D9, D3D11 and D3D12) and Common (1,044 lines - the interfaces themselves).

⚠

Backend age matters here. EasyGL, Vulkan, Bgfx and SDL_Renderer date from April 2026 (84-105 commits each). The other ten backends were all created within roughly the last two weeks - D3D9 on 2026-07-14; SDL_GPU, Dx3, Ascii and Canvas on 2026-07-15; WebGPU on 2026-07-12. Maturity tracks age very closely. Treat the newest backends as young code, not as finished alternatives to EasyGL.

Selecting a backend on the CMake line

Every backend is one CMake variable. The Windows-gated backends refuse to configure unless the target system is Windows; CANVAS refuses to configure outside an Emscripten target.

# EasyGL (2D + 3D; the most mature backend; needs the ../easy-gl sibling repo)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=EASYGL

# Vulkan (2D + 3D)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=VULKAN

# SDL_Renderer (2D only, widest portability)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=SDL_RENDERER

# SDL_GPU (2D + 3D; SDL3's GPU API, Vulkan device today)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=SDL_GPU

# bgfx (2D + 3D; GL/GLES/Vulkan/WebGPU renderers only)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=BGFX

# WebGPU (experimental; native wgpu-native)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=WEBGPU

# Software (CPU rasterizer; no GPU needed)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=SOFTWARE

# Headless (renders nothing by design; fast CI of game logic)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=HEADLESS

# Dx3 (2D only; DirectDraw-shaped, needs the ../free-direct sibling repo)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=DX3

# Ascii (2D only; quantizes the frame to a glyph/colour grid over SDL_Renderer)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=ASCII

# Direct3D 9 (Windows-only; the XNA-authenticity backend)
cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/mingw-w64.cmake -DCNA_GRAPHICS_BACKEND=D3D9

# Direct3D 11 (Windows-only)
cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/mingw-w64.cmake -DCNA_GRAPHICS_BACKEND=D3D11

# Direct3D 12 (Windows-only; partial - see its section below)
cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/mingw-w64.cmake -DCNA_GRAPHICS_BACKEND=D3D12

# Canvas (Emscripten-only; HTML5 2D canvas via EM_JS)
emcmake cmake -S . -B build -DCNA_GRAPHICS_BACKEND=CANVAS

How well each backend is verified

Because backend selection happens at compile time, each backend needs its own configure + build + test run - full coverage across all 14 means 14 separate runs. In total there are 648 backend integration and pixel tests registered as CTest, and they are distributed very unevenly. The numbers below are that distribution, and they are the single most useful honesty check on this page.

Across the project, roughly 436 of 559 example programs (78%) perform real GPU→CPU pixel readback with exact-match assertions (the default tolerance is 0), plus 17 golden PNG comparisons. That machinery is real - but as the table shows, it is not pointed evenly at all 14 backends. See Verification & Known Issues for the wider testing picture.

EasyGL backend

CMake flag: -DCNA_GRAPHICS_BACKEND=EASYGL  ·  5,305 lines  ·  239 CTest entries  ·  2D + 3D

EasyGL is CNA's production-ready backend and the default on Linux and Emscripten. It is built over the easy-gl sibling repository, a toolkit-independent OOP wrapper around OpenGL and OpenGL ES. Of the 132 virtuals on IGraphicsBackend, only 4 are left unoverridden here — the lowest of any backend.

Strengths:

  • 13 GLSL programs covering all 9 effect families
  • Both per-vertex and per-pixel lighting paths
  • Instancing, occlusion queries, anisotropic filtering, and fog
  • Real GL context-loss recovery
  • 239 CTest entries — more than any other backend by a wide margin

Limitations:

  • Requires the easy-gl sibling repository (which itself pulls in meta-gl)
  • OpenGL / OpenGL ES only — it does not reach Direct3D or Metal

Recommended for: essentially everything. If you have no specific reason to pick another backend, pick this one.

Vulkan backend

CMake flag: -DCNA_GRAPHICS_BACKEND=VULKAN  ·  10,506 lines  ·  138 CTest entries  ·  2D + 3D

The largest backend in the tree and the second-best verified. Rated functional, close to production.

Strengths:

  • 35 SPIR-V entry points across 8 effect paths
  • Device-queried depth formats rather than hardcoded assumptions
  • A real stencil pipeline-state object
  • MSAA resolve and mip blit cascades
  • 138 CTest entries

Limitations:

  • Multiple render targets are implemented as a proxy, not a native MRT path
  • 8 effect paths versus EasyGL's 9 effect families
  • Needs a Vulkan-capable GPU, driver and ICD

Recommended for: low-level GPU control on Vulkan-capable hardware, and as a strong second opinion when diagnosing an EasyGL rendering difference.

Direct3D 9 backend (Windows-only)

CMake flag: -DCNA_GRAPHICS_BACKEND=D3D9  ·  6,902 lines  ·  19 CTest entries  ·  2D + 3D  ·  created 2026-07-14

Rated functional, at the upper end. This backend has a purpose no other backend has: real XNA 4.0 ran on Direct3D 9, so D3D9 is the one backend that can be compared against the real thing pixel for pixel. It uniquely targets pixel-exact XNA 4.0 authenticity, and it is the backend the 39-scene XNA oracle corpus under tools/xna-oracle/ is diffed against at --tolerance 0.

Strengths:

  • 43 of 45 overrides are real implementations
  • 72 verified Shader Model 2 / Shader Model 3 bytecode blobs
  • Full device-lost and D3DPOOL_DEFAULT resource recovery
  • Caps-validated multiple render targets
  • The only path to pixel-exact XNA authenticity verification

Limitations:

  • Windows-only — the configure step is hard-gated
  • 2 of the 45 overrides are not real implementations
  • Only 19 CTest entries; most of its verification weight sits in the oracle corpus instead
  • Roughly two weeks old

Recommended for: XNA-fidelity work on Windows, and anywhere authentic XNA 4.0 pixel behaviour matters more than a modern API.

Direct3D 11 backend (Windows-only)

CMake flag: -DCNA_GRAPHICS_BACKEND=D3D11  ·  4,521 lines  ·  7 CTest entries  ·  2D + 3D

Rated functional. It shares the DXBC shader bytecode in D3DCommon with D3D9 and D3D12.

Strengths:

  • 5 state-object caches
  • Multiple render targets with deferred resolve
  • Instancing
  • Runtime shader compilation via D3DCompile

Limitations:

  • Windows-only — hard CMake gate
  • Only 7 CTest entries for 4,521 lines — verification is very thin relative to the surface area
  • Draw offsets (startIndex / baseVertex) are ignored on this backend
  • Never overrides SupportsCapability(), so it inherits the base class's unconditional true

Recommended for: a native Direct3D 11 path on Windows, with the draw-offset caveat above kept firmly in mind.

SDL_GPU backend

CMake flag: -DCNA_GRAPHICS_BACKEND=SDL_GPU  ·  6,683 lines  ·  21 CTest entries  ·  2D + 3D  ·  created 2026-07-15

Rated functional. Built on SDL3's GPU API with a deferred/retained design rather than an immediate one.

Strengths:

  • 23 SPIR-V shader blobs covering 9 effect families — the same breadth as EasyGL
  • Stencil support and MSAA resolve
  • A deferred/retained architecture that maps well onto modern explicit APIs

Limitations:

  • Vulkan is the only device backing it today — SDL_GPU's D3D and Metal devices are not in play
  • 21 CTest entries is thin for a 6,683-line 2D+3D backend
  • Never overrides SupportsCapability()
  • Roughly two weeks old

Recommended for: tracking SDL3's own GPU abstraction. Not yet a replacement for EasyGL or Vulkan.

Software backend (CPU rasterizer)

CMake flag: -DCNA_GRAPHICS_BACKEND=SOFTWARE  ·  1,739 lines  ·  6 CTest entries  ·  2D + 3D (narrow)

Rated functional within a deliberately narrow scope. This is a genuine CPU rasterizer, not a stub: it uses edge functions, a real Z-buffer, and perspective-correct 1/w attribute interpolation. No GPU, driver, or display server is involved at any point.

Strengths:

  • Real rasterization with a real depth buffer and correct perspective interpolation
  • Runs anywhere — no GPU needed at all
  • Deterministic, which makes it useful as a cross-backend reference

Limitations:

  • TriangleList only — no other primitive type
  • Only 6 CTest entries
  • Claims 6 capabilities it does not actually have via SupportsCapability()

Recommended for: deterministic GPU-free rendering checks and cross-backend diagnostics.

Dx3 backend (2D only)

CMake flag: -DCNA_GRAPHICS_BACKEND=DX3  ·  1,178 lines  ·  9 CTest entries  ·  2D only  ·  created 2026-07-15

Rated functional, with the best 2D fidelity of any backend. It is DirectDraw-shaped and fronts the free-direct sibling repository (a DirectX 3 / DirectDraw 2D subset implemented over SDL3). Despite the name, it is genuinely cross-platform — it is not Windows-gated.

Strengths:

  • A real CPU compositor with bilinear filtering
  • 4 distinct blend formulas
  • Real Wrap and Mirror texture addressing — a concrete win over SDL_Renderer
  • Small, readable surface (1,178 lines)

Limitations:

  • 2D only — no 3D path at all
  • Requires the free-direct sibling repository
  • Only 9 CTest entries
  • Roughly two weeks old

Recommended for: 2D work where texture-addressing fidelity matters.

Ascii backend (2D only)

CMake flag: -DCNA_GRAPHICS_BACKEND=ASCII  ·  753 lines  ·  6 CTest entries  ·  2D only  ·  created 2026-07-15

Rated functional. The smallest backend in the tree: a thin decorator over SDL_Renderer that quantizes the finished frame into a glyph and colour grid. Two runtime modes are selectable via the CNA_ASCII_MODE environment variable (BLACKWHITE or COLOR).

Strengths:

  • Tiny (753 lines) and inherits SDL_Renderer's behaviour underneath
  • Two genuinely different render modes, switchable at runtime without a rebuild

Limitations:

  • It is SDL-windowed, not a TTY backend — it does not render into your terminal
  • 2D only
  • Its SupportsCapability() reports the inverse of the backend it wraps
  • Only 6 CTest entries

Recommended for: stylised ASCII-art output over an existing 2D game.

SDL_Renderer backend (2D only)

CMake flag: -DCNA_GRAPHICS_BACKEND=SDL_RENDERER  ·  1,008 lines  ·  68 CTest entries  ·  2D only

Rated production-ready within its 2D scope, and the default backend on every platform other than Linux and Emscripten. It uses SDL3's built-in hardware-accelerated 2D renderer, so SDL picks the underlying API at runtime.

Strengths:

  • The only backend whose capability reporting is fully truthful — what SupportsCapability() says is what you get
  • No silent no-ops. 3D calls throw by design rather than quietly drawing nothing
  • 68 CTest entries against a small, deliberately bounded surface
  • Simplest integration — no dependency beyond SDL3

Limitations:

  • 2D only — every 3D entry point throws
  • Dx3 beats it on Wrap and Mirror texture addressing
  • Little control over the rendering pipeline; SDL chooses the driver

Recommended for: 2D games that want maximum portability and honest, predictable failure modes.

Canvas backend (Emscripten-only, 2D)

CMake flag: -DCNA_GRAPHICS_BACKEND=CANVAS  ·  1,177 lines  ·  0 CTest entries  ·  2D only  ·  created 2026-07-15

Rated mature but narrow, and unverified. It targets the HTML5 2D canvas directly through 11 EM_JS functions and is Emscripten-only.

⚠

No automated test anywhere in the project renders a single Canvas pixel. This backend has zero CTest entries. The code is careful and looks complete, but nothing mechanically proves it draws correctly. Verify it yourself before depending on it.

Strengths:

  • 11 EM_JS functions covering the 2D canvas surface directly — no GL layer in between
  • Careful un-premultiply and clipping handling, which is where naive canvas paths usually go wrong

Limitations:

  • Zero automated pixel verification
  • Emscripten-only — it cannot be selected on any native target
  • 2D only
  • Roughly two weeks old

Recommended for: web 2D output where you want to avoid WebGL entirely — with your own verification on top.

Direct3D 12 backend (Windows-only, partial)

CMake flag: -DCNA_GRAPHICS_BACKEND=D3D12  ·  6,819 lines  ·  1 CTest entry  ·  2D + 3D with gaps

Rated partial. The core is genuinely strong, but several ordinary rendering features simply are not there, and the automated verification is a single test.

⚠

One automated test covers 6,819 lines of code. D3D12 is the second-least-verified backend after Canvas. Do not read its solid architecture as evidence that it renders correctly.

Strengths:

  • Pipeline-state-object and root-signature caches
  • A real resource barrier tracker
  • Shares the D3DCommon DXBC shader bytecode with D3D9 and D3D11

Limitations:

  • No scissor rectangle
  • No viewport control
  • No stencil
  • No blend factor
  • MRT clears but never draws
  • Windows-only, and only 1 CTest entry
  • Never overrides SupportsCapability()

Recommended for: D3D12 development work on CNA itself. Not ready to carry a game.

bgfx backend (partial)

CMake flag: -DCNA_GRAPHICS_BACKEND=BGFX  ·  4,367 lines  ·  114 CTest entries  ·  2D + 3D

Rated partial — and this is the one case where a high test count is misleading, because the tests exercise the renderers that are wired up and cannot exercise the ones that are not.

⚠

The 108 shader blobs cover OpenGL, OpenGL ES, Vulkan and WebGPU only — there are no D3D or Metal variants. On bgfx's default renderer on Windows or macOS, 3D silently draws nothing. This is the opposite of SDL_Renderer's honest throw-on-unsupported behaviour, so it will look like a black screen rather than an error.

Strengths:

  • 108 shader blobs and 114 CTest entries on the renderers it does support
  • One CNA-side codebase across bgfx's GL, GLES, Vulkan and WebGPU renderers
  • bgfx is fetched by CMake automatically — no manual clone

Limitations:

  • No D3D or Metal shader variants — 3D silently renders nothing on bgfx's default Windows/macOS renderer
  • DrawUserIndexedPrimitives corrupts geometry. The backend never overrides CreateIndexBuffer32, so 32-bit indices are uploaded into a 16-bit buffer. Every other 3D backend implements this correctly
  • Draw offsets (startIndex / baseVertex) are ignored outside the wireframe path
  • bgfx.cmake is fetched at GIT_TAG master — it is the project's only unpinned dependency

Recommended for: GL/GLES/Vulkan/WebGPU targets where you specifically want bgfx in the stack. Not a route to Windows D3D or macOS Metal today.

WebGPU backend (experimental)

CMake flag: -DCNA_GRAPHICS_BACKEND=WEBGPU  ·  7,110 lines  ·  14 CTest entries  ·  2D + early 3D  ·  created 2026-07-12

Rated partial / experimental. It targets the native wgpu-native implementation (pinned to v29.0.1.1, downloaded by CMake by default). Architecturally it is a backbuffer-only forward renderer, and that single design fact explains most of its gaps.

Strengths:

  • A working 2D path plus an early 3D path over a modern explicit API
  • 7,110 lines of real implementation, not a skeleton

Limitations:

  • No render targets at all — it renders only to the backbuffer
  • No MSAA
  • No cube textures and no 3D textures
  • No queries and no instancing
  • Stencil is non-functional
  • It claims 5 capabilities it does not have via SupportsCapability()
  • Only 14 CTest entries

Recommended for: experimenting with CNA on WebGPU. Not a 3D alternative to EasyGL or Vulkan.

Headless backend (test harness)

CMake flag: -DCNA_GRAPHICS_BACKEND=HEADLESS  ·  1,545 lines  ·  7 CTest entries  ·  renders nothing

Headless is explicitly a test harness, not a renderer. It renders nothing, deliberately. ReadBackbuffer returns the last clear colour and discards the x and y coordinates entirely. It exists so game logic can be exercised quickly in CI with no GPU, no window, and no display server.

Strengths:

  • Runs in any container — no GPU, driver or display server needed
  • Fast, because it skips rendering entirely

Limitations:

  • It proves nothing about pixel correctness — by design
  • ReadBackbuffer ignores the requested coordinates and reports the last clear colour
  • Never overrides SupportsCapability()

Recommended for: fast CI runs of game logic where rendering output is irrelevant.

Known cross-backend caveats

These are verified, cross-cutting issues. They apply regardless of which backend you pick, so read them before choosing.

SupportsCapability() is not reliable

The base-class implementation returns true for everything, and 8 of the 14 backends never override it — Ascii, D3D11, D3D12, D3D9, Headless, SDL_GPU and Software. Those seven therefore report that they support every capability CNA can name. Of the backends that do override it, WebGPU claims 5 capabilities it lacks, Software claims 6, and Ascii reports the inverse of the backend it wraps.

SDL_Renderer is the only backend whose capability reporting is fully truthful. Do not branch game logic on SupportsCapability() and expect a correct answer on an arbitrary backend.

Draw offsets are silently ignored on two backends

startIndex and baseVertex are ignored on D3D11, and on Bgfx outside the wireframe path. Draws that rely on offsetting into a shared vertex or index buffer will render the wrong geometry on those backends, without an error.

Bgfx corrupts 32-bit indexed user primitives

DrawUserIndexedPrimitives corrupts geometry on Bgfx: the backend never overrides CreateIndexBuffer32, so 32-bit indices are uploaded into a 16-bit buffer. Every other 3D backend implements this correctly.

Ten of the fourteen backends are about two weeks old

Only EasyGL, Vulkan, Bgfx and SDL_Renderer date from April 2026 (84-105 commits each). D3D9 (2026-07-14), SDL_GPU, Dx3, Ascii and Canvas (all 2026-07-15) and WebGPU (2026-07-12) are new. Maturity tracks age closely, and the CTest distribution above reflects it. A backend existing is not the same as a backend being exercised.

Verification is thin in two specific places

Worth restating plainly: Canvas has zero automated pixel tests — no test in the project renders a Canvas pixel — and D3D12 has exactly one CTest entry across 6,819 lines. Both may well work. Neither is mechanically proven to.

Which backend should I choose?

💡

Default answer: EASYGL. It is the only production-ready backend, it covers 2D and 3D, and it carries 239 of the project's 648 backend tests. Choose something else only for a specific reason.

💡

For 2D-only games wanting maximum portability: SDL_RENDERER. It is production-ready within its 2D scope, it is honest about what it supports, and it throws rather than silently no-op'ing on 3D.

💡

For low-level GPU control: VULKAN, the second-best-verified backend at 138 tests.

💡

For XNA fidelity on Windows: D3D9. It is the only backend targeting pixel-exact XNA 4.0 authenticity, and the only one diffed against the real XNA oracle corpus.

💡

For CI with no GPU: HEADLESS if you only need game logic exercised, or SOFTWARE if you need real pixels (TriangleList only).

💡

For the web: EASYGL via Emscripten is the well-tested path. CANVAS is the Emscripten-only 2D-canvas alternative, but it has zero automated pixel tests — verify it yourself first.

⚠

Think twice before choosing D3D12, CANVAS, or BGFX for 3D on Windows/macOS. D3D12 lacks scissor, viewport, stencil and blend factor; Canvas is unverified; and Bgfx has no D3D or Metal shader variants, so 3D silently draws nothing on bgfx's default Windows and macOS renderer.
