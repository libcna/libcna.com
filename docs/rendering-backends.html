CNA backend system - selection, tradeoffs, and implementation status

How backends work

CNA separates the game-facing rendering API from the underlying rendering implementation through a set of pure virtual interfaces (IGraphicsBackend, ISpriteBatchBackend, ITextureBackend). Game code never calls backend APIs directly.

A backend is selected at build time via the CMake variable CNA_GRAPHICS_BACKEND. Only one backend is compiled per build - there is no runtime dispatch overhead. Swapping backends requires only a CMake reconfiguration.

CNA now supports nine backends in total: the four established general-purpose backends below (SDL_Renderer, EasyGL, bgfx, Vulkan), an experimental native WebGPU backend, two CI/testing-only backends that need no GPU at all (Headless, Software), and two native Windows Direct3D backends (D3D11, D3D12).

# SDL_Renderer (2D, all platforms, simplest)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=SDL_RENDERER

# EasyGL (2D + full 3D; Linux, Emscripten/WebGL 2)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=EASYGL

# bgfx (2D + full 3D, multi-API)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=BGFX

# Vulkan (2D + full 3D, all stock effects)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=VULKAN

# WebGPU (experimental; native wgpu-native, 2D + early 3D)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=WEBGPU

# Headless (CI/testing only; no GPU or window, renders nothing by design)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=HEADLESS

# Software (CPU rasterizer; deterministic pixel tests, no GPU needed)
cmake -S . -B build -DCNA_GRAPHICS_BACKEND=SOFTWARE

# Direct3D 11 (Windows-only; needs the MinGW-w64 toolchain file)
cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/mingw-w64.cmake -DCNA_GRAPHICS_BACKEND=D3D11

# Direct3D 12 (Windows-only, off-screen only; needs the MinGW-w64 toolchain file)
cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/mingw-w64.cmake -DCNA_GRAPHICS_BACKEND=D3D12

How well each backend is verified

Each backend gets its own full test run, because backend selection happens at compile time. These are GPU pixel-readback tests: they render a scene on a real graphics context, read the framebuffer back, and assert on actual pixel values.

BackendGPU pixel testsBackend sourceOpen failures
EASYGL 188 / 190 ~4,100 lines, 9 GLSL ES 3.0 programs Two-attachment MRT; ReferenceStencil override
VULKAN 125 / 126 ~9,300 lines, 23 GLSL→SPIR-V shaders RasterizerState.DepthBias
BGFX 102 / 104 ~3,900 lines, 21 .sc shaders RenderTargetCube depth attachment; MSAA resolve (environmental)
SDL_RENDERER 67 / 67 ~1,000 lines, no shaders None — 2D-only by design

Every failure above is named and tracked; see Verification & Known Issues for what each one actually breaks.

Its feasibility has been spiked and proven — Microsoft's own XNA 4.0 stock-effect HLSL shaders compile to real D3D9 bytecode, and real XNA 4.0 itself has been made to run as a verification oracle — but building it awaits a project-owner go-ahead. See the Roadmap for details.

SDL_Renderer backend

CMake flag: -DCNA_GRAPHICS_BACKEND=SDL_RENDERER

The SDL_Renderer backend uses SDL3's built-in hardware-accelerated 2D renderer. SDL_Renderer targets OpenGL, OpenGL ES, Direct3D, Direct3D 11, Direct3D 12, Metal, or software rendering - depending on the platform and driver availability. SDL chooses automatically at runtime.

Advantages:

  • Simplest integration - SDL handles all driver selection
  • Widest platform portability, including mobile and web (via Emscripten)
  • No additional dependencies beyond SDL3
  • Good for straightforward 2D workflows

Limitations:

  • Less control over rendering pipeline and shaders compared to raw OpenGL or bgfx
  • Fixed-function pipeline - custom shaders require SDL3's shader support (still maturing)

Recommended for: Getting started, Windows development, broad platform portability, and 2D-focused applications.

EasyGL (OpenGL ES 3.0) backend

CMake flag: -DCNA_GRAPHICS_BACKEND=EASYGL

The EasyGL backend is a custom shader-driven rendering path using the easy-gl helper library over OpenGL ES 3.0. It supports full 2D and 3D rendering and compiles to WebGL 2 via Emscripten. The House 3D Demo runs live in the browser using this backend.

Advantages:

  • Full 2D and 3D rendering pipeline — BasicEffect, SkinnedEffect, depth test, blend, cull mode
  • Four shader variants by vertex stride — handles all VertexPosition* types
  • Compiles to WebGL 2 via Emscripten — enables browser-based demos today
  • Explicit OpenGL ES 3.0 usage — good for learning and debugging

Limitations:

  • Requires the easy-gl sibling repository
  • OpenGL ES 3.0 only — not Metal, DirectX, or Vulkan natively
  • FillMode::WireFrame silently ignored (OpenGL ES 3.0 has no glPolygonMode)

Recommended for: Linux development, Emscripten/web targets, 3D rendering, and custom shader work.

bgfx backend

CMake flag: -DCNA_GRAPHICS_BACKEND=BGFX

The bgfx backend integrates bgfx - a cross-platform rendering library that supports Vulkan, Metal, DirectX 9/11/12, OpenGL, OpenGL ES, and WebGL from a single API. bgfx is fetched via CMake FetchContent at build time - no manual library installation is required.

Current state: Reached full 2D+3D pixel-verified parity with EasyGL and Vulkan as of this project's Phase 72. Working: all five stock effects (BasicEffect, AlphaTestEffect, DualTextureEffect, EnvironmentMapEffect, SkinnedEffect), RenderTarget2D/Cube (MSAA, mip, depth), Texture2D/3D/Cube SetData/GetData (including blit-based GetBackBufferData readback), all four state classes. Not implemented: custom ShaderEffect source compilation (CreateEffectBackend returns nullptr — bgfx wants precompiled binary shaders). Unverified in this project's sandbox: OcclusionQuery Begin/End wiring is real, but visible-vs-occluded pixel-count correctness can't be pixel-verified under this sandbox's software GL 2.1 driver.

Advantages:

  • Same backend code targets Vulkan, Metal, DirectX, and OpenGL
  • High-performance, production-proven rendering library
  • Good mobile and console potential
  • Future benefit: bgfx abstracts Vulkan, Metal, DX11/12, and OpenGL — enabling platforms CNA does not otherwise reach (macOS Metal, DirectX 12)

Limitations:

  • Custom ShaderEffect source compilation is not supported — bgfx requires precompiled binary shaders, and CreateEffectBackend returns nullptr
  • OcclusionQuery correctness can't be pixel-verified in this project's CI sandbox (software GL 2.1 driver, no dedicated-view architecture yet)
  • More complex integration than SDL_RENDERER
  • Requires internet access during CMake configure for FetchContent
  • FillMode::WireFrame is not available on this backend

Recommended for: Multi-API portability goals; full 2D and 3D rendering at parity with EasyGL/Vulkan today, aside from custom shader source compilation.

Vulkan backend

CMake flag: -DCNA_GRAPHICS_BACKEND=VULKAN

The Vulkan backend is a fully featured direct-Vulkan implementation and CNA's second-most mature backend after EasyGL. It uses a dedicated 2D pipeline with push constants for SpriteBatch, and a complete 3D pipeline supporting all five stock effects, all pixel-tested. Instanced rendering (VK_VERTEX_INPUT_RATE_INSTANCE), render targets (RenderTarget2D, RenderTargetCube, MRT), MSAA 4x with subpass auto-resolve, per-slot sampler state (16 slots), GetBackBufferData pixel readback, Texture3D/TextureCube upload, custom ShaderEffect (SPIR-V, 128-byte push constants, std140), DepthStencilState compare-op and stencil ops, debug labels, and FillMode::WireFrame (VK_POLYGON_MODE_LINE) are all implemented.

Two gaps that older documentation still lists are now closed. BlendState has a real per-Blend/BlendFunction mapping covering all 13 XNA blend factors, including BlendFactor and InverseBlendFactor. OcclusionQuery now performs real per-draw-call correlation. Both landed in code after the write-ups that describe them as blocked; if you read otherwise elsewhere, that source is out of date.

Current state: Full 2D and 3D pipeline, all five stock effects pixel-tested, custom SPIR-V shaders supported. 125 of 126 GPU pixel tests pass; the one failure is RasterizerState.DepthBias.

Recommended for: Production 3D applications on Vulkan-capable desktop and mobile hardware, and anywhere you want low-level GPU control with a near-complete XNA effects pipeline.

WebGPU backend (experimental)

CMake flag: -DCNA_GRAPHICS_BACKEND=WEBGPU

The WebGPU backend is CNA's fifth graphics backend, activated by the project owner on 2026-07-12. It targets the native wgpu-native implementation (pinned to v29.0.1.1, auto-downloaded by CMake by default) rather than a browser — this is a native desktop backend, not browser/Emscripten WebGPU.

Current state: the native 2D baseline is genuinely verified: device/surface setup, resize and present-mode handling, RGBA8 Texture2D upload, a full WGSL SpriteBatch pipeline (tint, source/destination rect, rotation, flips, linear/nearest filtering, wrap/clamp/mirror sampling), and real GetBackBufferData() pixel readback are all implemented and verified — twice: once via CNA's own demo, and independently against a real third-party XNA-style game (../mobile-eggbert) that reached its main menu and played a full animated cutscene with pixel-correct rendering. A first real 3D draw path (DrawColoredPrimitives, genuinely depth-tested, not "last draw wins") also exists.

Advantages:

  • Modern explicit GPU API with a native (non-browser) implementation
  • 2D SpriteBatch rendering is production-quality and independently verified against a real game
  • Genuine depth-tested 3D draw path already proven

Limitations:

  • Stock effects (BasicEffect real lighting/texture dispatch, SkinnedEffect, etc.) are not yet implemented — only an unlit/untextured 3D draw path exists so far
  • No render targets, cube/3D textures, MSAA, or instancing yet
  • Texture2D.GetData() (arbitrary texture readback), full BlendState/RasterizerState/stencil-op mapping, and custom WGSL effects are all open
  • Browser/Emscripten WebGPU is not implemented — native desktop only

Recommended for: experimenting with CNA's WebGPU path today for 2D games; not yet a 3D-parity alternative to EasyGL/Vulkan/Bgfx.

Headless backend (CI / testing only)

CMake flag: -DCNA_GRAPHICS_BACKEND=HEADLESS

The Headless backend is a CI/testing-only backend, verified 2026-07-13. It never touches SDL's video subsystem, OpenGL, Vulkan, or any GPU library — no window is created and no GPU context exists. It renders nothing by design: ReadBackbuffer() simply reports the last Clear() color for every pixel. In place of real rendering it does real bookkeeping — argument validation, resource-lifecycle tracking, and draw-call/state-change counters — so a test can assert "this code path ran, with these arguments, this many times, and nothing leaked," fast and without a display server.

A runtime strictness dial (the CNA_HEADLESS_MODE environment variable) selects between Fast (counters only), Validation (default — throws on the kind of misuse a real backend would reject), and Trace (adds a structured call log, debug labels, and trace-log diffing between two runs).

Advantages:

  • No GPU, window, or display server needed at all — runs in any CI container
  • Fast: skips real rendering entirely, just validates and counts
  • Validated against a real third-party game (../mobile-eggbert), running 20+ seconds with zero crashes or exceptions

Limitations:

  • Proves nothing about pixel correctness — it is a logic-testing harness, not a rendering backend
  • No disposed-state-object validation (a real interface constraint, not a gap expected to close)

Recommended for: fast CI tests of game logic (draw-call counts, resource lifetime, argument validation) where no GPU or display server is available.

Software backend (CPU rasterizer)

CMake flag: -DCNA_GRAPHICS_BACKEND=SOFTWARE

The Software backend is a CPU-only rasterizer, verified 2026-07-13. Like Headless it never touches SDL's video subsystem, OpenGL, Vulkan, or any GPU library — but unlike Headless it actually rasterizes real triangles into a CPU-owned RGBA8 framebuffer, with a real edge-function rasterizer, perspective-correct attribute interpolation, and a real per-pixel depth test. GetBackBufferData() returns genuinely correct pixels, with no GPU, window, or display server involved at any point.

Verified 2026-07-13 against EasyGL on a canonical unlit-triangle scene via a dedicated cross-backend diagnostic tool: max per-channel pixel difference of 1 (effectively identical, ordinary rounding noise).

Advantages:

  • Deterministic pixel tests with no GPU driver, display server, or Xvfb needed at all
  • Works in server/CI environments with no GPU whatsoever
  • A fast, portable, independently-implemented reference for basic XNA primitive/effect rendering behavior

Limitations:

  • TriangleList only — other primitive types throw a clear error
  • No per-light diffuse lighting or fog (DualTextureEffect/EnvironmentMapEffect/SkinnedEffect are supported, minus lighting)
  • No MRT, MSAA, mipmapping, Texture3D, or RenderTargetCube
  • Only two blend modes distinguished (Opaque vs. one simplified "over" composite for everything else)
  • Present() is a no-op — there is no way to view a Software-rendered frame on screen in its current form
  • Not a real-time backend — no SIMD, multithreading, or tiling; correctness and determinism are the goals, not speed

Recommended for: deterministic, GPU-free pixel tests, headless CI environments with no GPU at all, and cross-backend rendering diagnostics.

Direct3D 11 backend (Windows-only)

CMake flags: -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/mingw-w64.cmake -DCNA_GRAPHICS_BACKEND=D3D11

The D3D11 backend is CNA's first native Direct3D backend — as opposed to Bgfx, which can select a D3D11/D3D12 renderer internally on Windows, but that is bgfx's own abstraction rather than a CNA-level one. It gives XNA/FNA-style games a dependency-free native Windows path. Verified 2026-07-14: hard-gated to CMAKE_SYSTEM_NAME=Windows at configure time, cross-compiled from Linux with MinGW-w64, and verified running through Wine + DXVK on a real GPU — 6 CTest binaries, 96+ checks, all passing.

Working and pixel-verified: all 10 stock HLSL shader variants (BasicEffect/AlphaTestEffect/DualTextureEffect/EnvironmentMapEffect/SkinnedEffect, each colored/textured/lit variant, plus sprite/instanced), textures and render targets (MRT, 4× MSAA, occlusion queries), all four state-object classes (BlendState/DepthStencilState/RasterizerState/SamplerState), a real SpriteBatch (rotation/scale/crop/flip, custom Effect support, TextureAddressMode Wrap/Mirror), and a runtime-D3DCompile()-backed custom ShaderEffect path.

Advantages:

  • Native Direct3D 11, not a translation layer — direct control over the exact calls made
  • Broad, pixel-verified coverage across all 10 stock shader variants and all 4 state-object classes
  • Real SpriteBatch plus a working, Wine-verified swap chain and Present()

Limitations:

  • Windows-only — the CMake configure step fails fast with a clear error on native Linux/macOS
  • Not yet verified on real Windows hardware. Every check above ran through Wine+DXVK on this project's own Linux dev machine's real GPU — real DXGI present/tearing behavior, full device-lost recovery, and WARP software-rasterizer fallback all still need a real Windows machine
  • Specular highlights, multi-light discrimination, and mip chains beyond level 0 are implemented but not yet independently pixel-tested

Recommended for: teams that want a dependency-free native Direct3D 11 path for Windows once real-hardware verification lands; today, best used for local Wine+DXVK development and CI.

Direct3D 12 backend (Windows-only, off-screen)

CMake flags: -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/mingw-w64.cmake -DCNA_GRAPHICS_BACKEND=D3D12

The D3D12 backend is CNA's second native Direct3D backend, built directly on D3D11's own experience — it shares D3D11's HLSL/DXBC shader bytecode, format/state mapping tables, and constant-buffer layouts. Verified 2026-07-14 the same way as D3D11 (Windows-only hard gate, MinGW-w64 cross-compiled) but through Wine + vkd3d-proton instead of DXVK. D3D12_Smoke CTest: 80/80 checks, all passing.

Working and pixel-verified, off-screen: real command queues, descriptor heaps, command lists, fences with genuine 2-frame back-pressure, a real per-resource barrier-transition tracker, pipeline state objects, root signatures, vertex/index buffers, 2D and cube textures, the same 10 stock HLSL shader variants D3D11 uses, a real SpriteBatch, and a real, functionally-proven device-removed recovery path.

Off-screen only — the most significant open gap: swap-chain creation is implemented for real but crashes under this dev loop, a genuine architecture mismatch between the system dxgi.dll and vkd3d-proton's own d3d12.dll — a real Wine/vkd3d-proton environment issue, not a CNA bug. Every proof for this backend stays off-screen for that reason.

Advantages:

  • Real, off-screen-pixel-verified D3D12 device/command/PSO/root-signature pipeline, reusing D3D11's proven HLSL shaders
  • Real, functionally-proven device-removed recovery (full teardown/rebuild of every device-lifetime resource)

Limitations:

  • Windows-only, same hard CMake gate as D3D11, and not yet verified on real Windows hardware
  • Off-screen only — no working swap chain/Present() under this dev loop
  • No runtime-settable BlendState/DepthStencilState/RasterizerState (baked into hardcoded PSOs); no per-slot SamplerState (hardcoded static sampler)
  • No public render-target backend (RenderTarget2D/RenderTargetCube/MRT don't work via the real XNA API yet), no Texture3D, no occlusion queries

Recommended for: off-screen D3D12 rendering/CI work today; not yet usable for an on-screen Windows game until swap-chain presentation and real-hardware verification land.

CI & platform-specific backend verification

Five more backends exist for purposes other than general cross-platform 2D/3D gameplay rendering — CI logic testing, deterministic GPU-free pixel testing, native Windows Direct3D, and an experimental native WebGPU path. Each is verified differently from the four backends above, so they are not part of the shared "490 GPU pixel tests across its four established backends" figure quoted elsewhere on this site:

BackendVerification methodNotes
HEADLESS Dedicated Headless_* CTest suite (bookkeeping/argument-validation/trace-log checks) plus a real third-party game run 20+ seconds with zero crashes Renders nothing by design — proves call sequencing and resource lifetime, not pixels
SOFTWARE Dedicated rasterizer/effects CTests plus a cross-backend pixel-diff tool run against EasyGL (max per-channel difference of 1 on a canonical scene) Real CPU-rendered pixels, no GPU — TriangleList only, no lighting/fog in v1

FillMode::WireFrame availability

FillMode::WireFrame (wireframe rendering via RasterizerState) is available on the Vulkan backend only. It is not available on EasyGL (OpenGL ES 3.0 does not support glPolygonMode), SDL_RENDERER, or BGFX.

BackendFillMode::WireFrameNotes
VULKAN Available Implemented via VK_POLYGON_MODE_LINE
EASYGL Not available OpenGL ES 3.0 has no glPolygonMode; silently ignored
SDL_RENDERER Not available SDL_Renderer has no polygon mode control
BGFX Not available Not implemented in the bgfx backend

Which backend should I choose?

💡

For getting started or Windows: Use SDL_RENDERER. It is the simplest, most portable 2D option.

💡

For 3D rendering or Emscripten/web: Use EASYGL. It provides full 2D and 3D, custom shaders, and compiles to WebGL 2 in the browser.

💡

For multi-API portability: Use BGFX. It reached full 2D+3D pixel-verified parity with EasyGL/Vulkan as of Phase 72, and enables Vulkan, Metal, and DirectX from one CNA build (only custom ShaderEffect source compilation is still unsupported).

💡

For Vulkan production use: The VULKAN backend has all five stock effects (pixel-tested), instancing, MSAA 4x, MRT, custom SPIR-V shaders, real per-factor BlendState and working OcclusionQuery. Choose it when you need full low-level GPU control on Vulkan-capable hardware.

💡

For CI logic tests with no GPU at all: Use HEADLESS. It renders nothing but validates every draw call, tracks resource lifetime, and runs in any container with no display server.

💡

For deterministic, GPU-free pixel tests: Use SOFTWARE. It's a real CPU rasterizer — genuinely correct pixels with no GPU, driver, or Xvfb needed, though it's not a real-time backend.

💡

For native Windows Direct3D: Use D3D11 for a dependency-free, pixel-verified native Direct3D 11 path (Wine+DXVK-verified; real Windows hardware verification still open), or D3D12 if you specifically need off-screen D3D12 rendering today (swap-chain presentation isn't working yet under this project's Wine+vkd3d-proton dev loop).

💡

For experimenting with WebGPU: Use WEBGPU. Its native 2D SpriteBatch path is genuinely verified against a real game; 3D stock effects and render targets are still early.
