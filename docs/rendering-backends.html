How renderers work

CNA separates the game-facing rendering API from the underlying graphics implementation with a pure virtual interface, IGraphicsRenderer. Game code never calls a graphics API directly, and never names a renderer.

The compact default is a single-renderer build. Choose its renderer at configure time with either form below; do not mix the forms:

# Long form: name the renderer
cmake -S . -B build -DCNA_GRAPHICS_RENDERER=SDL_GPU

# Option form: exactly one CNA_RENDERER_<NAME> may be ON
cmake -S . -B build -DCNA_RENDERER_SDL_GPU=ON

CNA exposes 10 public renderer identities, implemented by 8 families. The three GL identities below (OPENGLES3, OPENGL33, WEBGL2) share one family, EasyGL; none of the public identities is an alias. The defaults are WEBGL2 under Emscripten, SDL_GPU on Windows, macOS and iOS, and OPENGLES3 everywhere else (Linux, Android and the BSDs) (RendererIdentityDefault.cmake).

Every identity has a stable, sparse C ABI value (OPENGLES3 is 3, FNA3D is 43) that is never renumbered; the values in between that no current identity uses are permanently reserved, and the next new identity would take 52. The CMake list, the C++ enum, the CMake registry map, the C header and the C API table are held together by scripts/check_renderer_identities.py, which CTest runs as RendererIdentityRegistry. C++ enum ordinals, by contrast, are dense (GraphicsRendererType::OpenGLES3 is 0 and Fna3d is 9) and are not a stable contract: never convert between an ordinal and a C ABI value.

A name outside the 10 given to CNA_GRAPHICS_RENDERER or as a member of CNA_GRAPHICS_RENDERERS — a misspelling, a lower-case spelling, or an identity that an older document or build script mentions but this snapshot does not provide — stops the configure step with a FATAL_ERROR. A retired name is refused by name, with its reserved C ABI value, on every route: the CMake options, the CNA_GRAPHICS_RENDERER environment variable, GraphicsRendererSelection::SetPreferred and the C API’s by-name route. The check runs first, before SDL or any dependency is configured. There are no aliases, and CMake matches the public names case-sensitively (sdl_gpu is an unknown name; SDL_GPU is not). One route is not covered: a CNA_RENDERER_<X>=ON switch whose name is neither a public nor a retired identity (-DCNA_RENDERER_D3D9=ON, -DCNA_RENDERER_EASYGL=ON, a typo) is a cache entry nothing reads, so the configure does not fail and builds the platform default renderer (at most CMake's generic warning about a manually specified variable that was not used). In old scripts name the renderer with CNA_GRAPHICS_RENDERER, and read the CNA: Using <X> graphics renderer line of the configure log.

💡

Which CNA does this page describe? CNA snapshot c6dec91f (24 October 2026) on branch next, 812 commits after the v0.1.0 release tag; its version string is still 0.1.0. A plain git clone https://github.com/libcna/cna.git gives the 0.1.0 release, whose renderer set was larger; use git clone -b next and check out c6dec91f for what is documented here, with sharp-runtime on its next branch and easy-gl and meta-gl at v0.1.1 and v0.4.1 (see Releases & Versioning).

💡

The Windows, macOS and iOS default is SDL_GPU, and it is not qualified there yet. SDL_GPU is CNA’s modern native path: CNA maps XNA 4.0 onto SDL’s GPU API, and SDL picks its Vulkan, Direct3D 12 or Metal GPU driver underneath. At this snapshot it is validated on Linux (Vulkan) and, cross-compiled, under Wine with vkd3d-proton (Direct3D 12). No native Windows run, no re-run on Apple hardware and no iOS build of it exists yet; CI has macOS and iOS legs for it, the macOS one gating (CNA’s handoff.md §5.2). On Windows, DIRECTX9 is the alternative; on macOS and iOS, SOFTWARE is the evidenced fallback.

⚠

10 identities are not 10 equally complete renderers. They differ in scope, dependencies, platform gates and verification. Treat an identity as a named implementation contract, not as a promise of feature parity with every other row — the capability matrix and the declared maturity table show the differences.

Multi-renderer builds and runtime selection

This snapshot supports an opt-in build mode that links several compatible renderer families into one binary. CNA_GRAPHICS_RENDERERS is a semicolon-separated set; CNA_GRAPHICS_RENDERER remains the default and must be a member of that set (otherwise the configure step fails; nothing is silently substituted). Omitting the plural option keeps the ordinary single-renderer build. Duplicates are removed, the default is moved first, and the configure log prints CNA: renderer set -- <list> (default: <X>).

cmake -S . -B build-multi -G Ninja \
  -DCNA_GRAPHICS_RENDERER=HEADLESS \
  -DCNA_GRAPHICS_RENDERERS="HEADLESS;SOFTWARE;STUB"

Before the first GraphicsDevice is created, CNA::GraphicsRendererSelection resolves the renderer in this order: an explicit SetPreferred() call, the CNA_GRAPHICS_RENDERER environment variable, then the compile-time default. In an Emscripten build the page property Module.cnaPreferredRenderer is consulted at the environment variable's precedence (a real environment variable wins over it), and the exported Module._cna_set_preferred_renderer(name) behaves like an explicit SetPreferred(). A name that is unknown, retired or not compiled in throws; CNA never substitutes silently.

#include <array>
#include "CNA/GraphicsRendererSelection.hpp"

using CNA::GraphicsRendererSelection;
using CNA::GraphicsRendererType;

GraphicsRendererSelection::SetPreferred(GraphicsRendererType::SdlGpu);   // or SetPreferred("SDL_GPU")

constexpr std::array chain{GraphicsRendererType::OpenGLES3,
                           GraphicsRendererType::Software};
GraphicsRendererSelection::SetFallbackChain(chain);                      // opt-in

MyGame game;
game.Run();

On a native build the environment route is CNA_GRAPHICS_RENDERER=SDL_GPU ./mygame; in a page it is var Module = { cnaPreferredRenderer: "WEBGPU" };. Names are case-insensitive at run time (unlike CMake).

Fallback is off by default. SetFallbackChain() (which takes a std::span, so pass an array rather than a bare brace list) or EnableAutomaticFallback(true) opts in; every skipped renderer is recorded in GetFallbackHistory() with a reason (NotCompiledIn, ProbeUnavailable, InitializationFailed, WindowKindConflict). Automatic fallback tries the renderers that show a picture first and HEADLESS only after them. GetSelected() is the renderer CNA will try, GetActive() is what actually started, and GraphicsDevice::GetGraphicsRendererType() reports the device's real renderer. The compile-time getCurrentGraphicsRendererType() still reports only the build default.

⚠

Selection latches at the first successful device. The latch closes when the first GraphicsDevice has successfully created a renderer. After that, SetPreferred, SetFallbackChain and EnableAutomaticFallback throw InvalidOperationException. A failed creation does not latch, so a game may catch the error and try another configuration; GetSelected() never latches; recreating the same renderer on a live device (Reset, an MSAA change) and creating a second GraphicsDevice keep the selection. Fallback between renderers that need different kinds of window can recreate a CNA-owned window, but a caller-owned DeviceWindowHandle cannot be recreated; that candidate is skipped as WindowKindConflict.

Two device flags ask for a specific renderer: GraphicsAdapter::UseNullDevice requires HEADLESS and UseReferenceDevice requires SOFTWARE (C++ accessors setUseNullDeviceProperty and setUseReferenceDeviceProperty). If that renderer is not compiled in, or the selection already latched to another one, device creation fails with NoSuitableGraphicsDeviceException; a fallback chain cannot satisfy them with a different renderer. For testing, the environment lists CNA_DEBUG_UNAVAILABLE_RENDERERS and CNA_DEBUG_FAIL_RENDERER_INIT simulate an unavailable or failing renderer, and CNA_FORCE_HEADLESS_DEVICE_EXT creates the named renderers' device without a window. The full API, fallback ordering and C ABI surface are on Runtime Renderer Selection.

Combination rules

Multi-renderer builds add code size and every selected family's dependencies. This snapshot rejects demonstrated conflicts at configure time, each with a reason in the error. Windows-only and Emscripten-only identities cannot cross platform partitions: one toolchain cannot target both.

Platform partitionIdentitiesEnforced by
Windows only (1)DIRECTX9FATAL_ERROR unless CMAKE_SYSTEM_NAME is Windows (native MSVC/MinGW or the mingw-w64 cross toolchain)
Emscripten only (1)WEBGL2Refused on any other target; OPENGLES3 and OPENGL33 are refused under Emscripten
Everything else (8)All other identitiesNo operating-system partition; each family's own dependencies still apply (and iOS admits only its allow-list, see below)

Several EasyGL identities may coexist in one binary — the GL profile is a runtime value — provided they do not cross the native/Emscripten partition. In a multi-renderer build only the default renderer's CNA_RENDERER_<IDENTITY> macro is defined project-wide; CNA_MULTI_RENDERER is defined when more than one is compiled in. The rules are checked by scripts/check_renderer_combinations.py.

Names that changed (and one trap)

The renderer vocabulary was normalised. If you are following an older document, translate first — the old spellings are not aliases, they are unknown values that stop the configure step with a FATAL_ERROR when given to CNA_GRAPHICS_RENDERER or CNA_GRAPHICS_RENDERERS (an old-style -DCNA_RENDERER_D3D9=ON switch is simply not read; see above). The old option name behaves the same way: no build file at this snapshot reads CNA_GRAPHICS_BACKEND, so -DCNA_GRAPHICS_BACKEND=OPENGL33 is accepted without an error and the platform default renderer is configured (read from the CMake files; not executed). In old scripts, rename the option itself.

The GL family — three profiles, one EasyGL implementation

Three renderer identities share one internal implementation, EasyGL, which lives in the ../easy-gl sibling repository (itself needing ../meta-gl). The profile is a runtime value inside the family, so the two native profiles can be linked into one binary; WEBGL2 sits on the other side of the native/Emscripten partition.

Against the 39-scene XNA oracle corpus, EasyGL is gated on two line scenes at tolerance 0 (EasyGL_XnaLineCoverage); a whole-corpus measurement recorded 10 of 39 on 2026-08-11, before later pixel-centre fixes — see How renderers are verified. The adapter promises at most 4× MSAA. Step-by-step use is in Tutorial 102.

"EasyGL" remains the correct name for the implementation and for the sibling library. It is not a value you can pass to CNA_GRAPHICS_RENDERER.

Modern GPU APIs: SDL_GPU and WebGPU

Two renderers drive a modern explicit GPU API, both through a portable layer: SDL_GPU through SDL3’s GPU API, and WEBGPU through WebGPU. CNA has no compute-shader, storage-buffer, indirect-draw or GPU-timer API on any renderer; ordinary graphics (stock effects, ShaderEffect, PBR, image-based lighting, shadows, float render targets, instancing, compiled effects) is what these renderers implement.

SDL_GPU is covered by Tutorial 131 and WEBGPU by Tutorial 132. To run on Vulkan, Direct3D 12 or Metal, use SDL_GPU (or FNA3D, whose own SDL_GPU driver reaches the same APIs); the native GPU driver is SDL’s choice, reported by SDL, not a CNA identity.

⚠

What SDL_GPU does not do yet. CNA records these gaps against the native renderers it replaced (CNA’s CHANGELOG.md and handoff.md §5.2): ShaderEffect is compiled out on Windows, Apple and Emscripten builds because no runtime GLSL → SPIR-V → DXIL/MSL path exists; occlusion queries are unavailable (SDL’s GPU API has none); BlendState.MultiSampleMask reaches the renderer but is deliberately not applied (the pinned SDL reserves the field); cube faces inside a multi-render-target set are refused with NotSupportedException; and SpriteSortMode::Immediate batches its sprites (CNA’s one open defect at this snapshot, shared with WEBGPU). Base-instance drawing is implemented by expanding per-instance streams on the host.

2D games

Every renderer that draws pixels draws both 2D and 3D, so a SpriteBatch-only game runs on any of them and the platform default is a good choice. STUB reports ThreeD false, but it is a no-op renderer, not a 2D renderer.

What a 3D call does where 3D is missing

The behaviour is a setting, Unsupported3DGraphicsCallBehavior, changed with GraphicsDevice::SetUnsupported3DGraphicsCallBehavior (or, from C, cna_graphics_device_set_unsupported_3d_call_behavior). Throw is the default and raises an error naming the renderer and the method; WarnAndStub logs one warning per operation and returns a safe no-op or null object (on STUB and HEADLESS a Texture3D request gets such a null object too). WarnAndStub does not change any SupportsCapability() answer.

Windows renderers: Direct3D 9 and SDL_GPU

One renderer is hard-gated to CMAKE_SYSTEM_NAME=Windows and stops the configure step with a FATAL_ERROR anywhere else: DIRECTX9, real Direct3D 9 — the API real XNA 4.0 itself ran on — through its genuine COM interfaces rather than emulated over another API. The Windows default, SDL_GPU, reaches Direct3D 12 through SDL’s GPU driver.

⚠

Windows evidence is Wine evidence. CNA validates DIRECTX9 through MinGW-w64 cross builds run under Wine with DXVK, and SDL_GPU’s Direct3D 12 driver under Wine with vkd3d-proton. A native-Windows MSVC workflow exists (d3d-windows-ci.yml: the DIRECTX9 suite and an SDL_GPU Direct3D 12 smoke leg), but it is manual-dispatch only; CNA’s handoff records the SDL_GPU leg as not run yet and no current real-Windows hardware validation. The reference images of the oracle corpus were captured under Wine + DXVK on Linux, not on Windows. Treat any Wine result as evidence for that exact configuration.

Only DIRECTX9 has no SupportsCapability() override. It relies on the permissive base defaults wholesale, so its true answers are the least informative. Custom ShaderEffect shaders on it are HLSL, compiled at run time with D3DCompile (vs_3_0/ps_3_0 under HiDef, vs_2_0/ps_2_0 under Reach). DIRECTX9 is the only renderer recorded as pixel-exact against the XNA oracle corpus — see How renderers are verified. A guided tour is Tutorial 103.

Browser renderers

Two renderers draw in a browser. WEBGL2, from the GL family, exists only there and is the Emscripten default. WEBGPU also has a browser route (the browser’s own WebGPU through the emdawnwebgpu port) but is not Emscripten-only, because it also builds natively through wgpu-native. A page uses WebGPU where the browser offers it and WebGL 2 elsewhere; both can be linked into one bundle.

The Emscripten multi-renderer workflow builds one bundle containing WEBGL2 and WEBGPU and asserts that both renderer archives, both registry entries and the JavaScript selection surface are present — it builds and inspects symbols; it does not run them. Under Emscripten a WEBGPU build needs a larger Asyncify stack, which the build sizes automatically. The strongest browser evidence is outside CI: the 90 sample builds at samples.libcna.com run on WEBGL2 and were each run in Chrome when they were published (against earlier CNA revisions).

To pick a renderer from the page, set the property before the module starts: var Module = { cnaPreferredRenderer: "WEBGPU" }; (or call Module._cna_set_preferred_renderer); the bundle must have been built with that renderer in CNA_GRAPHICS_RENDERERS. Tutorial 105 and Tutorial 132 walk through both routes.

⚠

Web caveats apply to both renderers in this group (to WEBGPU when it is built for the browser). There is no video: FFmpeg is never built for Emscripten, so the Video types exist and link but throw NotSupportedException at run time. Online sessions and invitations are refused in a browser build. Your Game object does not have to be heap-allocated: Game::Run() blocks through Asyncify, so MyGame game; game.Run(); is fine, and the browser loop honours a variable time step. Save persistence and threading are described on Platforms.

Translation and adapter layers

Three renderers do not name one native graphics API. Each targets a portable layer that itself picks a native API — sometimes at build time, sometimes at run time. CNA classifies WEBGPU, SDL_GPU and FNA3D as its TranslationLayer category. That indirection is the point, and it is also where the surprises live.

SDL_GPUSDL3's GPU API; SDL picks the native GPU driver and CNA feeds it SPIR-V2D + 3DAny host SDL3's GPU API supportsSDL3; SDL_shadercross + SPIRV-Cross; optional libshaderc

Group-specific caveats, all of which change what your code does rather than merely how fast it runs:

  • SDL_GPU is an SDL3 API, so it requires the SDL3 platform. A configure with CNA_ENABLE_SDL=OFF refuses it by name, and a platform without SDL video refuses it as the platform rather than failing later. On Windows and Apple SDL_shadercross is on by default (CNA_SDL_GPU_SHADERCROSS); Linux and Android use the committed SPIR-V natively.
  • WEBGPU’s native route downloads a pinned wgpu-native release unless you give CNA_WEBGPU_ROOT; its browser route needs no native library. Its Windows, macOS and linux-aarch64 packages are unverified.
  • FNA3D enables XNA/FNA compiled Effect Framework bytecode automatically. It executes those binaries through MojoShader and cannot compile ShaderEffect source at all. Its Fna3d_XNA_Oracle test renders the whole corpus but gates only that every scene renders, not that it matches. FNA3D’s own driver decides some answers (CNA records, for example, that it ignores SkinnedEffect.VertexColorEnabled). See Tutorial 108.

CPU and no-GPU renderers

Three renderers need no GPU, no driver and no display server. One produces real pixels on the CPU; two produce none at all.

💡

SOFTWARE never presents to a window. It rasterizes for real and stays off-screen in an SDL3 window (on Windows, X11 or Wayland alike): you read the result back with GetBackBufferData() rather than watching it appear in a window. That makes it useful for deterministic, GPU-free pixel checks. The deliberate exceptions are platforms that report surface presentation without a native window handle: SOFTWARE on CNA_PLATFORM=TERMINAL attached to a TTY hands each finished frame to the terminal platform's surface presenter, and on iOS it is presented through the platform's surface presenter. Terminal accepts only SOFTWARE, HEADLESS and STUB, and of those only SOFTWARE actually displays.

SOFTWARE reports CustomEffects false: its fixed CPU shading path produces the pixels, and your shader source will not run. HEADLESS validates and records the call without executing it, which is exactly what a harness should do. UseNullDevice maps to HEADLESS and UseReferenceDevice to SOFTWARE. See Tutorial 107.

What each renderer needs from the platform

The renderer and the platform implementation (CNA_PLATFORM: SDL3 by default, HEADLESS, TERMINAL) are independent build axes, but the platform decides which renderers can find a window or a GL context. SDL3 is CNA’s one windowing implementation: Windows, X11, Wayland, macOS, iOS, Android and the browser are reached through SDL’s own video drivers, and a renderer that needs a native handle (an HWND, an X11 Display* and window, a Wayland wl_display* and wl_surface*, a Cocoa or UIKit view) receives it from the SDL3 window through NativeWindowHandle.

  • Two renderers are SDL3 APIs or depend on SDL directly: SDL_GPU and FNA3D. The other families are SDL-free at source level and take their window and GL context from the platform.
  • A GL context is provided by the SDL3 platform (not Terminal, not Headless).
  • An SDL-free build has no window. CNA_ENABLE_SDL=OFF refuses CNA_PLATFORM=SDL3, SDL3 audio and the two SDL renderers by name; what remains is a windowless configuration (HEADLESS or TERMINAL with HEADLESS, SOFTWARE or STUB, and Null or ALSA audio) for servers, test runners and terminal games.
  • Terminal accepts only the CPU/no-pixel renderers and is POSIX-only. iOS admits SOFTWARE and SDL_GPU (the latter never yet built for iOS); anything else is a FATAL_ERROR unless the unsupported override -DCNA_APPLE_ALLOW_UNVALIDATED_RENDERER=ON is given.

The platform matrix, the CNA_AUDIO_PLATFORM axis and the per-OS status are on Platforms.

Shaders: what actually executes where

Two separate things get called "shaders" in an XNA-shaped framework, and CNA treats them very differently.

Compiled Effect Framework bytecode is the XNA-compatible path described below. It accepts XNA/FNA Direct3D 9 Effect binaries on qualified renderer builds; it is not a compiler for HLSL .fx source and does not accept DXBC or MGFX.

Renderer-native custom shaders use ShaderEffect, and three separate questions apply: does the renderer accept a ShaderEffect (the CustomEffects capability), does the supplied source text determine the pixels (the detailed ShaderEffectSourceExecution feature), and which payload does it consume (its declared shader dialect, CNA::ShaderDialectEXT).

GraphicsCapability::CompiledEffects is independent of CustomEffects. It means the renderer can execute XNA/FNA Direct3D 9 Effect Framework bytecode (.fxb), which needs MojoShader (or CNA's translation of it) from the pinned FNA3D checkout. Capability reporting

⚠

Do not branch game logic on a bare positive SupportsCapability() answer and expect execution proof. The base implementation of IGraphicsRenderer::SupportsCapability still returns true for every member except MultiStreamVertexInput (false), StencilBuffer (delegated to the renderer), CompiledEffects (routed through its false-by-default opt-in) and FloatRenderTargets and HalfFloatRenderTargets (false). Only DIRECTX9 has no override at all; SDL_GPU uses a switch with no default arm, STUB answers false to everything, and WEBGPU, HEADLESS, SOFTWARE, EasyGL and FNA3D use partial default: true arms.

GraphicsCapability has 17 members: the 14 that existed in alpha.1 (ThreeD, DepthStencilBuffer, MultiSampleAntiAliasing, MultipleRenderTargets, AnisotropicFiltering, WireFrame, OcclusionQuery, CustomEffects, Texture3D, MultiStreamVertexInput, Instancing, StencilBuffer, AdditiveBlending, CompiledEffects) and three added since: FloatRenderTargets, HalfFloatRenderTargets and HalfFloatTextureLinearFiltering. At the device level, GraphicsDevice::SupportsCapability answers six members from separate questions rather than the renderer's own switch: CompiledEffects from the renderer’s opt-in, FloatRenderTargets and HalfFloatRenderTargets from whether Vector4 and HdrBlendable are accepted as render-target formats, half-float filtering from a false-by-default virtual, and MultipleRenderTargets and Texture3D ANDed with the graphics profile’s limits. The device-level answer is the public one: a caller who holds the renderer interface directly can see different values.

The practical consequence is unchanged: a capability query is a hint, not a contract. The reliable checks are the ones this page states directly — which renderers execute custom shaders, and which report a feature in the matrix below — plus the detailed profile that follows. Tutorial 101 shows how to query and interpret them.

One gap no capability member reports: a cube face inside a multiple-render-target set. DIRECTX9 and SDL_GPU refuse it at SetRenderTargets with System::NotSupportedException, and WEBGPU refuses it with its own message (a face "cannot be bound in a multiple-render-target set"); HEADLESS accepts it (it rasterizes nothing), and the GL family and SOFTWARE implement it. A single cube face bound on its own is a different, ordinary path. Check Render Targets before relying on it.

RendererCapabilityProfile: the detailed answer

The 17-member GraphicsCapability enum is a summary. The finer API is CNA::RendererCapabilityProfile: 31 RendererFeature ids (the legacy summaries split further, plus ShaderEffectSourceExecution, Texture3DSampling, ShadowSampling, ImageBasedLighting, six shader-dialect flags, BaseInstanceDrawing, SamplerLevelOfDetailBias, PbrEffectShading and SkinnedPbrEffectShading), a four-state answer (Unknown, Unsupported, Supported, Restricted), 8 RendererLimit ids (texture size, vertex streams, uniform-buffer size, sampled textures per stage, vertex-input bindings and attributes, colour attachments, uniform-buffer offset alignment, each with an explicit known/unknown flag), per-format usage masks for the 27 SurfaceFormat values (each usage carries separate known and supported bits, so an unclassified use is not misread as unsupported), and a generated English report. Retired feature and limit ordinals stay reserved, so the surviving values keep their numbers. The profile is built lazily by the GraphicsDevice and cached until renderer reconstruction or device destruction.

#include "Microsoft/Xna/Framework/Game.hpp"
#include "CNA/RendererCapabilityProfile.hpp"

// inside a Game subclass, after the device exists:
auto& device = getGraphicsDeviceProperty();

bool shadows = device.SupportsRendererFeatureEXT(CNA::RendererFeature::ShadowSampling);
CNA::RendererLimitValue maxTex =
    device.GetRendererLimitEXT(CNA::RendererLimit::MaxTextureDimension);   // maxTex.known / maxTex.value
CNA::RendererFormatSupport color =
    device.GetRendererSurfaceFormatSupportEXT(Graphics::SurfaceFormat::Color);
bool colorRt = color.Supports(CNA::RendererFormatUsage::RenderTarget);

std::string_view report = device.GetRendererCapabilityReportEXT();       // English text

The accessors are GetRendererCapabilityProfileEXT(), GetRendererFeatureSupportEXT(), SupportsRendererFeatureEXT(), GetRendererLimitEXT(), GetRendererSurfaceFormatSupportEXT() and GetRendererCapabilityReportEXT(); C functions expose the same surface in the experimental C API (ABI 0.50.0). Texture and surface formats

SurfaceFormat has 27 members: the 20 classic XNA formats and 7 CNA extensions (ColorBgraEXT, ColorSrgbEXT, Dxt5SrgbEXT, Bc7EXT, Bc7SrgbEXT, ByteEXT, UShortEXT). Each renderer classifies formats itself; a renderer with no classifier gets the framework rule: SurfaceFormat::Color only, anything else throws ("... is not implemented by the selected graphics renderer"). Six families classify Texture2D formats (DIRECTX9, EasyGL, FNA3D, SDL_GPU, SOFTWARE, WEBGPU), so only HEADLESS and STUB accept nothing but Color textures; four classify render-target formats (EasyGL, SDL_GPU, SOFTWARE, WEBGPU), so DIRECTX9, FNA3D, HEADLESS and STUB accept only Color render targets. Native Alpha8 render-target storage exists on no renderer: a target preferring it falls back to Color. Summaries below come from the implementation files, so treat them as guidance and use the profile for the truth on your device.

  • EasyGL: Color, Alpha8 and DXT1/3/5 on every profile (CPU-decoded without S3TC), the packed 16-bit formats as sized GL storage, NormalizedByte2/4 and the remaining classic formats through the ES 3 sized-format set; the extension formats defer.
  • SDL_GPU: Color, packed 16-bit, DXT (native BC or CPU decode), NormalizedByte2/4 and Alpha8; Rgba1010102, Rg32, Rgba64 and the float and half-float formats in their exact native storage (widened to four channels with Direct3D 9’s fill) where the device can sample that storage, refused otherwise — never substituted; float formats in Texture3D too.
  • DIRECTX9: native Texture2D, cube and volume formats through its D3DFMT mapping, checked against the device; render targets Color only.
  • WEBGPU: BC only when the device enabled it; HalfVector4 and HdrBlendable stored natively as rgba16float in Texture2D; float formats in Texture3D; optional browser texture formats are gated on what the browser offers; Rgba64 has no render-target mapping.
  • SOFTWARE: the 20 classic formats, DXT stored as blocks; a block-compressed Texture2D keeps no zero-filled CPU shadow.
  • FNA3D: Color and the signed-normalized NormalizedByte2/NormalizedByte4 (authentic XNA normal maps) are classified supported, with typed Texture3D formats; DXT and BC7 follow the driver’s own format answer; every other format defers to the framework rule.

How renderers are verified

Renderer verification is configuration-scoped. The selected renderer set, platform implementation, audio implementation, host and feature options decide which pixel, smoke and integration tests are built and registered. A multi-renderer build may contain several renderer test sets. Report ctest -N and executed results for the exact configuration rather than quoting a tree-wide registration total as though it were universal. CNA’s own latest full Debug runs (17 October 2026, Linux, Mesa RADV, recorded in its handoff.md, not repeated here) cover SDL_GPU, WEBGPU, SOFTWARE, FNA3D and a multi-renderer tree with OPENGLES3 as default; Verification lists them.

Which renderer should I choose?

💡

Default answer: the platform default, with one caveat. OPENGLES3 on Linux and Android, WEBGL2 on the web, SDL_GPU on Windows, macOS and iOS. The first two are the best-evidenced configurations CNA has. SDL_GPU is CNA’s chosen modern path but is qualified on Linux and under Wine only at this snapshot, so test your game on the real target.

💡

For a 2D game wanting maximum portability: the platform default. Every pixel-producing renderer draws SpriteBatch content; SOFTWARE needs no GPU at all.

💡

For a modern 3D desktop game: SDL_GPU (SDL chooses Vulkan, Direct3D 12 or Metal) or OPENGL33/OPENGLES3; DIRECTX9 on Windows if you need the XNA-faithful path. Remember that SDL_GPU compiles ShaderEffect out on Windows and Apple and has no occlusion queries. Check the profile at start-up rather than assuming a feature.

💡

For measured XNA pixel fidelity: DIRECTX9, the only renderer recorded as matching the checked-in 39-scene oracle corpus exactly. It is Windows-gated; the repository provides a manual MinGW/Wine + DXVK route, not an automatic workflow.

💡

For CI with no GPU: HEADLESS or STUB when you only need game logic exercised, or SOFTWARE when you need real pixels — read back with GetBackBufferData(), since it does not present to a window (UseNullDevice and UseReferenceDevice select HEADLESS and SOFTWARE for you).

💡

For the web: WEBGL2 is the default and the widest path, and the one the 90 published sample builds use; WEBGPU is Supported where the browser offers WebGPU. Whichever you pick, the web caveats above apply (no video; threaded builds proxy WebGL to the main thread).

⚠

Know what you are opting into. Custom ShaderEffect shaders are not accepted by SOFTWARE or FNA3D (FNA3D supports the separate compiled Effect Framework path instead), nor by SDL_GPU outside Linux and Android builds. Compiled-effect support is an opt-in build everywhere except FNA3D. CI does not exhaustively exercise every identity and driver combination.
