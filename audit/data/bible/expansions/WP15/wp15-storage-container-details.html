StorageContainer details that affect save code

Three behaviours are easy to miss when XNA save code is ported; each was checked by reading {{src:modules/storage/src/StorageContainer.cpp|StorageContainer.cpp}} at this snapshot (not executed). The internals are on {{page:development/internals/modules/storage.html#authority|the storage internals page}}.

Reading a save back completely

Stream::Read returns how many bytes it actually copied, which may be fewer than requested. Loop until the expected length is reached or a read returns 0, and treat a short result as a truncated save rather than parsing it:

std::unique_ptr<System::IO::Stream> in =
    container->OpenFile("savegame.dat", System::IO::FileMode::Open);
std::vector<SharpRuntime::bytecs> bytes(static_cast<std::size_t>(in->getLengthProperty()));

SharpRuntime::intcs offset = 0;
const auto total = static_cast<SharpRuntime::intcs>(bytes.size());
while (offset < total) {
    const SharpRuntime::intcs n = in->Read(bytes.data(), offset, total - offset);
    if (n == 0) break;          // end of file before the expected length
    offset += n;
}
if (offset != total) { /* reject a truncated save */ }

Syntax-checked with g++ -fsyntax-only against an earlier snapshot’s headers and a sibling sharp-runtime checkout; the calls it uses are unchanged at c6dec91f. Not run.

Wildcard patterns, exactly

GetFileNames(pattern) and GetDirectoryNames(pattern) match each entry name at the container's top level (not recursively) against the whole pattern with CNA's own matcher: * matches any run of bytes, including none; ? matches exactly one byte, so a non-ASCII character, which is several UTF-8 bytes, needs several; every other byte, . included, matches only itself, case-sensitively on every host. There are no character classes and no escapes, and an empty pattern returns no names without touching the filesystem, as in XNA. "slot?.sav" therefore finds slot1.sav but not Slot1.SAV or slot10.sav. The storage tests match plain prefixes and suffixes ("*.bin", "directory-*") against non-ASCII names, not the matcher’s ? and case edge cases, so test the patterns your game depends on.

Disposal and concurrent writers

Dispose() sets IsDisposed and then raises Disposing once. From then on every file and directory method, and the DisplayName and StorageDevice getters, throw System::ObjectDisposedException before validating arguments or touching the filesystem, as XNA does; files on disk and streams opened earlier are kept. Sharing follows XNA’s defaults: CreateFile and the two- and three-argument OpenFile open with FileShare::None, so a second open of the same file fails with System::IO::IOException while the first is held, and a refused Create or Truncate open does not truncate the stored data first. The four-argument OpenFile applies the share mode you pass: Windows enforces it, POSIX systems use advisory locks, which only other processes that also lock respect, and the browser’s virtual file system makes no promise. CNA records this on Linux; Windows validation is still pending. Within one game, serialise saves rather than relying on locks.
