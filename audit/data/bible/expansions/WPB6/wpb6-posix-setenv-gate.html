The POSIX-environment rule behind a Windows CnaTests

The header of the native workflow gives POSIX ::setenv() in test files as the reason it does not build CnaTests, and that is a rule with a checking script of its own. MinGW-w64, like MSVC, has neither setenv nor unsetenv, so a single call in any translation unit that reaches a Windows build stops CnaTests.exe from compiling. The repair recorded in docs/cnatests-mingw-setenv-proposal.md replaced the call sites with System::Environment::SetEnvironmentVariable(name, value), where an empty value means unset. At this snapshot 38 files under modules/, tools/ and tests/ use that call.

Eleven new POSIX calls had appeared by 2026-08, so the rule was written down as a text check. {{src:scripts/check_no_posix_setenv.py|check_no_posix_setenv.py}} scans every .cpp and .hpp under modules/, tools/ and tests/, skips comment lines and third-party trees, and fails on any setenv( or unsetenv( call. The script's point is to fail on a Linux build long before anyone attempts a Windows one. At this snapshot no CMake file and no workflow runs it, so it is a check a maintainer invokes by hand, not a CTest.

The script does not pass at this snapshot. Its pattern, applied read-only to the snapshot tree for this page, matches 42 calls in 13 files: four Gamer Services example programs, eight Gamer Services test files, one network harness and one content-pipeline serializer test. Some of them sit beside a _WIN32 alternative or inside a POSIX-only block and others do not; because the script matches text, not targets, a red result says “a POSIX environment call exists somewhere in the tree”, and only reading the call sites shows whether a Windows build is affected.
