Phones reshape the preferred back buffer; desktops do not

GraphicsDeviceManager decides once, when it is constructed, whether the process runs on a platform that cares about device orientation ({{src:modules/runtime/src/GraphicsDeviceManager.cpp|GraphicsDeviceManager.cpp}}, platformSupportsOrientations). It compares the name that the current platform's system-information service reports with "iOS" and "Android". This is a run-time string comparison, not an #ifdef, and it copies FNA's SupportsOrientations. The ambient platform is asked, not the game's own platform, because the default constructor has no game to ask. Only the SDL3 implementation serves those two targets, and its system information reports SDL_GetPlatform().

The answer changes how CreateDevice() and ApplyChanges() turn the preferences into presentation parameters:

  • Desktop, web and every other name. The back buffer is PreferredBackBufferWidth × PreferredBackBufferHeight, taken verbatim with no landscape swap. This is XNA's and FNA's desktop behaviour. SupportedOrientations is stored, but it is not forwarded to the window.
  • iOS and Android. The two preferred sizes are treated as a pair of edges. When the presentation parameters' DisplayOrientation is Portrait, the smaller edge becomes the width. Any other value, including the default, gives the landscape shape: the larger edge becomes the width. SupportedOrientations is passed to the window through SetSupportedOrientations before the screen-device change, with XNA's Default resolved from the preferred size first (GameWindow::resolveSupportedOrientations): Portrait when the preferred back buffer is taller than wide, both landscapes otherwise. The device is created in an orientation the game supports (selectDeviceOrientation): the window's current orientation when it is supported, else the one the preferred shape implies, so the presentation parameters always carry a concrete DisplayOrientation for the swap below.

A size recorded after the user resized the window takes precedence over both rules for the next pass. In practice, a phone game that asks for 480×800 gets a portrait 480×800 back buffer even when it leaves SupportedOrientations at Default, and one that asks for 800×480 keeps its landscape buffer. A desktop build of the same code gets 480×800.

Evidence. DefaultBackBufferPreferencesAreTheXnaDefaults covers the desktop half ({{src:modules/runtime/tests/Microsoft/Xna/Framework/GraphicsDeviceManagerPlatformTests.cpp|GraphicsDeviceManagerPlatformTests.cpp}}). The test skips itself on iOS and Android, because the swap is intended there. The phone reshape is covered by {{src:modules/runtime/tests/Microsoft/Xna/Framework/GraphicsDeviceManagerOrientationTests.cpp|GraphicsDeviceManagerOrientationTests.cpp}}, which runs the manager on the build's own platform reporting itself as Android: Default with 480×800 gives Portrait 480×800, Default with 853×480 gives LandscapeLeft 853×480, and an explicit Portrait with 800×480 gives 480×800. The commit that added them records one Android emulator run of a portrait sample; no phone run is recorded in CNA. Checked by reading at c6dec91f; not executed on a phone.
