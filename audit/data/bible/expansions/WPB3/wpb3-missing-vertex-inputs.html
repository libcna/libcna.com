When the declaration lacks an input the stock effect reads

Microsoft XNA 4.0 refuses such a draw. GraphicsDevice.VerifyCanDraw compares the bound VertexDeclaration with the vertex shader's input signature and throws InvalidOperationException (resource MissingVertexShaderInput, read from the IL of the genuine XNA 4.0 graphics assembly). At this snapshot CNA performs the same check once, in the shared layer, before any family sees the draw: GraphicsDevice::RequireStockEffectInputs ({{src:modules/graphics/src/Xna/GraphicsDevice.cpp|GraphicsDevice.cpp}}) requires Position0 always, Color0 when vertex colour is enabled, TextureCoordinate0 when a texture is, TextureCoordinate1 for the dual-texture effect, Normal0 when lighting is on, and BlendIndices0 with BlendWeight0 for a skinned draw. A missing element throws InvalidOperationException with XNA's wording, for example "The current vertex declaration does not include all the elements required by the current vertex shader. Normal0 is missing."

The check reads the union of every bound stream, per-instance streams included, because Direct3D 9 validates a shader's inputs against all of them, and it first applies FNA3D's declaration-collision rule (a repeated usage and index moves to the first free index of that usage), so a legitimate split TEXCOORD0/TEXCOORD0 layout is validated as the TEXCOORD0/TEXCOORD1 the renderer will consume. DrawUserPrimitives and DrawUserIndexedPrimitives are checked against the declaration they upload with. Four kinds of draw keep their own input contracts and are not checked: a compiled XNA effect, a custom ShaderEffect (its source decides what it reads), CNA's PBR extension, and the legacy route with an empty declaration, which has no elements to compare; a skinned draw on that route is refused outright, because its layout cannot be inferred from a stride.

On those exempt routes, and for any input a stock program declares beyond the checked set, the families fall back to a neutral value. {{src:modules/graphics/include/CNA/Internal/Graphics/StockVertexSemantics.hpp|StockVertexSemantics.hpp}} documents it as (0, 0, 0, 1): the value Direct3D 9 fills into a vertex register's missing components and the value OpenGL's disabled generic attribute holds, which is what the reference renderer, EasyGL, leaves such an input at; the header warns that a friendlier default such as white would quietly diverge. One exception landed after that rule was written: since 24 October 2026 EasyGL sets an absent colour input to white, the identity the vertex-colour multiply needs, because a colourless 48-byte PbrEffect record with VertexColorEnabledEXT on selects its colour program and otherwise drew black (EasyGLRenderer.cpp; every other absent input keeps GL's own default). The header's comment still describes the older rule. DIRECTX9 additionally checks its own BasicEffect and AlphaTestEffect draws against the declaration ({{page:deep-dives/renderers/direct3d9-xna-fidelity.html#effect-reach|DIRECTX9: which variants a draw can reach}}). Until 15 October 2026 there was no shared check, each family decided for itself, and the same draw that XNA refuses produced different pictures on different renderers; supply every semantic the effect variant reads, and test such draws by pixels.
