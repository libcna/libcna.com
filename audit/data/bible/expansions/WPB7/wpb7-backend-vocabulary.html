"Backend" in CNA's own identifiers

The selectable graphics implementation is a renderer: the option is CNA_GRAPHICS_RENDERER, the enum is GraphicsRendererType and the implementations live under {{tree:modules/renderers|modules/renderers}}. In CNA's own identifiers, "backend" usually names something else: an internal service implementation behind a device or network interface. Examples are ICompassBackend and IMotionBackend for the sensors (implemented on Android by AndroidCompassBackend and AndroidMotionBackend), IVibrateBackend for vibration, and ENetBackend for SystemLink networking ({{src:modules/net/include/CNA/Internal/Net/ENetBackend.hpp|ENetBackend.hpp}}).

The two classification enums in the core module use the renderer word too. GraphicsRendererCategory ({{src:modules/core/include/CNA/GraphicsRendererCategory.hpp|GraphicsRendererCategory.hpp}}: Native, TranslationLayer, Software, Web, Diagnostic) and GraphicsRendererMaturity ({{src:modules/core/include/CNA/GraphicsRendererMaturity.hpp|GraphicsRendererMaturity.hpp}}: Production, Supported, Experimental, Historical, Deprecated) classify a renderer; getGraphicsRendererCategory(GraphicsRendererType) returns the category of the given renderer, and getCurrentGraphicsRendererCategory() that of the build default; getGraphicsRendererMaturity and getCurrentGraphicsRendererMaturity() do the same for maturity. They are descriptors, not a second selection axis; see {{page:development/internals/graphics/backends.html|the renderer internals}}. CNA’s identity check refuses the old graphics-backend identifiers in its own active files, so a source search for "backend" now finds the other meaning only, apart from upstream libraries’ own vocabulary (SDL’s GPU backends, for example).
