This matrix keeps three questions apart for every glTF 2.0 feature: what the shared import core accepts or transforms, what the runtime Model represents, and which committed evidence reaches it. "Reported" means GltfImportReportEXT makes a loss visible; it never means the missing feature was implemented. Test suite names are the CnaTests suites under the glTF import tests unless stated; their existence was read at 009d40f5, not their results. The contracts behind each row are explained on the import core, vertex packing, skinning and animation and conformance pages.

Route and oracle boundaries

The direct reader and the converter share semantic extraction but package the result differently: direct loading builds one model with every represented group at unit scale 1, while the converter can apply an explicit scale and writes one named .cnj per group. A .cnj reload proves the serialized boundary for the fields it carries (cameras are not among them); it is not a claim that JSON bytes and a live object are identical. A .cnb compiled from that .cnj restores skeleton, clips, morph data and lights but carries neither cameras, material variants nor the import report, and an .xnb built from glTF drops skeleton, clips, lights and morphs with named warnings.

All original D1–D8 records, and the later GLTF-241 record, are fixed and kept in the append-only ledger as regression history. CNA's plan records the broader GLTF ROBUST milestone at 9 of 12 rows: KHR_materials_specular texture sampling (only METAL among the current PBR renderers lacks it), native point and spot lighting, and a fourth renderer on the bounded external retake matrix remain open. The snapshot therefore supports strong, layer-qualified claims — not an unqualified promise about every file and renderer combination.
