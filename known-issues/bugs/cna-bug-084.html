CNA-BUG-084: Game::ResetElapsedTime() does nothing under the default fixed time step

ResetElapsedTime sets its flag only when IsFixedTimeStep is false, while XNA 4.0 honours it in both modes, so a blocking load followed by ResetElapsedTime causes a catch-up burst of updates in CNA only.

Affected contract
Microsoft::Xna::Framework::Game::ResetElapsedTime()

Expected behaviour

XNA 4.0's Game.ResetElapsedTime (IL of Microsoft.Xna.Framework.Game) sets forceElapsedTimeToZero and resets the running-slowly counters unconditionally; Game.Tick tests that flag right after reading the clock, before the fixed/variable branch, and discards the frame's elapsed time. The standard XNA idiom - load a level synchronously inside Update, then call ResetElapsedTime() - therefore yields no catch-up updates.

Actual behaviour at TARGET

In Game.cpp, ResetElapsedTime is if (!IsFixedTimeStep_) forceElapsedTimeToZero_ = true;, and Tick reads the flag only in its variable-step branch. Under the default fixed step the call is a no-op: after a 2-second load the accumulator is clamped to MaxElapsedTime (500 ms) and the next tick runs up to 29 back-to-back updates at the default 60 Hz before drawing (500 ms / 16.6667 ms, the last partial step carried over).

Source locations

  • modules/runtime/src/Game.cpp — Game::ResetElapsedTime and Game::Tick (the forceElapsedTimeToZero_ read in the variable branch only)
  • modules/runtime/include/Microsoft/Xna/Framework/Game.hpp — ResetElapsedTime documentation: 'for the next variable-timestep update'

Evidence

Checked by reading the named sources at 009d40f5; nothing was built or executed for this entry. XNA behaviour read from the IL of the genuine XNA 4.0 Game assembly (~/deps/xna-il-cache). The CNA header documents the narrower behaviour, and so does the site's timing deep dive; the contract that CNA claims to follow is XNA's.

Focused reproduction

// Illustrative; not compiled or run for this entry.
protected: void Update(const GameTime& t) override {
    if (!loaded_) {
        LoadEverythingSynchronously();   // takes ~2 s
        loaded_ = true;
        ResetElapsedTime();              // XNA: next tick runs one update
    }
    ++updates_;                          // CNA fixed step: next tick runs ~29 updates
    Game::Update(t);
}

Current tests

No test in modules/runtime/tests calls ResetElapsedTime.

Regression test

A Game test with a fake platform clock: advance the clock by 2 s inside Update, call ResetElapsedTime, and assert that the following tick runs exactly one Update with ElapsedGameTime equal to TargetElapsedTime (fixed step).

Blast radius

Every fixed-step game (the default) that relies on ResetElapsedTime after a blocking load or a pause; variable-step games are unaffected. The browser loop (EmscriptenMainLoopCallback) ignores the flag in both modes (CNA-BUG-080).

Workaround

After a long blocking operation, skip catch-up updates in game code, or temporarily set IsFixedTimeStep = false for the reset tick.
