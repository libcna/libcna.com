Roadmap

Development Roadmap

CNA is a long-term project developed incrementally. This page describes the honest current state and the path forward - no overpromising, no fake ETAs.

⚠

Honest timeline note: CNA is a long-term open-source project maintained in spare time. There are no fixed release dates. Milestones are goals, not commitments, and items marked "Open" below are gaps that have been identified, not work that has been scheduled. Progress is incremental and driven by API coverage, renderer stability, and real-world testing against ported games.

Current State

Where CNA actually is

CNA released 0.1.0 on 10 October 2026 (tag v0.1.0, commit 10a4ef1c), after the first tagged pre-release, 0.1.0-alpha.1 of 20 August 2026; it follows Semantic Versioning and is still pre-1.0. This page tracks the development snapshot c6dec91f (24 October 2026, branch next), which is 812 commits after the release; its product version string is still 0.1.0 (see Releases & Versioning). CNA’s own handoff describes the project as leaving its feature-expansion phase for long-term maintenance: no new renderers, asset formats or subsystems, and work focused on defects, XNA fidelity and deterministic validation. At this snapshot CNA represents every one of the 331 documented XNA 4.0 runtime types and 3,627 documented members — representation, not behaviour — exposes 10 renderer identities across 8 implementation families (alpha.1: 50 across 46), and has 898 C++ test sources with 11,898 statically discoverable GoogleTest-family definitions. These are source facts, not a universal pass count; APIs may still change before 1.0.

Read that as: breadth is largely done, depth is not. The sections below separate what has shipped from what is genuinely partial and what remains open.

Shipped

What is done and verified

Everything in this list exists in the source tree of snapshot c6dec91f and was confirmed by audit rather than by changelog. Items labelled "New" arrived after the alpha.1 tag; "Since 0.1.0" marks what arrived after the release.

Complete

10 renderer identities, single or multi-renderer builds Shipped

A normal build selects one identity with CNA_GRAPHICS_RENDERER. An opt-in CNA_GRAPHICS_RENDERERS list links several compatible families and selects one before the first device through GraphicsRendererSelection; fallback is explicit and the choice latches once the first renderer has been created successfully. Platform gates and dependency costs still apply. Since alpha.1 the set has been deliberately curated from 50 identities over 46 implementation families to 10 over 8, the last narrowing coming after the 0.1.0 release: SDL_GPU is now CNA’s modern native path and the default on Windows, macOS and iOS. A name outside the 10 is a configure-time error and a retired one is refused at run time too, never a silent fallback; no surviving identity was renumbered in the C ABI. See Graphics Renderers.

Production-ready

EasyGL renderer — the most mature path Shipped

EasyGL implements CNA's three GL-profile identities — OPENGLES3, OPENGL33 and the browser's WEBGL2 — and is the default on Linux and Android through OPENGLES3. It covers the stock effect families, lighting and GL context-loss recovery, instancing, occlusion queries, anisotropy, multiple render targets, 3D textures, PBR, image-based lighting and shadow sampling. Use the renderer capability report for the exact profile and feature boundary.

Complete — was listed here as "planned, not started"

Direct3D 9 renderer — functional, and the pixel-exact XNA oracle target Shipped

This page previously described DIRECTX9 as a possible future renderer. That is out of date: it is a Windows-only implementation with SM2/SM3 shaders, device-lost recovery and MRT bounded by the graphics profile. It is also the renderer used for CNA's 39-scene pixel-exact XNA oracle comparison at --tolerance 0: the references come from the genuine XNA 4.0 runtime under Wine and DXVK on Linux, the result is recorded as 39 of 39 (the last consolidated dated report covers 31 scenes; later per-scene notes record the rest), and the check is manual and not run in CI. Compiled XNA effects are an opt-in build feature.

New

SDL_GPU renderer Shipped

CNA’s modern native path: a deferred/retained renderer on SDL3’s GPU API with SPIR-V shaders, the stock effect families, stencil and MSAA resolve, float targets, PBR, image-based lighting, shadow sampling and base-instance drawing. SDL chooses its Vulkan, Direct3D 12 or Metal driver; with CNA_SDL_GPU_SHADERCROSS (on by default on Windows and Apple) the SPIR-V is translated through SDL_shadercross for the last two. It reports no occlusion queries, and compiled XNA effects are an independent opt-in feature. Since 0.1.0 it is the default on Windows, macOS and iOS, where it is not yet qualified (see below).

New

ASCII effect Shipped

A CNAEXT post-process effect, CNA::Graphics::AsciiPostProcessEffect, renders any finished frame as ASCII art. Because it works through the public Texture2D::GetData() and SpriteBatch API, it applies on any renderer and to 3D-rendered sources. Requires -DCNA_CNAEXT=ON.

Complete

The .xnb content pipeline Shipped

A real XNB loader is wired into ContentManager: 61 built-in readers (60 without native 128-bit integers), covering primitives, math, textures, fonts, audio, video, stock and compiled effects, and models on top of LZX decompression and shared-resource resolution. Typed external references and explicit custom-reader registration are present, ReflectiveTypeReaderBuilder registers custom types from a declared field list, and each Load<T>() installs the built-in readers its type needs, so nothing has to be registered (since 0.1.0). Since alpha.1 CNA also writes content: the build-time cna-content tool turns source assets into .cnb (the default) or .xnb, including LZX compression, and ContentManager resolves .xnb, then .cnb, then loose files. CNA reports that its XNB output loads in a genuine XNA 4.0 runtime under Wine; that has not been re-run for this page. See XNB Content Pipeline.

New

Build-time Content Pipeline and the CNB format Shipped

The XNA-shaped Microsoft::Xna::Framework::Content::Pipeline API is represented (128 of 128 types, 705 of 705 members, 10 importers, 12 processors) and driven by cna-content, which imports images, audio, video, fonts, glTF, .fbx, .x and existing .xnb and compiles .fx sources through an external legacy fxc (that route's verification against a genuine Microsoft fxc is not established). CNB is CNA's own deterministic container: a 64-byte header, CRC-32C per structure and chunk, and schemas for textures, models, animation clips, sounds and more. The pipeline has no C ABI export. See Content Pipeline, CNB Format and Command-Line Tools.

Complete

PBR effects and skeletal animation Shipped

Beyond the five XNA stock effects and SpriteEffect (all implemented natively in C++, not translated from bytecode), CNA ships non-XNA PbrEffect and SkinnedPbrEffect, with shadow-map and image-based-lighting inputs. Skeletal animation is real: SkinningData on Model::Tag with AnimationPlayer, AnimationClipEXT, BoneTrackEXT and KeyframeEXT (the Avatar path has its own SkinnedModelEXT), plus MorphTargetEXT blend shapes. All of it sits behind the CNAEXT boundary, so it is visible at compile time as non-XNA surface. PBR draws are shaded on every pixel-producing renderer: the GL family, SDL_GPU, WebGPU, Direct3D 9 and FNA3D on the GPU and Software on the CPU, each reporting it in the renderer capability profile.

Complete

Pixel-exact verification against the real XNA runtime Shipped

39 scenes under tools/xna-oracle/, rendered by the genuine Microsoft XNA 4.0 runtime under Wine and DXVK on Linux and diffed byte-for-byte against CNA's DIRECTX9 output at --tolerance 0 — recorded in the repository as matching all 39, run manually rather than in CI, and not yet repeated on native Windows. Alongside it: differential testing against a real running FNA build (tools/fna-reference/, also manual), and a compile-time CNAEXT purity check: defining CNA_STRICT_XNA_API turns CNAEXT declarations into [[deprecated]] warnings that -Werror promotes to errors, though the repository's own harness for it covers only Microsoft::Devices and its sensors.

Complete

A real Input, Audio, Net and Storage core Shipped

Input has zero stubs and a SDL3 GamePad bridge. XACT is a real parser and player, not a facade — a real binary parser for the XGS/XWB/XSB formats with FACT's actual volume formula. Net is real ENet over genuine UDP with real LAN discovery and best-effort host migration; PlayerMatch, Ranked and JoinInvited are refused with GamerServicesNotAvailableException rather than pretending. Storage is real std::filesystem IO with correct player namespacing and path-containment checks. See XNA Compatibility for the per-namespace breakdown.

New

XNA API representation closed: 331 of 331 types, 3,627 of 3,627 members Shipped

Every documented type and member of the ten XNA 4.0 runtime assemblies now has a matching C++ declaration (the first census found 3,463), measured by tools/audit_xna_runtime_surface.py against Microsoft's own XML documentation and DLL metadata. That includes the previously missing Microsoft.Xna.Framework.Design namespace: thirteen type converters in the opt-in CNA::Design module (see Framework.Design). This is representation, not behaviour: behaviour is verified only for the subsets on the Verification page, and the census is a manual script, not a CI gate.

New

Windows, X11 and Wayland through one SDL3 platform Shipped

CNA_PLATFORM selects one of three implementations: SDL3 (the default and the one windowing platform), HEADLESS and TERMINAL. SDL3 reaches Windows, X11 and Wayland through SDL’s own video drivers, and a game can still read the native handles (HWND, the X11 display and window, the Wayland display and surface) through GameWindow::GetNativeWindowHandleEXT(). CNA_ENABLE_SDL=OFF builds a windowless tree without SDL. CI runs the SDL3 window suite on SDL’s x11 driver under Xvfb and on its wayland driver under a headless Weston, and builds and runs it natively on Windows by manual dispatch. See Windows, X11 and Wayland.

New

ALSA audio and optional FFmpeg Shipped

CNA_AUDIO_PLATFORM=ALSA plays and records through ALSA (libasound is loaded at run time) with CNA's own mixer and vendored WAV, Ogg Vorbis, MP3 and FLAC decoders, so SDL-free Linux builds have XNA audio. FFmpeg video is now optional (CNA_ENABLE_VIDEO=AUTO|ON|OFF): the Video types link everywhere and throw NotSupportedException when no backend was built.

New

Compiled XNA effects on 8 renderer identities Shipped

Effect(GraphicsDevice&, bytes) and the XNB EffectReader load XNA Effect Framework bytecode on FNA3D (always) and, behind default-OFF build options, on the EasyGL family, WebGPU, Software, Direct3D 9 and SDL_GPU. A default configure reports the capability on FNA3D only, and MojoShader is linked only into builds that opt in. Runtime HLSL .fx compilation, DXBC and MGFX remain unsupported.

New

Renderer fidelity work across the surviving renderers Shipped

Float and half-float render targets, shadow-map and image-based-lighting sampling and PBR now reach every pixel-producing renderer that classifies those formats or carries those shaders — SOFTWARE, DIRECTX9 and FNA3D gained PBR, punctual lights and shadow sampling after the release — and each renderer reports them in the RendererCapabilityProfile API (31 features, 8 limits and per-format usage; GraphicsCapability has 17 members). 32 cross-renderer parity fixtures are registered for EasyGL, WebGPU and SDL_GPU, against the fixtures' own assertions — not against real XNA. The renderer-internal compute, storage-buffer, indirect-draw and GPU-timer layer was removed rather than finished: CNA has no such API.

Since 0.1.0

A program contains only what it uses Shipped

Each subsystem is now reached only through the calls that need it: a 2D game no longer links the avatar catalog, the system Guide, glTF, Draco, media, networking or cube and volume textures, and content readers are installed per family on first load. CNA recorded one 2D game shrinking from 44.6 MB to 6.2 MB stripped (Debug) — a measurement of that game, not a guarantee. Link-footprint gates keep the boundaries, CNA_OPTIMIZE_FOR_SIZE and CNA_ENABLE_GAMER_SERVICES are new options, and C++ consumers must rebuild against this revision. See Link boundaries and binary size.

Since 0.1.0

Generated C API boundary and an installable C++ SDK Shipped

Every C route’s boundary is generated from one line of a declarative specification, so the exception barrier, output, boolean and text rules are written once (C ABI 0.50.0). Separately, CNA_INSTALL_CXX=ON installs a relocatable C++ module SDK for find_package(CNA ... COMPONENTS ...); CNA records it validated for native Linux only. See the C API and Building.

Since 0.1.0

Defect repair driven by real programs Continuing

A stabilization pass (16–17 October 2026) fixed or removed every reproduced defect on CNA’s own list, which now names one open defect. A repair campaign driven by CNA’s demo suite then worked through 156 historical findings in math, content, storage, media, networking, Gamer Services and graphics: CNA records 147 with a final disposition (110 fixed and validated) and fixes committed for the remaining nine that its matrix has not yet closed on a complete checkpoint. Consumer projects (a museum simulator, cna-engine) fed further repairs. See Known Issues for what is open at this snapshot.

New, opt-in

CNAEXT extensions Opt-in, not in CI

The opt-in CNA::Graphics module holds three retro post-processing effects (CRT, colour-depth reduction, ASCII), a debug-drawing helper and portable shader packages. It needs -DCNA_CNAEXT=ON (default OFF); no workflow builds it. See CNAEXT Extensions.

New, opt-in

Diagnostics and Inspector Opt-in, not in CI

CNA_DIAGNOSTICS=OFF|STATS|FULL (default OFF) adds counters, gauges, per-frame counters, CPU profiler zones, bounded recording and Chrome-trace export, with built-in instrumentation for frames, draw calls and audio voices. CNA_BUILD_INSPECTOR adds an in-process agent (authenticated TCP) and the cna-inspector bridge that serves an offline browser UI; it is view-only and desktop-only, and no renderer supplies a resource-preview provider yet. No workflow configures either. See Diagnostics and Inspector.

New

C# through CNA.NET Beta, source-first

The C# binding builds on the C ABI: CNA.XnaCompat exposes the Microsoft.Xna.Framework API over the native C++ runtime, so XNA 4.0 C# game source compiles and runs without being rewritten. Its public metadata matches the selected XNA 4.0 runtime profile, it admits exactly one C ABI generation (0.47.0, from CNA’s next branch in mid-October; it refuses both the 0.1.0 release and this snapshot), and a dotnet new template creates games with desktop, browser and Android heads. Qualified on Linux x86_64, in headless Chromium and on the x86_64 Android emulator; on a physical Mac mini M4 (osx-arm64) it built, passed its managed suites and package acceptance, and smoke-ran its 84 samples on SOFTWARE against an earlier CNA, as local evidence without a CI leg, signing or notarization. See C# with CNA.NET.

New

XNA 4.0 samples in C++, in the browser and in original C# Practically complete

91 of Microsoft’s XNA 4.0 samples and games have complete C++ ports (cna-samples 5db32e6); 8 relevant C# programs remain, and the rest of the 153-entry audit list are not port targets. 90 C++ builds are playable at samples.libcna.com; the Racing Game Kit is ported but not hosted. 84 original C# sample programs run unchanged through CNA.NET (cna-dotnet-samples 1e6d763). See the Showcase.

New

Gamer Services, Guide, avatars and online sessions Linux; macOS recorded

Players are local profiles by default; configured outside game code, the same XNA APIs connect to the self-hosted CNA Gamer Services server for accounts, friends, presence, pictures, leaderboards and relayed PlayerMatch and Ranked sessions with invites and host migration. Avatars draw with CNA’s own art. Qualification is on Linux, with a CNA-recorded run on one physical Mac mini M4; there is no public server instance, and achievements and scores are client claims without anti-cheat. See Gamer Services & Avatars.

New

Save persistence on the web Shipped

WebAssembly builds mount the browser’s IndexedDB for StorageDevice and isolated storage and restore it before main(), so saves survive a page reload; threaded builds need CNA_EMSCRIPTEN_USE_WASMFS=OFF for this. The GamerServices local profile store is not yet inside these mounts.

In Progress

Partial, and known to be partial

These exist and work in part. The gaps below are specific and audited, not vague.

Partial

WebGPU — Supported, verified on Linux and in the browser Partial

In alpha.1 this was a backbuffer-only forward renderer. It now reports real MRT (two to four targets), occlusion queries, wireframe, multi-stream input, instancing, probed MSAA and float render targets, PBR, image-based lighting and shadow sampling, with a browser route through the Emscripten emdawnwebgpu port and opt-in compiled effects. CNA declared it Supported on 17 October 2026 and runs it in its platform and glTF CI jobs; it is verified on Linux x86_64 and in headless Chrome only, its Windows, macOS and linux-aarch64 packages are unverified, and SpriteSortMode::Immediate batches its sprites.

Partial

SDL_GPU as the Windows, macOS and iOS default — not yet qualified there Partial

Since the renderer set was narrowed after the 0.1.0 release, SDL_GPU is the default on Windows, macOS and iOS. CNA’s own status: it is validated on Linux (Vulkan) and, cross-compiled, under Wine with vkd3d-proton (Direct3D 12); a native Windows run, a re-run on Apple hardware and any iOS build are not done (CI has a gating macOS smoke leg and non-gating iOS legs). Gaps to be implemented or capability-gated: ShaderEffect is compiled out on Windows, Apple and the browser, occlusion queries are unavailable, BlendState.MultiSampleMask is ignored, and Immediate-mode sprites are batched.

Thin

Continuous integration Partial

The snapshot contains 18 workflow files (25 jobs; 16 of the files trigger automatically on pushes and pull requests, and 22 of the jobs run that way) covering Linux, Apple (macOS and iOS, on macos-26 runners), Emscripten, the SDL3, HEADLESS and TERMINAL platform implementations (SDL3 on SDL’s x11 and wayland drivers), multi-renderer selection and six build-free C API gates. The general job runs the unfiltered suite on OPENGLES3 with no known-failure allowlist. Still absent: any workflow for Android, building the C API library or running the oracle corpus; the Windows lanes remain manual; and nothing builds the CNAEXT extensions, Diagnostics or the Inspector. The working lanes provide useful scoped evidence, but not exhaustive coverage across 10 identities, graphics drivers, physical devices or the complete GPU pixel/oracle matrix.

Open

Truthful capability reporting Partial

At the device level six GraphicsCapability answers are derived rather than read from the renderer’s switch: compiled effects, float and half-float render targets (from the renderer’s format classification) and half-float linear filtering come from dedicated hooks that default to false, and multiple render targets and Texture3D are capped by the GraphicsProfile. The remaining entries still fall through to the renderer's own switch, whose shared default is permissive. DIRECTX9 still never overrides SupportsCapability() — so it advertises MSAA, occlusion queries, custom effects and instancing without necessarily querying the device. The RendererCapabilityProfile adds device-probed answers, but a true from the older capability API still means "not contradicted", not "verified".

Experimental

Experimental C API — release gate "Not ready" Partial

The C ABI is at 0.50.0 (alpha.1: 0.7.0; the 0.1.0 release: 0.46.0) with 60 headers, 3,212 generated routes and 196 recorded struct layouts. Its committed release report records one unmet criterion: 625 in-scope public C++ declarations still lack C mappings (8,125 inventoried: 7,032 implemented, 15 partial, 625 planned, 453 not applicable). No CNA CI job builds the library; CNA’s own development trees build and test it on Linux and run its pure-C suites under Wine, and CNA.NET builds and uses an earlier generation. ABI 0.x is experimental, and several minor steps were incompatible, three of them after the 0.1.0 release. The C# binding CNA.NET admits exactly 0.47.0; the Common Lisp, Go, Java, Python, Ruby, Rust, Swift and TypeScript bindings are archived and will not follow new ABI versions. See Experimental Native C API.

Remaining boundaries

Work that remains before 1.0

Highest impact

Compiled effects beyond qualified builds Partial

XNA/FNA D3D9 Effect Framework binaries now load through Effect and XNB EffectReader on 8 of the 10 identities: FNA3D always, and seven more behind default-OFF build options. What remains open is the no-pixel renderers, and the default configure, which reports the capability on FNA3D only. HLSL .fx source, DXBC and MGFX remain unsupported at run time; .fx sources compile only at build time through an external legacy fxc, which was not exercised on macOS.

Planned

Consistent surface-format coverage Renderer-dependent

Public Texture2D format admission is renderer-qualified: six renderer families (SDL_GPU, WebGPU, Direct3D 9, FNA3D, EasyGL and Software) classify texture formats themselves (four of them render-target formats too), while the others defer to the framework's Color-only public rule even when an internal renderer layer knows additional native formats. The default Reach profile additionally refuses the eleven HiDef-only formats. The remaining task is a truthful, tested per-renderer contract for every format a game intends to use.

Partly done

ReflectiveReader for custom XNB types Partial

The XNB loader has 61 built-in readers. Video, typed external references and compiled effects are represented, and custom readers can be registered explicitly, either as a ContentTypeReader<T> or, since alpha.1, through ReflectiveTypeReaderBuilder and EnumTypeReader from a declared field list. What remains absent is runtime reflection-based discovery, which C++ does not offer: user and closed-generic types still require deliberate registration.

Planned

Gamer Services beyond Linux Open

The service client, relay and server are qualified on Linux; on macOS, CNA’s Apple campaign records them on one physical Mac mini M4, with online play needing a WebSocket-capable libcurl rather than Apple’s system one. Open: Windows (credential storage is sealed with DPAPI but has run only under Wine; the server has not run natively), a real wide-area network, browser builds (where the service, relay and voice are absent), iOS (built without networking) and no public server instance is operated. Online sessions refuse guests. (Offline leaderboard stream columns, a gap listed here before, are persisted since the demos repair campaign.)

Planned

Media portability and codec coverage Platform-dependent

The Media catalogue layer, playback, and FFmpeg-backed video paths are implemented. Remaining boundaries are platform and codec specific: the Video types exist in every build, but file-backed decoding needs the optional FFmpeg backend, which is built only on Linux and macOS, so elsewhere it throws NotSupportedException; on macOS a binary linked against Homebrew’s FFmpeg starts only on the macOS that FFmpeg was built for. SDL_mixer does not provide AAC decoding for .m4a/.aac; CNA's own ALSA mixer decodes WAV, Ogg Vorbis, MP3 and FLAC, and Opus, WMA and XMA are not decoded. Expand only with explicit build and runtime evidence.

Planned

Deeper tests for Media and Storage Open

Coverage is uneven rather than absent: Storage now has 70 GoogleTest-family definitions, most of them error, path and sharing contracts added by the repair campaigns, and Media more than 300. Those source counts still leave many runtime paths and platform combinations without execution evidence.

Open

Android and oracle checks in CI Open

Android has code, an SDL entry point and a demo Gradle project, but no workflow builds for Android. The 39-scene XNA oracle diff is a CTest only in a DIRECTX9 plus Wine cross-build tree and is in no workflow; the last consolidated dated DIRECTX9 report covers 31 scenes (later per-scene notes record the rest) and a native-Windows re-run is open; EasyGL and Software have a CTest on two line scenes only (the EasyGL test fails on any pixel difference; the Software test only if a scene does not render). Software has been measured at 18 of 39 scenes byte-exact.

Planned

CNA.NET on Windows and iOS, and on macOS beyond local evidence Future qualification

CNA.NET’s runtime qualification covers Linux x86_64, headless Chromium and the x86_64 Android emulator and, as local evidence on a physical Mac mini M4, macOS on Apple silicon (osx-arm64): its managed suites, package acceptance, the template and a smoke run of all 84 samples on SOFTWARE, against an earlier CNA and without a CI leg, signing or notarization. CNA.NET has not yet admitted the C ABI of this snapshot. Windows has documented build steps but nothing has been run on it; iOS is planned through static linking. Interactive browsers, hardware GPUs in the browser, physical Android devices and a macOS CI leg are the next evidence to collect.

Long term

Public stable release (v1.0) Long term

The project is versioned and released 0.1.0, but it is deliberately pre-1.0, and this snapshot is unreleased development after that tag. Reaching 1.0 requires an explicit compatibility policy, stable public APIs (the C ABI is 0.x and has taken incompatible steps recently), clearer renderer capability contracts, reproducible configuration-scoped verification and production evidence on the platforms CNA intends to support.
