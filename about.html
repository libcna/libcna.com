About

What is CNA?

A native C++ framework that mirrors the XNA 4.0 programming model - without a managed runtime, without a virtual machine, just clean C++23 on SDL3.

⚠

Measured against FNA, essentially every public XNA 4.0 type is now present in CNA — the only outright absences are five reflection-only ContentSerializer attributes that have no meaning in C++. Presence is not the same as behaviour, though, and CNA is honest about the split: Graphics, Input, Audio, Net, Storage and the math namespace are production-real, while Media's catalogue types and all of GamerServices are deliberate API-shaped no-ops that let XNA code compile. A real .xnb content pipeline now exists (49 type readers, genuine LZX decompression); you register the built-in readers once at startup. The biggest remaining gap is compiled .fx shader bytecode, which still throws — custom shaders must be hand-written GLSL/SPIR-V through ShaderEffect. A second real limit: only SurfaceFormat::Color textures can be constructed, so float/half/HDR render targets are unavailable despite the enum listing them. Verification is real: 4,845 unit tests and 648 backend pixel/integration tests across 14 selectable backends, plus differential testing against a running FNA build and a 39-scene oracle corpus diffed pixel-exactly against the real XNA 4.0 runtime. 63 of the 86 official XNA samples build on it. APIs are still evolving — good for research, demos and porting experiments, not yet for shipping a commercial game.

📝

Where the project actually stands. CNA is 236,708 lines across 908 source files and extremely active — 2,738 commits, 2,183 of them in July 2026 alone. That pace cuts both ways: ten of the fourteen rendering backends are only about two weeks old, and their maturity tracks their age closely. CI is thin (one auto-triggered Linux workflow running a subset of tests); the full suites are run locally. Media and Storage have no unit tests at all.

Background - the XNA programming model

Microsoft XNA Game Studio was a managed game development framework targeting Windows, Xbox 360, and Windows Phone. Released around 2006–2013, it offered developers a clean, well-structured API for 2D and 3D game development. The framework's game loop (Initialize, LoadContent, Update, Draw), its sprite batching system, content pipeline, and the Microsoft.Xna.Framework namespace hierarchy were widely praised for their clarity.

XNA was discontinued by Microsoft in 2014. The open-source community responded with notable projects:

  • FNA - a fully managed C# reimplementation that is binary-compatible with XNA 4.0, built on SDL2.
  • MonoGame - a cross-platform C# successor to XNA, used commercially to this day.

Both FNA and MonoGame are excellent projects. However, both remain in the managed C# ecosystem. There was no mature native C++ reimplementation of the XNA 4.0 API.

Why CNA?

CNA was created to fill a specific niche: native C++ implementation of the XNA 4.0 API. The reasons this is useful:

  • No managed runtime: C++ avoids garbage collection pauses, managed heap overhead, and JIT warmup costs. Useful for performance-critical or embedded scenarios.
  • Toolchain flexibility: C++ integrates directly with any C or C++ codebase, LLVM toolchains, and embedded/console targets that may not support .NET.
  • API preservation: The XNA programming model is genuinely good design. Preserving it in C++ keeps the conceptual clarity that game developers appreciated while moving to a native runtime.
  • Portability: Built on SDL3, CNA targets Linux (primary, and the only platform with automatic CI), Windows (MinGW-w64 cross-toolchain plus native MSVC, with the Direct3D 9/11/12 backends Windows-gated and verified from Linux through Wine+DXVK / vkd3d-proton), Web/Emscripten (its own CMake preset and the Emscripten-only CANVAS backend), and Android (wired through CMake and the NDK). macOS handling is minimal and iOS is not addressed.

What problem does CNA solve?

If you are building a game or engine in C++ and you want:

  • A familiar, well-structured game loop modelled after XNA
  • A SpriteBatch API for 2D rendering and BasicEffect-powered 3D rendering
  • A GraphicsDevice abstraction that hides backend details — one of 14 backends chosen at build time, from production-ready EasyGL through Vulkan, Direct3D 9/11/12, SDL_GPU, SDL_Renderer, bgfx and WebGPU down to the GPU-free Software and Headless backends for CI
  • Complete input handling — Keyboard, Mouse, GamePad (a real SDL3 bridge with rumble, trigger rumble, LED and hot-plug), and a TouchPanel that genuinely detects all 10 XNA gesture types
  • Audio via SoundEffect, SoundEffectInstance, and MediaPlayer — plus a real XACT implementation that parses the XGS/XWB/XSB binary formats and plays them back, rather than a facade
  • Real SystemLink multiplayer via NetworkSession, backed by genuine ENet over UDP with real LAN discovery. (PlayerMatch and Ranked correctly no-op, as they require Xbox Live, and GamerServices is an API-shaped shim with no backend of any kind.)
  • A real .xnb content pipeline, with loose-file loading as a fallback
  • The ability to swap rendering backends without changing game code

…then CNA provides these today while keeping the implementation in native C++23 — with the caveats above about .fx bytecode, surface formats and GamerServices.

What CNA is not

  • CNA is not a C# framework or a .NET library.
  • CNA is not affiliated with or endorsed by Microsoft Corporation.
  • CNA does not use any Microsoft, Xbox, or XNA branding assets. XNA is referenced only as the compatibility target and API inspiration.
  • CNA is not a game - it is a framework and runtime abstraction layer.
  • CNA is not a macOS or iOS framework — macOS gets minimal handling and iOS is not addressed at all.
  • CNA is not yet recommended for shipping commercial games, though it is suitable for research, demos, and open-source development.

In practical terms: where FNA provides a C# class implementing a particular XNA behaviour, CNA translates that behaviour into C++23 idioms - replacing managed types with RAII, delegates with virtual methods, and properties with getter/setter methods. The game-facing API shape follows FNA's C# surface as the authoritative XNA 4.0 reference, while the internal implementation is native C++ throughout.

Both FNA and MonoGame remain excellent choices for managed C# game development. CNA serves the C++ ecosystem specifically.

C++ API differences — the NOXNA marker

Declarations marked with NOXNA in CNA's source code are not part of the XNA 4.0 public API. NOXNA is an empty marker macro that visually tags every non-XNA declaration — there are 1,289 of them across the public headers — and a CMake option enforces the boundary at compile time, turning every non-XNA-tagged declaration into a [[deprecated]] warning under -Werror. When consuming the API as a game developer you can use NOXNA declarations freely; the marker simply means they have no XNA counterpart.

Some of it is plain C++ glue (iterator support, RTTI helpers, RAII wrappers), but a lot of it is substantial functionality XNA never had:

  • Graphics: ShaderEffect (the only custom-shader path), PbrEffect/SkinnedPbrEffect for physically based rendering, SkinnedModelEXT with AnimationPlayer, AnimationClipEXT, BoneTrackEXT and KeyframeEXT for skeletal animation, MorphTargetEXT blend shapes, tangent/skinned vertex types, and sRGB/BC7 surface formats.
  • Input: around 17 GamePad extension methods (GUID, light bar, trigger vibration, gyro/accelerometer, power info, touchpad fingers, Steam handle), paddle and touchpad buttons, scancode-based Keyboard methods, MouseCursor and TextInputEXT.
  • The whole CNA:: namespace — roughly 58 public headers that are not XNA at all: Camera, FileDialog, MessageBox, SystemTray, Clipboard, UrlLauncher, Locale, PowerInfo, DisplayInfo, SystemInfo, full Joystick/Haptics APIs, Logger, and render-pipeline settings including PbrMaterial, TonemappingMode and ShadowQuality.

Note that the CMake options gating the extended layers (CNA_NOXNA and CNA_DEVICES) both default to OFF, so they are not exercised by any current build or CI job.

Technology stack

  • Language: C++23 — requires GCC 12+, Clang 15+, or MSVC 2022 v17.8+
  • Platform foundation: SDL3 (vendored submodule) — windowing, input, audio initialisation
  • Image loading: SDL3_image (vendored submodule) — PNG, JPG, BMP, and more
  • Audio: SDL3_mixer (vendored submodule) — SoundEffect, SoundEffectInstance, MediaPlayer/Song
  • OpenGL backend: easy-gl — a sibling repo providing a toolkit-independent OOP wrapper over OpenGL/GLES; required only for the EASYGL backend
  • DirectDraw backend: free-direct — a sibling repo reimplementing a DirectX 3 / DirectDraw 2D subset over SDL3; required only for the DX3 backend
  • Runtime support: sharp-runtime — a required sibling repo, and a serious project in its own right: a C++23 reimplementation of a .NET BCL subset at 135,204 LOC with roughly 12,375 test cases. It implements System::* broadly — primitives, Collections (Generic/Immutable/Concurrent/Frozen/Specialized), IO (plus Compression and Hashing), Text (including a full System.Text.Json and Regex), Net (Sockets/Http/WebSockets), Threading (plus Tasks and Channels), Xml, Globalization, Numerics (including BigInteger) and hashing-only Security.Cryptography. This is where bytecs, intcs and Single come from
  • Video playback: FFmpeg — real libavcodec/libavformat decoding for VideoPlayer, with PTS-driven pacing. Unavailable on Emscripten, Android and every Windows target, so video playback is effectively native-Linux-only today
  • Networking: in-tree enet for reliable UDP; also in-tree are cgltf, stb and a pinned wgpu-native
  • Build system: CMake 3.20+ with the CNA_GRAPHICS_BACKEND flag selecting the rendering backend at compile time. Because that choice is compile-time, full coverage requires 14 separate configure/build/test runs
  • Test suite: GoogleTest (CnaTests target) — 4,845 test cases across 419 suites, covering Graphics (1,627), CNA internals (553), Audio (493), Devices/Sensors (356), GamerServices (311), Input (232), Net (174), Content (158) and the core math types
  • Model tooling: gltf_to_cnj, an offline glTF 2.0 → .cnj Model/AnimationClip converter built unconditionally — CNA's actual content path for models

Real-world validation

Unit tests only prove that the code does what its author expected. CNA is checked against several things it does not control:

  • A real XNA reference renderer. The oracle corpus under tools/xna-oracle/ holds 39 scenes rendered by a genuine C#/XNA reference renderer, diffed pixel-exactly (--tolerance 0) against CNA's D3D9 output. D3D9 is the backend that uniquely targets pixel-exact XNA 4.0 authenticity.
  • A running FNA build. A C# harness links the real FNA build, dumps reference values to JSON, and a script diffs them against CNA's own output. Ground truth comes from executing the reference implementation, not from reading its source.
  • The official XNA sample collection. cna-samples ports Microsoft's XNA Game Studio 4.0 samples to C++ on CNA: 86 samples, of which 63 currently build.
  • GPU pixel readback. 648 backend integration and pixel tests run as CTest entries; roughly 436 of 559 example programs (78%) do real GPU→CPU readback with exact-match assertions at zero tolerance, plus 17 golden PNGs.

Beyond that, CNA Craft (a voxel game) and the browser demos exercise the API under real game-code conditions, including in WebAssembly. Be aware of the limits, though: none of these suites are gated by CI, and Media and Storage have no unit tests at all. See Verification & Known Issues for the full picture, including what is currently broken.
