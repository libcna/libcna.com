Contributing

Contribute to CNA

CNA is an open-source C++23 reimplementation of the XNA 4.0 API built on SDL3. Contributions of any kind are welcome — new implementations, tests, platform fixes, and documentation improvements all help.

Getting started

Step 1 — Clone CNA and initialise submodules

git clone https://github.com/openeggbert/cna.git
cd cna
git submodule update --init --recursive

This populates third_party/SDL, third_party/SDL_image, and third_party/SDL_mixer. SDL3 is built from source by CMake — no system SDL packages are required.

Step 2 — Clone sibling repositories

CNA always requires sharp-runtime as a sibling directory next to cna/. Two more siblings are needed only by specific backends: easy-gl for EasyGL and free-direct for FreeDirect.

parent/
├── cna/
├── sharp-runtime/   # always required
├── easy-gl/         # required by the OPENGLES3 backend
└── free-direct/     # required by the FREEDIRECT backend

Clone them at the same level:

git clone https://github.com/openeggbert/sharp-runtime.git
git clone https://github.com/openeggbert/easy-gl.git
git clone https://github.com/openeggbert/free-direct.git

Step 3 — Build with EasyGL

cmake -S . -B build -DCNA_GRAPHICS_RENDERER=OPENGLES3
cmake --build build --target CnaTests

The CNA target builds the framework library. The CnaTests target builds the GoogleTest unit-test binary. CNA selects its backend at build time — exactly one per build, with no runtime dispatch — so testing another backend means a fresh configure. The 14 valid values are SDL_RENDERER, OPENGLES3, BGFX, VULKAN, WEBGPU, HEADLESS, SOFTWARE, DIRECTX11, DIRECTX12, CANVAS, FREEDIRECT, DIRECTX9 and SDL_GPU. See the Building documentation for cross-compilation instructions.

Step 4 — Run the tests

ctest --test-dir build --output-on-failure

The CnaTests binary holds 6,818 GoogleTest case definitions across 433 test files, plus 1,621 CMake-registered renderer pixel/smoke tests tree-wide. All should pass on a clean Linux build with the EasyGL backend. If any fail, please open an issue with the full CTest output.

ⓘ

Because backend choice is compile-time, full coverage requires 14 separate configure + build + test runs. Only one CI workflow is auto-triggered, and it runs a five-way Linux matrix over the input-labelled tests — so verifying your change on more than one backend locally is genuinely valuable.

Repository structure

PathContents
include/Microsoft/Xna/Framework/ Public C++ headers — the XNA 4.0 API surface. Any type or method added here must match the XNA 4.0 public API (or be marked CNAEXT).
src/ Implementation files corresponding to the public headers.
tests/ GoogleTest unit tests (CnaTests target — 6,818 case definitions across 433 test .cpp files). Heaviest areas: Graphics 1,627, CNA internals 553, Audio 493, Devices/Sensors 356, GamerServices 311, Input 232, Net 174, Content 158, core math ~700.
third_party/ Vendored submodules: SDL3, SDL3_image, SDL3_mixer. Do not modify these directly.
docs/ CNA-internal documentation: xna-4-api-coverage.md, coverage.md, and related notes on implementation status.
CHECKLIST.md Per-file porting checklist tracking which XNA types have been ported. Also explains the CNAEXT marker convention.
GRAPHICS_TASKS.md Graphics-specific implementation task plan listing remaining work per backend.

The CNAEXT marker

📝

Rule: When porting XNA APIs, stay faithful to the public XNA 4.0 surface. Use the CNAEXT marker only for C++ glue code that has no counterpart in the managed XNA/FNA API.

Methods and types annotated with a // CNAEXT comment in the source are not part of the XNA 4.0 public API. They exist purely to support C++ idioms and integration patterns. Examples:

  • Iterator support — begin() / end() on collections to enable range-for loops
  • GetTypeName() — runtime type name helper for debugging
  • RAII helpers and move constructors that have no equivalent in managed C#

The authoritative reference for the XNA 4.0 public API surface is FNA (C#). When in doubt whether a method belongs to the XNA API, check the corresponding FNA class. If it is present there without modification, it belongs in CNA without the CNAEXT marker. If it is a C++-only addition, mark it CNAEXT.

What needs work

Below are the most impactful contribution opportunities, grouped by area. Any of these would be a meaningful addition to the project.

Open

Compiled .fx shader bytecode

The highest-leverage gap in the whole project. Effect's bytecode constructor throws, so any XNA game with custom HLSL shaders cannot be ported without rewriting them by hand — it is what blocks 23 of the 86 official XNA samples. Wants someone comfortable with DXBC/HLSL bytecode and a translation path to GLSL/SPIR-V.

Open

bgfx 32-bit index buffers

A confirmed correctness bug. The bgfx backend never overrides CreateIndexBuffer32, so 32-bit indices are uploaded into a 16-bit buffer and DrawUserIndexedPrimitives corrupts geometry. Every other 3D backend implements this. Well-scoped and clearly diagnosed — a good first substantial contribution.

Open

bgfx D3D and Metal shader variants

bgfx ships 108 shader blobs, but only for GL, GLES, Vulkan and WebGPU — there are no D3D or Metal variants. The practical consequence is that 3D silently draws nothing on bgfx's default Windows and macOS renderers. Building out the missing shader variants through bgfx's shader toolchain would make the backend genuinely cross-platform.

Open

Truthful SupportsCapability()

The base implementation returns true for every capability except multi-stream vertex input, and DIRECTX9, DIRECTX11, DIRECTX12 and SDL_GPU never override it at all. Because the default fails open, several renderers advertise features whose implementation throws or silently does nothing. Renderers that report honestly — deterministically refusing what they cannot do — are the model to follow. Mechanical, high-value, and easy to verify.

Open

DIRECTX12 scissor, viewport, stencil and blend factor

DIRECTX12 has a strong core (PSO and root-signature caches, a barrier tracker) but four unimplemented pieces of fixed-function state, and its MRT path clears attachments but never draws to them. Windows-only work with a clear specification and existing sibling implementations in DIRECTX9 and DIRECTX11 to follow.

Open

Draw-offset handling

startIndex and baseVertex are ignored on DIRECTX11, and on bgfx outside the wireframe path. Any code that draws a sub-range of a shared buffer therefore renders the wrong geometry on those backends. Small, well-defined, and pixel-testable.

Needs CI

Broader CI coverage

CI is broader than it once was — eight workflows now cover Linux tests, input, devices and sensors, 32-bit arithmetic, headless-Chromium HTML_DOM tests and a macOS/Metal build, with two Windows MSVC workflows on manual dispatch. It is still thin relative to the project's surface: several workflows only fire on master/main and so lie dormant on develop, roughly three-quarters of the 46 renderers have no CI coverage, there is no Android or Emscripten-build CI, and neither the full unit suite nor the GPU pixel suites are gated. Extending any of this is real, useful work.

Needs a Windows toolchain fix

CnaTests on Windows

The full CnaTests suite cannot build on any Windows toolchain: roughly ten test files use the POSIX ::setenv(). Replacing those with a portable shim would let the whole unit suite run natively on Windows for the first time, which in turn would make Windows CI worth expanding.

Unofficial

macOS support

CNA has minimal macOS handling today and no macOS CI. If you have a Mac, a build report or a CI workflow would be very welcome. Note that bgfx has no Metal shader variants, so EasyGL or Vulkan (via MoltenVK) are the realistic starting points.

Open

XNB reader gaps

The .xnb pipeline is real — 50 registered type readers, an LZX decompressor, fuzz-hardened parsing, wired into ContentManager. The remaining gaps are specific: there is no ReflectiveReader, so no custom or user-defined type can be loaded from XNB at all; EnumReader, ExternalReferenceReader and VideoReader are missing; and EffectReader is a placeholder that always throws. The Array/List/Dictionary/Nullable readers are implemented but not registered, since without reflection each closed generic needs hand-registration. See XNB Content Pipeline.

Open

ContentManager lifecycle

ContentManager::Unload() clears its maps without disposing the assets they held, and ResourceContentManager is the repository's only pure stub. Both are small, self-contained fixes with obvious correctness criteria.

Always welcome

Test coverage

6,818 GoogleTest case definitions exist, but coverage is uneven — Media and Storage have zero unit tests, which is the clearest gap on the board. The Canvas backend is another: it is mature within its narrow Emscripten scope but no automated test ever renders a Canvas pixel. New GoogleTest unit tests for any type are accepted without reservation; follow the pattern in tests/. Pixel tests under examples/ are equally welcome — roughly 436 of the 559 example programs already do real GPU-to-CPU readback with exact-match assertions.

Code style

  • C++23 throughout. CNA requires GCC 12+, Clang 15+, or MSVC 2022 v17.8+. Use modern C++ features freely — structured bindings, ranges, concepts — but keep readability first.
  • API shape is fixed. The Microsoft::Xna::Framework public API mirrors XNA 4.0 exactly. Do not rename, remove, or add overloads to public methods without a compelling reason backed by FNA precedent.
  • Properties become getter/setter methods. C# public int Width { get; set; } becomes intcs getWidthProperty() const and void setWidthProperty(intcs value) in C++.
  • Use sharp-runtime types. Use intcs, bytecs, Single, String, events, and interfaces from sharp-runtime to match C# semantics. Avoid raw int or float at the public API boundary.
  • No extra runtime dependencies. CNA's dependency set is deliberately small and mostly vendored or submoduled — SDL3 (plus SDL_image and SDL_mixer), sharp-runtime, and the per-backend siblings easy-gl and free-direct, alongside in-tree enet, cgltf, stb and wgpu-native. Do not introduce new third-party libraries without prior discussion.
  • Mark non-XNA additions as CNAEXT. Any method or type added purely for C++ convenience must carry a // CNAEXT comment so that API coverage tooling stays accurate.
